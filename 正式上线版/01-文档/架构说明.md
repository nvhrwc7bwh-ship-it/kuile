## 一、整体架构

```
微信小程序（03-小程序前端）
    │  HTTPS + Bearer Token
    ▼
   Nginx（04-部署脚本/nginx-kuile.conf）
    │  限流 / HTTPS / 反向代理
    ▼
   Node.js 后端（02-后端）:3000  ← 只监听 127.0.0.1
    │
    ├──→ MySQL 8.0（**自建**，同机 :3306，只监听 127.0.0.1）—— 业务数据
    ├──→ 腾讯云 COS —— 打卡照片
    ├──→ 火山方舟（豆包 vision）—— AI 打卡判定
    ├──→ 微信开放接口 —— 登录换 openid
    └──→ 微信支付 —— 押金收取与退还
```

**为什么是这套组合：**

- **Node.js + Express**：轻量、部署简单，腾讯云轻量应用服务器直接跑 PM2 就行。
- **MySQL（自建）**：关系型数据（用户、Flag、打卡、见证关系），事务支持是押金正确性的基础。
  装在同一台服务器上，**只监听 `127.0.0.1`** —— 不对公网开放，
  所以不需要额外买托管数据库，也不需要配数据库安全组。
- **COS**：照片存对象存储，不占服务器磁盘和带宽。
- **火山方舟**：国内可直接调用，无需翻墙；视觉模型能读秤面读数。

## 三、核心设计决策

### 3.1 规则引擎独立成纯函数

`domain/rules.js` 里的函数**不碰数据库、不碰网络**，只接收数据、返回结果。

**好处：**
1. 可以用 `tests/rules.test.js` 直接断言，不用起数据库
2. 改规则的影响面一目了然
3. 未来要迁到其他语言/服务，直接搬这个文件

**新增规则的标准流程：**
1. 在 `rules.js` 里写函数
2. 在 `tests/rules.test.js` 里加断言
3. 改调用方
4. 跑 `npm test`

### 3.2 前端不写死任何规则

所有周期参数、押金档位、信用上限都通过 `GET /api/flags/config` 下发。

**为什么重要：** 信用分从 60 涨到 90，能立的周期从「7/14」变成「7/14/30/90」，押金上限从 500 变成 5000。如果前端写死，规则一变就出错。

### 3.3 支付回调必须幂等

微信支付会**重复推送**同一个回调（这是官方机制，不是异常）。

处理链路：

```
回调到达
  → 验签（不通过直接拒绝）
  → 解密
  → 事务开始
  → SELECT ... FOR UPDATE 锁住订单
  → 检查 status 是否已是 success
      → 是：直接返回（幂等）
      → 否：更新订单 + 写押金流水 + 更新 Flag
  → 提交事务
```

订单表上有 `UNIQUE KEY uk_out_trade_no (out_trade_no)` 做最后一道防线。

### 3.4 金额一律用「分」做整数运算

`settleDeposit` 里：

```js
const paidCents = Math.round(paid * 100);
const deductCents = Math.round(paidCents * rate);
return { refund: (paidCents - deductCents) / 100, deduct: deductCents / 100 };
```

**为什么：** `0.1 * 0.35 = 0.035000000000000003`，浮点误差在退款场景是资金 bug。

### 3.5 AI 只做初筛，不直接定生死

```
AI 判定 → 通过   → 打卡成功
AI 判定 → 存疑   → 转人工复核（不惩罚）
AI 判定 → 驳回   → 转人工复核队列（不直接判负）
AI 调用失败      → 转人工复核（不误伤）
```

**理由：** 模型会因光照、角度、秤型号判断错误。直接判负会造成大量投诉。

**留痕要求（合规）：** 每一次判定都写 `ai_review` 表，包含：
- 模型名、提示词版本号（`prompt_version`）
- 模型原始返回（`raw_response`，JSON）
- 结论、置信度、理由、耗时

这样即使半年后有人质疑「当时 AI 怎么判的」，也能完整还原。

### 3.6 定时任务而不是事件驱动

`syncLifecycles()` 每 60 秒跑一次，做三件事：

1. 筹备期到期 → 转进行中（冻结名单、拍定档位）
2. 断卡判定（打卡日次日凌晨）
3. 结束日到期 → 自动结算

**为什么不用精确的定时器：** 断卡判定依赖「日」的边界（凌晨 0 点），用轮询比维护 N 个定时器可靠得多。60 秒的精度对「天」级业务完全够用。

### 3.7 押金逐用户独立记账

`deposit_ledger` 表记录每一笔进出一账，带 `flag_id` + `user_id`。

对应产品规则「押金池隔离要求」：逐用户独立记账、专款专用、押金不是平台收入。

### 3.8 🆕 名义押金与实收押金分离（内测免收的核心设计）

本次上线采用「内测阶段暂不收取押金」模式，由 `config.deposit.enabled`
（`.env` 的 `DEPOSIT_ENABLED`）控制。

**两个金额字段回答两个不同的问题：**

| 字段 | 含义 | 内测期取值 | 正式期取值 |
|---|---|---|---|
| `flag.deposit_amount` | **名义押金** —— 这一局「本来要押多少」 | 照常记录（如 500） | 照常记录 |
| `flag.deposit_paid` | **实收押金** —— 实际收到多少 | **0** | 500 |

**设计要点：结算逻辑只认 `deposit_paid`，不看全局开关。**

这带来一条铁律：**收过的钱一定退，没收过的钱绝不退。**

| 场景 | 若按「名义押金」结算会怎样 | 按「实收」结算（当前实现） |
|---|---|---|
| 内测局 → 后来打开开关 → 才结算 | 退一笔**从没收到过**的钱（资损） | 实收 0 → 扣 0、退 0 |
| 正式局 → 后来关掉开关 → 才结算 | 收了钱不退款（违规 + 投诉） | 实收 500 → 照常退款 |

**这条不变量由 `tests/beta-deposit.test.js` 的 18 项断言守着**，
包含「开关中途翻转」这种在常规测试中根本不会暴露的场景。

**接口契约：**
- `POST /api/pay/create` —— 内测期不创建订单、不调微信支付，返回 `{ beta: true }`
- `GET /api/health` —— 返回 `depositEnabled`，供部署后自检
- `GET /api/flags/config` —— 返回 `depositEnabled`，供前端显示参考
- `GET /api/notifications/...`（记录卡）—— 返回 `depositEnabled`，但**按实收判断**，避免虚假告知

**前端为什么不能自己判断要不要支付？**
前端拿到的 `depositEnabled` 可能来自**本地缓存**（会过期）。
如果服务器把开关从 `false` 改成 `true` 而缓存没过期，
前端会跳过支付 —— **用户的押金永远收不到钱**。
所以前端只负责提交，**「收不收钱」一律听 `/api/pay/create` 返回的 `beta` 标记**。

### 4.2 三个设计约定

**ID 统一 VARCHAR(32) + 业务前缀**
`usr_` `flg_` `cki_` `fw_` `vd_` `msg_` `ord_` `led_` `cl_` `ntf_` `rc_`
好处：日志里看到一个 ID 就知道是什么类型，不用查表。

**时间统一 UTC 存储**
`DATETIME` 存 UTC，接口返回 ISO 8601 字符串，前端负责转本地时区。服务器换时区不会影响数据。

**金额统一 DECIMAL(10,2)**
`mysql2` 配置了 `decimalNumbers: true`，取出来就是 JS number。

### 4.3 只追加不改的表

`credit_log`（信用分流水）和 `deposit_ledger`（押金流水）**只追加，永不 UPDATE**。

这是财务和信用体系的审计基础 —— 任何时候都能重建出「这一局是怎么结算的」。

### 5.1 网络层

`utils/api.js` 统一封装：
- 自动带 `Authorization: Bearer <token>`
- 业务错误码统一处理（401 自动清 token 并重启）

### 5.2 页面清单

| 页面 | 路径 | 作用 |
|---|---|---|

| 广场 | `pages/square` | 全部公开 Flag，三种排序 |
| 通知 | `pages/notifs` | 站内通知 + 待办入口 |

| 打卡 | `pages/checkin` | 拍照 + 填表 + 轮询 AI 判定 |
| 目标详情 | `pages/flag` | 节点、见证席、留言、举报 |
| 见证席 | `pages/witness` | 判定投票 + 我的任务 |
| 用户主页 | `pages/profile` | 公开信息 |
| 记录卡 | `pages/record` | 结局产物，可分享 |

### 5.3 打卡页的判定轮询

```
提交打卡 → 拿到 checkinId
       → 每 2 秒查一次 /api/flags/:id/checkins
       → status 从 pending 变成 ok/rejected 时停止
       → 最多 15 次（30 秒）后提示用户稍后再看
```

**为什么轮询而不是 WebSocket：** 判定是秒级的短任务，轮询实现简单、不会漏消息、对服务器压力可忽略。WebSocket 在小程序里要额外配置且很多场景用不上。

## 七、测试策略

### 7.1 规则测试（必须）

```bash
npm test
```

共 **110 项断言**，分五层。**改任何规则后必须跑。**

| 层 | 项数 | 覆盖 |
|---|---|---|
| 规则对账 | 60 | 逐条对应《参数速查表》 |
| 数据层一致性 | — | 静态比对代码与建表 SQL，24 张表全对齐 |
| 业务编排集成 | 19 | 完整业务流程（含内存数据库替身，不需装 MySQL） |
| 🆕 内测押金专项 | 18 | 名义/实收分离、开关翻转不产生资损 |
| 接口冒烟 | 13 | 全部路由注册、鉴权与参数校验生效 |

规则对账的覆盖范围：
- 周期天数、结束日、节点位置、中期到账
- 断卡容忍次数与三种后果
- 档位分级、系数、只降不升
- 信用分区间、等级分档、分段到账
- 押金区间、扣收比例、失败损失、新人保护
- 判定聚合、见证门槛、结算分值
- 成功/失败判定

内测押金专项额外覆盖：
- `DEPOSIT_ENABLED` 默认值为 `false`（安全默认值）
- 内测期失败结算**不扣押金**（扣 0 元）
- 内测期失败**照常扣信用分**（承诺本身照样生效）
- 正式期结算照常扣收与退款
- **开关中途翻转不产生资损**（内测局不退款 / 正式局照退）
