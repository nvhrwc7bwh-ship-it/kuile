## 一、部署前准备

### 1.1 你需要有的东西

- [ ] 腾讯云轻量应用服务器（Ubuntu 22.04），已能 SSH 登录
- [ ] 域名已备案，HTTPS 证书已下载（Nginx 格式）
- [ ] **服务器上已装好 MySQL 8.0**（自建，见 2.0 节）
- [ ] 腾讯云 COS 存储桶
- [ ] 火山方舟 API Key + Endpoint ID
- [ ] 微信支付商户号 + APIv3 密钥 + 商户私钥

> **💡 原理：为什么这 6 样东西缺一不可？**
> 这就是**一个完整的小程序后端要连的「五方 + 一份配置」**：
> - 服务器（跑 Node + Nginx + **自建 MySQL**）— 你自己的机器
> - 数据库（存业务数据）— **本机自建 MySQL 8.0**
> - 对象存储（存照片）— 腾讯云 COS
> - AI 服务（判打卡）— 火山方舟
> - 微信开放接口（登录换 openid）
> - 微信支付（收押金）
>
> 每一项在《上线执行清单》里都有一整章教你怎么办。**本文只负责「代码怎么上去」。**
>
> **💡 注意：数据库是「自建」不是「买」的**
> 数据库就装在同一台服务器上（只监听 `127.0.0.1`），
> 所以**不需要单独买云数据库，也不需要配数据库安全组**。
> 详见 2.0 节。

### 1.2 登录服务器

**方式一：网页终端**（最简单）
腾讯云控制台 → 轻量应用服务器 → 点「登录」→ 「网页登录」

**方式二：本地终端**
```bash
ssh root@你的服务器公网IP
```

**方式三：图形化工具**（推荐，拖文件方便）
下载 [MobaXterm](https://mobaxterm.mobatek.net/) 或 [FinalShell](https://www.hessian.com/)，填 IP / root / 密码。

> **💡 原理：三种方式的区别在哪？**
> - **网页终端**：浏览器里直接连服务器，不用装任何软件。缺点是**不能拖文件**，
>   传文件还得用另外两种方式。
> - **本地终端（SSH）**：能敲命令，但传文件要用 `scp`（比较麻烦）。
> - **图形化工具（MobaXterm / FinalShell）**：**左侧是命令行、右侧是文件面板**，
>   可以直接拖文件。既能敲命令又能传文件 —— **新手最省事的一个**。
>
> 三种方式的共同点是**都走 SSH 协议**，所以加密、权限机制完全一样。

## 二、首次部署（一条命令流）

### 2.0 上传代码（先做这步）

```bash
# 在服务器上创建目录
mkdir -p /var/www/kuile
```

然后用 MobaXterm 的 SFTP 面板，把 `正式上线版` 整个文件夹拖到 `/var/www/kuile/`。

上传后目录应该是：
```
/var/www/kuile/正式上线版/
├── 01-文档/
├── 02-后端/
├── 03-小程序前端/
├── 04-部署脚本/
└── 05-上线执行清单/
```

> **💡 原理：为什么用 `/var/www/` 放网站文件？**
> 这是 Linux 的**惯例**。`/var` 放「运行时产生的数据」，
> `/var/www` 专门放「要对外提供服务的文件」。
> 好处是**和其他系统数据物理隔离** —— 重装系统、清理日志时不会误伤网站文件。
> 另外 `/etc`（配置）和 `/opt`（第三方程序）也是类似的分区思路。

### 2.1 准备自建数据库

> **💡 本项目的数据库是【自建 MySQL 8.0】，不是腾讯云托管数据库。**
> 数据库就装在这台服务器上，**不额外花钱**，也**不需要配数据库安全组**。
>
> **📋 为什么排在「上传代码」之后？**
> 建表（`npm run migrate`）要用到 `migrations/*.sql` 和 `mysql2` 依赖，都在代码里。
> 不过**下面这 7 步命令本身不依赖代码**，纯服务端操作。

```bash
# 1. 装 MySQL 服务器
sudo apt update
sudo apt install -y mysql-server mysql-client

# 2. 启动 + 开机自启
sudo systemctl enable --now mysql

# 3. 加固：只监听本机
sudo vi /etc/mysql/mysql.conf.d/mysqld.cnf
#   在 [mysqld] 段确认/添加：
#     bind-address = 127.0.0.1
#     default-time-zone = '+00:00'
#     innodb_buffer_pool_size = 1G

# 4. 重启生效
sudo systemctl restart mysql
sudo ss -tulpn | grep 3306     # 应该只看到 127.0.0.1:3306

# 5. 安全加固（删匿名用户、禁 root 远程）
sudo mysql_secure_installation

# 6. 建库建账号
sudo mysql <<'SQL'
CREATE DATABASE kuile CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'kuile'@'localhost' IDENTIFIED BY '你的密码';
GRANT ALL PRIVILEGES ON kuile.* TO 'kuile'@'localhost';
FLUSH PRIVILEGES;
SQL

# 7. 服务器时区也设成 UTC（和 MySQL 对齐）
sudo timedatectl set-timezone UTC
```

> **🔴 时区必须统一成 UTC**，否则「断卡判定」「结束日结算」的日期边界会算错一天。
> 详细原理见《上线执行清单》第 4 章「4.5 校准时区」。
>
> **💡 为什么 `bind-address = 127.0.0.1` 是最重要的一行？**
> 它让 MySQL **只接受本机连接** —— 别人从公网发来的请求在 TCP 层就被拒绝，
> 根本进不到 MySQL 的密码认证逻辑。
>
> 托管版要额外配「安全组只放行内网 IP」（新手最容易配错的地方），
> 自建版把安全边界收在**一个配置文件**里，反而更彻底。

### 2.2 一键部署

```bash
cd /var/www/kuile/正式上线版/04-部署脚本
vi deploy.sh
```

**改两处：**
```bash
REPO_URL=""            # 不用 Git 就留空
BRANCH="main"
```

> 用 Git 的话填上仓库地址，脚本会自动 clone/pull。
>
> **💡 目录对不上的话改这里**
> 脚本顶部有两个目录变量：
> ```bash
> REPO_DIR="/var/www/kuile"                  # 仓库根（git clone 的目标）
> APP_DIR="$REPO_DIR/正式上线版"              # 项目目录（里面有 02-后端 等）
> ```
> 如果你的代码不放在 `/var/www/kuile/正式上线版/`，就改 `APP_DIR`。
> 目录结构应该是：
> ```
> /var/www/kuile/正式上线版/
> ├── 01-文档/
> ├── 02-后端/        ← 后端代码在这
> ├── 03-小程序前端/
> ├── 04-部署脚本/    ← deploy.sh 在这
> └── 05-上线执行清单/
> ```

然后：

```bash
chmod +x deploy.sh
./deploy.sh
```

脚本会依次做这些事，每一步都有提示：
1. 检查 Node.js / PM2 / Nginx / MySQL
2. 拉取代码（`REPO_URL` 留空则跳过）
3. `npm ci --omit=dev`（装依赖）
4. 检查 `.env`（没有会停下来提醒你）
5. **检查数据库连通性**（连不上会提前退出，不跑到一半才挂）
6. 执行建表
7. PM2 启动服务 + 开机自启
8. 复制 Nginx 配置并重载
9. 健康检查

> **💡 原理：脚本里几个关键动作在干什么？**
> - `npm ci --omit=dev`：**按 `package-lock.json` 精确安装生产依赖**。
>   `npm ci` 保证每次装出来的版本完全一致（`npm install` 可能因为 `^` 版本号装到更新版），
>   `--omit=dev` 跳过开发依赖（测试框架之类），省空间、缩小攻击面。
> - `node scripts/migrate.js`：执行建表。**幂等** —— 重复跑不会出错。
> - `pm2 start src/server.js --name kuile-api`：让 PM2 启动后端并给它起个名字。
>   之后 `pm2 logs kuile-api`、`pm2 restart kuile-api` 就是靠这个名字找到它。
>
> **💡 顺序上有个小细节：`.env` 要在跑 `deploy.sh` 之前填好**
> 脚本第 4 步会检查 `.env` 存在，没有就直接停下并告诉你怎么建。
> 数据库那几行在 [2.1](#21-准备自建数据库) 的说明里有填法，
> 其余密钥填法见第三章「配置 .env」。

### 2.3 遇到问题

| 提示 | 怎么办 |
|---|---|
| `缺少 .env 文件` | `cd /var/www/kuile/正式上线版/02-后端 && cp .env.example .env && vi .env` 填好后重跑 |
| `数据库连接失败` | 检查 `.env` 的 `DB_HOST` 是不是 `127.0.0.1`；检查 `sudo systemctl status mysql` |
| `nginx -t` 报错 | 说明 `nginx-kuile.conf` 里的域名没改，或证书路径不对 |
| 健康检查失败 | `pm2 logs kuile-api --lines 50` 看日志 |

> **💡 原理：脚本为什么要「遇到错误就停」？**
> 部署脚本里都有 `set -e`：**任何一条命令失败就立刻退出**。
> 没有它的话，假设「建表失败」了，脚本还会继续往下跑「启动服务」，
> 最后你看到「部署成功」，但服务根本起不来 —— **错误被掩盖了**，
> 你会花半小时在一个已经失败的步骤上找原因。

## 三、配置 .env（最关键的一步）

```bash
cd /var/www/kuile/正式上线版/02-后端
cp .env.example .env
vi .env
```

### 逐项填写

```ini
# ── 服务 ──
NODE_ENV=production
PORT=3000
API_BASE_URL=https://api.你的域名

# ── 微信小程序 ──
WECHAT_APPID=wx1234567890abcdef
WECHAT_APPSECRET=32位密钥

# ── 数据库 ──
DB_HOST=127.0.0.1                       # 自建 MySQL，只监听本机
DB_PORT=3306
DB_NAME=kuile
DB_USER=kuile
DB_PASSWORD=数据库密码

# ── COS ──
COS_REGION=ap-guangzhou
COS_BUCKET=kuile-prod-1250000000
COS_SECRET_ID=AKIDxxxxx
COS_SECRET_KEY=xxxxx
COS_CDN_URL=https://kuile-prod-1250000000.cos.ap-guangzhou.myqcloud.com

# ── 豆包 AI ──
ARK_API_KEY=xxxxx
ARK_ENDPOINT_ID=ep-xxxxx
ARK_MODEL=doubao-1-5-vision-pro-250528
AI_VERIFY_ENABLED=false                # 先 false，测通了再改 true

# ── 🆕 押金总开关 ──
# false = 内测阶段暂不收取押金（本次上线就用这个）
# true  = 正式收押金，走微信支付全套流程
DEPOSIT_ENABLED=false

# ── 微信支付 ──
WECHAT_PAY_MCH_ID=1900000000
WECHAT_PAY_SERIAL_NO=证书序列号
WECHAT_PAY_PRIVATE_KEY_PATH=./certs/apiclient_key.pem
WECHAT_PAY_API_V3_KEY=32位APIv3密钥
WECHAT_PAY_NOTIFY_URL=https://api.你的域名/api/pay/notify

# ── 登录令牌 ──
JWT_SECRET=自己生成的64位随机串
TOKEN_EXPIRE_DAYS=30
```

> **💡 原理：`.env` 是什么？为什么要单独一个文件？**
> **代码和配置必须分离。**
> 代码是「要公开的」（进 Git、给同事看），配置是「你独有的秘密」（密钥、密码、你的服务器地址）。
> 如果密钥写死在代码里：① 代码一开源密钥就公开了；② 换服务器要改代码；③ 三个环境用不同密钥没法同时跑。
>
> **`.env` 就是「一个 KEY=VALUE 一行的纯文本配置表」**，程序启动时读它。
> 本项目**没有引入 dotenv 依赖**，而是在 `src/config.js` 里手写了 20 行解析 ——
> 少一个第三方包就少一份供应链风险。

> **💡 原理：`DEPOSIT_ENABLED` 这个开关的完整语义**
> | 值 | 界面 | 实际收钱 | 结算 |
> |---|---|---|---|
> | `false` | 押金档位照常显示、照常选 | **不收** | 不扣不退 |
> | `true` | 同上 | 收 | 按规则扣收/退款 |
>
> **为什么用开关而不是删代码？** 因为「改一行配置就能切回去」，
> 而且开关的两种路径都被测试覆盖（`tests/beta-deposit.test.js`）。
>
> **为什么结算不跟着开关走？** 因为结算**只认「实收金额」**。
> 内测局实收 0 → 扣 0、退 0；正式局实收 500 → 照常结算。
> 这样**无论开关什么时候翻转，都不会出现资损**。

### 生成随机密钥

```bash
# 生成 64 位随机串，填到 JWT_SECRET
openssl rand -hex 32
```

> **💡 原理：`JWT_SECRET` 是干嘛的？**
> 后端给用户签发登录 token 时，会用这个密钥做签名。
> 服务器每次收到请求都**用同一个密钥重算一遍签名**，
> 对得上才承认这个 token 有效。
>
> **签名 = 防伪**。没有它，任何人都能自己造一个 token 冒充别人。
>
> **为什么必须自己改掉默认值？**
> 因为默认值是写在代码里的，**全网公开**。谁都能用默认值造出合法 token。
> 代码里已经做了保护：`NODE_ENV=production` 时如果 `JWT_SECRET` 还是默认值，
> **服务直接拒绝启动**。这比「提示一下让你改」可靠得多。

### 设置文件权限（很重要）

```bash
chmod 600 .env
ls -l .env
# 应该显示 -rw------- 1 root root ... .env
```

> **💡 原理：`chmod 600` 是什么意思？**
> `chmod` = change mode（改权限）。`600` 表示：
> **属主（root）可读可写，其他人（组和其他用户）零权限**。
> 服务器上可能有多个运维账号、甚至有第三方运维工具在跑，
> 权限收紧能防止别人 `cat .env` 直接看到你的商户私钥。

### 商户私钥放文件

```bash
mkdir -p certs
# 用 MobaXterm 把 apiclient_key.pem 拖到 certs/ 目录
chmod 600 certs/apiclient_key.pem
```

> **💡 原理：为什么私钥要存成文件而不是写进 `.env`？**
> ① **`.env` 是一行一个 KEY=VALUE 的格式**，多行的私钥塞进去必然出问题。
> ② **权限可以单独管**（`chmod 600`），也能单独轮换。
> ③ **不会被日志误打** —— 私钥内容打进日志就是重大安全事故。

## 四、配置 HTTPS 证书

```bash
# 1. 放证书
mkdir -p /etc/nginx/ssl/kuile
# 用 MobaXterm 把 fullchain.pem 和 privkey.pem 拖到 /etc/nginx/ssl/kuile/

# 2. 改 Nginx 配置里的域名
vi /etc/nginx/conf.d/kuile.conf
# 把所有 yourdomain.com 替换成你的域名

# 3. 检查并重载
nginx -t
nginx -s reload
```

> **💡 原理：`fullchain.pem` 和 `privkey.pem` 为什么是两个文件？**
> - `privkey.pem`：**私钥** —— 解密会话密钥、给响应签名。**绝不外泄。**
> - `fullchain.pem`：**证书链** —— 你的证书 + 中间 CA + 根 CA。
>
> **为什么要「链」？** 证书不是自证的，是「上家担保下家」：
> 根 CA（浏览器内置信任）签了中间 CA，中间 CA 签了你的证书。
> 浏览器要顺着这条链一路验到根，才能确认你的证书是真的。
> 只给一张自己的证书，浏览器不知道该信谁，就报「证书无效」。
> `fullchain` 里的 `full` 就是「完整链条」的意思。

> **💡 原理：`nginx -t` 是什么？**
> **先测试再重载**。Nginx 的配置解析失败时默认不影响正在运行的服务，
> 但如果直接 reload 失败你就得进服务器改文件了。
> `-t` = test，只检查语法不实际加载。**改完 Nginx 配置永远先 `-t`。**

### 验证

```bash
# 本机
curl http://127.0.0.1:3000/api/health
# 公网
curl https://api.你的域名/api/health
```

两个都能返回 JSON 就说明通了。

> **💡 原理：为什么要做「本地 + 公网」两次健康检查？**
> 这是**分层定位故障**：
> - `127.0.0.1:3000` **通** → Node 后端和数据库都正常，问题在 **Nginx 或域名/证书**。
> - `127.0.0.1:3000` **不通** → 问题在 **Node 或数据库**，跟 Nginx 无关。
>
> 一次排查掉一半的可能，比盲目改配置快得多。

### 让 Nginx 开机自启

```bash
systemctl enable nginx
systemctl start nginx
```

> **💡 原理：`systemctl enable` 和 `start` 的区别？**
> - `enable` = **设置开机自启**（写进开机启动清单）
> - `start` = **现在立刻启动**
>
> 两个都要做。只 `enable` 的话，当前还没跑起来；只 `start` 的话，重启服务器就没了。

## 五、日常运维命令

### 查看运行状态

```bash
pm2 list                        # 看进程是否 online
pm2 logs kuile-api              # 看实时日志（Ctrl+C 退出）
pm2 logs kuile-api --lines 100  # 看最近 100 行
pm2 monit                       # 实时监控 CPU/内存
```

> **💡 原理：`pm2 list` 里看什么？**
> 最关键是 **status 列**：
> - `online` = 正常
> - `errored` = 启动失败，看 `pm2 logs`
> - `stopped` = 停了，`pm2 restart` 拉起来
>
> 还有一个容易忽略的列是 **restarts（重启次数）** ——
> 如果这个数字在涨，说明服务在**反复崩溃重启**。
> 这种情况下接口可能「时好时坏」，日志里能看到崩溃原因。
> **这是个很重要的健康信号，不要只看 online 就放心。**

### 重启 / 停止

```bash
pm2 restart kuile-api
pm2 stop kuile-api
pm2 delete kuile-api            # 彻底删除（下次要重新 start）
```

> **💡 原理：改了 `.env` 或代码后，什么时候需要 restart？**
> - 改了 `.env`（比如 `DEPOSIT_ENABLED`、`AI_VERIFY_ENABLED`）→ **必须 restart**
> - 改了代码 → **必须 restart**（Node 不会热更新，除非你配了 nodemon）
> - 改了 Nginx 配置 → 只需要 `nginx -s reload`（Nginx 支持热加载，**不用重启服务**）
>
> 这个区别能省掉不必要的服务中断。

### 更新代码（改完代码后）

```bash
cd /var/www/kuile/正式上线版/02-后端
git pull                        # 如果用 Git
npm install --omit=dev          # 有新依赖时
npm run migrate                 # 有新表结构时
pm2 restart kuile-api
```

> **💡 原理：`npm run migrate` 什么时候必须跑？**
> 只有**数据库表结构变了**才需要。比如新加了一个字段、加了一张表。
> 如果只是改了业务逻辑（改了个计算公式），**不用跑 migrate**。
>
> 因为 migrate 会真的改生产库的结构 —— 跑错脚本是有风险的。
> **判断标准很简单：改了 SQL 文件就要跑，没改就不要。**

### 开机自启确认

```bash
pm2 save
pm2 startup systemd -u root --hp /root
# 按提示执行它输出的那条命令
```

> **💡 原理：为什么「只做 startup 不做 save」等于没做？**
> `pm2 startup` 让 systemd 在开机时启动 PM2 **守护进程**，
> 而 PM2 守护进程启动后要读 `~/.pm2/dump.pm2` 这个存档才知道要拉起哪些服务。
> **`pm2 save` 就是生成这个存档。**
> 顺序不能反：**先 start 服务，再 save**。

### 数据库备份

**已配好自动备份**：`04-部署脚本/backup-db.sh` + crontab（每天凌晨 3:17）。

确认定时任务已生效：

```bash
crontab -l
# 应该能看到：
# 17 3 * * * /var/www/kuile/正式上线版/04-部署脚本/backup-db.sh >> /var/log/kuile-backup.log 2>&1
```

**手动跑一次：**

```bash
cd /var/www/kuile/正式上线版/04-部署脚本
./backup-db.sh
```

**手动备份（临时用）：**

```bash
mkdir -p /var/backups/kuile
mysqldump -h 127.0.0.1 -u kuile -p kuile kuile | gzip > /var/backups/kuile-$(date +%F).sql.gz
```

**恢复演练（重要，别跳过）：**

```bash
# 在临时库上恢复一次，确认能用
gunzip -c /var/backups/kuile-2026-11-27.sql.gz > /tmp/test.sql
mysql -u root -p -e "CREATE DATABASE kuile_restore_test;"
mysql -u root -p kuile_restore_test < /tmp/test.sql
mysql -u root -p kuile_restore_test -e "SHOW TABLES;" | wc -l   # 应该是 24
mysql -u root -p -e "DROP DATABASE kuile_restore_test;"
```

> **💡 原理：`mysqldump` 为什么能把数据导出成 .sql 文件？**
> 因为它**不是复制二进制文件**，而是**把数据翻译成一系列 SQL 语句**
> （`CREATE TABLE` + 一堆 `INSERT INTO`）。
>
> 这也解释了它为什么有两个缺点：
> - **慢**（数据量大时很慢，因为是一行行生成文本）
> - **不保证一致性**（导出期间如果有写入，导出的可能是「半个事务」的状态）
>   —— 用 `--single-transaction` 参数可以解决（`backup-db.sh` 已经加上了）
>
> 物理备份（直接复制数据文件）快且一致，托管版控制台的「自动备份」默认就是这一类。
> 但 `mysqldump` 胜在**可读、可跨版本、可以只导部分表** ——
> 所以它是「导出一份出来手动核对」的最佳工具。

> **💡 原理：为什么「没验证过的备份等于没有备份」？**
> 备份和恢复是**两套逻辑**：备份只管「把数据复制出去」，
> 恢复时才管「复制出来的东西能不能用」。
> 真实案例：某公司备份每天全绿，真出事时才发现备份文件是空的或缺数据。
> **必须定期拿备份恢复到一个临时实例上跑几个查询**。建议每季度演练一次。

### 磁盘监控

```bash
df -h                    # 看磁盘剩余
du -sh /var/www/kuile/*  # 看谁占空间
pm2 flush                # 清空 PM2 日志（释放空间）
```

> **💡 原理：磁盘满了会导致什么后果？**
> **MySQL 写不进去** —— 数据库依赖磁盘持久化。
> 磁盘满 → 写入报错 → 服务大面积 500。
> 这是「**一个资源耗尽导致全站故障**」的典型案例。
>
> **💡 哪样东西最容易吃满磁盘？**
> 一般是**日志**。PM2 写的日志不自动清理，跑几个月能到几个 GB。
> `pm2 flush` 立刻释放。要根治就装 `pm2-logrotate-daily`（按天切割 + 定期清理）。

## 六、监控与告警

### 简单方案：crontab 健康检查

```bash
crontab -e
```

加一行（每 5 分钟检查一次，失败发邮件）：
```bash
*/5 * * * * curl -sf http://127.0.0.1:3000/api/health > /dev/null || echo "亏了服务异常 $(date)" | mail -s "告警" you@email.com
```

> **💡 原理：`*/5 * * * *` 怎么读？**
> crontab 的格式是 `分 时 日 月 星期`，五个字段。
> `*/5 * * * *` = 「每 5 分钟执行一次后面的命令」，其余字段是通配（不限）。

> **💡 原理：为什么用 `curl -sf` 而不是 `curl`？**
> `-s` = silent（安静，不输出内容）、`-f` = fail（HTTP 出错时返回非 0 退出码）。
> 有了这两个参数，**服务返回 500 或连不上时 `curl` 的退出码就是非 0**，`||` 就会触发告警。
> 如果不加，curl 拿到 500 响应体照样退出 0，**告警永远不会触发** —— 这是个很常见的坑。

> **💡 原理：为什么要「自动告警」而不是「每天手动看」？**
> 因为故障发生的时间点，和你看监控的时间点，是**两个独立的随机变量**。
> 如果凌晨 3 点服务挂了、你在早上 9 点才看到 —— 那 6 小时的宕机，
> 用户已经经历了一切。**告警的意义是把「发现延迟」从小时级压到分钟级。**

### 进阶：接入腾讯云监控

在腾讯云控制台 →「云监控」→ 主机监控 → 创建告警：
- 指标：CPU 使用率 > 80% 持续 5 分钟
- 指标：内存使用率 > 85% 持续 5 分钟
- 通知渠道：微信 / 邮件 / 短信

> **💡 原理：为什么阈值要「持续 5 分钟」而不是「超过就报」？**
> 因为**瞬时尖峰是正常的** —— 用户集中打卡时 CPU 冲到 90% 一秒钟，然后又降下来。
> 如果不设持续时间，你会收到几十条「告警风暴」，**然后就开始无视告警了**。
>
> **告警最重要的属性不是「准确」，是「可信」** ——
> 一个月收到 5 条真告警，比一天收到 50 条误报有用得多。

## 七、常见部署问题排查

### 服务起不来

```bash
pm2 logs kuile-api --err --lines 50
```

按错误类型处理：

| 错误 | 原因 | 解决 |
|---|---|---|
| `ER_ACCESS_DENIED_ERROR` | 数据库密码错 | 核对 `.env` 的 `DB_PASSWORD`；`sudo mysql -u kuile -p` 试一下 |
| `ER_NOT_SUPPORTED_AUTH_MODE` | 账号认证插件太新 | `ALTER USER 'kuile'@'localhost' IDENTIFIED WITH mysql_native_password BY '你的密码';` |
| `ECONNREFUSED` | 数据库连不上 | `sudo systemctl status mysql`；`sudo ss -tulpn \| grep 3306`；核对 `DB_HOST=127.0.0.1` |
| `ER_BAD_DB_ERROR` | 库没建 | `sudo mysql -e "SHOW DATABASES;"` 确认有 `kuile` |
| `Missing required environment variable` | `.env` 少填了 | 按报错提示补 |
| `Port 3000 already in use` | 端口被占 | `lsof -i:3000` 看是谁 |

> **💡 原理：怎么读这些报错？**
> 这些都是 **MySQL 驱动（`mysql2`）的错误码**，不是 Node 的。看前缀就能定位：
> - `ER_` 开头 = MySQL 服务器返回的错误（权限、语法、找不到库、认证插件不兼容）
> - `ECONNREFUSED` = **网络层错误**，连都没连上（MySQL 没启动、端口没监听、地址写错）
> - `Port already in use` = Node 层的错误，端口被别的进程占了
>
> **💡 自建 MySQL 的排查顺序（和托管版不同）**
> 托管版出问题时数据库是别人家的，你只能查网络和密码。
> 自建版数据库就在你手边，**排查手段多得多**：
> ```bash
> sudo systemctl status mysql    # 服务起没起
> sudo ss -tulpn | grep 3306     # 监听到哪了
> sudo mysql -e "SHOW DATABASES;" # 库在不在
> tail -50 /var/log/mysql/error.log   # MySQL 自己的错误日志
> ```
> **代价是「你要自己负责」，回报是「出问题你有完整的手感」。**
>
> **分清「网络层」和「服务器层」能省很多时间**：
> `ECONNREFUSED` 说明请求根本没到 MySQL，去查网络和安全组；
> `ER_ACCESS_DENIED` 说明请求到了但被拒，去查密码和权限。

### 能访问但接口全 500

```bash
pm2 logs kuile-api | grep "未捕获异常"
```

> **💡 原理：为什么健康检查能返回 200，但业务接口全 500？**
> 因为健康检查只验证「服务活着 + 数据库连得上」，
> **不验证任何一个业务逻辑**。所以它挂不了 —— 这是它的设计目的（要极简可靠）。
>
> 业务接口 500 说明**某段业务代码抛异常了**。
> 这时「未捕获异常」日志里会有完整堆栈，看第一行通常就知道是哪个文件哪一行。

### 支付回调不通

```bash
# 1. 回调地址能访问吗
curl -X POST https://api.你的域名/api/pay/notify -d '{}' -H "Content-Type: application/json"
# 应该返回 FAIL（验签失败），不是超时或 404

# 2. 看日志
pm2 logs kuile-api | grep 微信支付
```

> **💡 原理：为什么「返回 FAIL」是好事？**
> 这个测试**故意发一个空报文**过去。
> - 返回 **FAIL / 验签失败** → 说明**你的服务器活着、能收到 POST、能跑验签逻辑** —— 链路是通的！
> - 返回 **超时** → 服务器没响应，可能是进程挂了或 Nginx 转发有问题
> - 返回 **404** → 路由没注册（路径写错了，或 Nginx 的 location 配错了）
>
> **所以「失败得正确」也是通过验证。** 这是一个典型的「负向测试」思路。

### 图片上传失败

```bash
pm2 logs kuile-api | grep COS
```

常见原因：
- COS 桶名写错
- SecretId/SecretKey 填错
- COS 地域填错（必须和服务器一致）
- 桶是私有读但没配「公有读」→ AI 读不到图

> **💡 原理：为什么「桶是私有读」会导致 AI 判定失败而不是上传失败？**
> 因为**上传**和**读取**是两条独立的链路：
> - 上传走的是**后端签名**（后端用密钥签一个临时授权给小程序）→ 私有桶完全没问题。
> - 但 **AI 判定时，是 AI 服务器自己去下载你的照片** —— 它没有你的密钥。
>
> 所以桶必须是**公有读**。如果配成私有读，你会看到一个很迷惑的现象：
> **上传成功、打卡提交成功，但 AI 判定老是失败或「无法识别」。**
> 排查方法：把照片 URL 贴到浏览器里，能打开就说明 AI 也能访问。

## 八、回滚

如果新版本有问题：

```bash
cd /var/www/kuile/正式上线版/02-后端
git log --oneline -5        # 找到上一个好的 commit
git checkout <commit>       # 切回去
npm install --omit=dev
pm2 restart kuile-api
```

**数据库回滚要谨慎** —— 生产库不要随便回滚结构。

> **💡 原理：为什么数据库不能随便回滚？**
> 代码可以切回旧版本，但如果新版本已经**往数据库写了新格式的数据**，
> 旧代码读不懂就会出错（或者更糟：旧代码误解新数据、写出错误结果）。
>
> 这就是为什么本项目的两个流水表（`credit_log`、`deposit_ledger`）
> **只追加、永不 UPDATE** —— 追加型的数据结构天然对回滚友好。
>
> **💡 更好的做法：灰度发布**
> 先让 5% 的用户跑新版本，观察无误再全量。
> 这样即使出问题，受影响的也只有 5% 的用户，而且**数据库里的新数据量很小**，
> 回退成本低。这是所有大流量产品的标准做法。
