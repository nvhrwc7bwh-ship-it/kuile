## 第 0 章：先看懂名词

这一章解释全文出现的所有词。看不懂随时回来查。

### 0.1 三个工具分别是什么

| 工具 | 它到底是什么 | 类比 |
|---|---|---|
| **Git** | 一个**记录文件版本**的软件。每次改动存成一张"快照"，随时能回到任意一张 | 游戏的存档系统 |
| **GitHub** | 一个**网上存代码的网站**。Git 把代码传上去，GitHub 负责保管和展示 | 公司的云端档案室 |
| **FinalShell** | 一个**远程操作服务器的图形界面工具**。左边敲命令，右边拖文件 | 服务器上的"遥控器" |

> **💡 FinalShell 到底能干什么？**
> 它是给你"远程遥控"腾讯云服务器的软件。左边那块黑色区域是**命令行**（打字敲命令），
> 右边是**文件面板**（像资源管理器一样，能看到服务器上的所有文件、可以拖拽）。
> 你第一次部署时上传代码，就是用右边的面板把整个文件夹拖上去的。

### 0.2 一句话解释整套流程

```
你的电脑  ──git push──▶  GitHub  ──git pull──▶  服务器  ──pm2 restart──▶  用户能用
 (改代码)              (存代码)               (取代码)                (重启服务)
```

**三个箭头就是你要记的全部内容。**

> **💡 为什么要绕 GitHub 这一圈？不能直接从电脑传到服务器吗？**
> 能，但有三个麻烦：
> 1. 传的是"当前这一刻的文件"，**服务器上到底跑的是哪个版本，没人说得清**
> 2. 传错了没法回退
> 3. 每次都要手动拖几十个文件
>
> 走 GitHub 的话，服务器上的代码**和 GitHub 上的一模一样**，
> 而且 Git 记着每一个历史版本，随时能退回去。这就是"版本管理"。

### 0.3 高频名词表

| 名词 | 解释 |
|---|---|
| **命令行 / 终端** | 用文字指令操作电脑的地方。FinalShell 左边那块黑的就是它 |
| **仓库（repository）** | 一个被 Git 管理的文件夹。里面多了一个隐藏的 `.git` 文件夹，用来存版本历史 |
| **提交（commit）** | 把当前改动存成一张"版本快照"，附带一句说明文字 |
| **推送（push）** | 把本地的提交上传到 GitHub |
| **拉取（pull）** | 从 GitHub 把最新内容下载到本地（服务器上执行的就是这个） |
| **分支（branch）** | 平行版本线。`main` 是主线，你日常用它就行 |
| **`.git`** | 一个隐藏文件夹，是"这个目录是 Git 仓库"的标志。里面存着全部版本历史 |
| **`.gitignore`** | 一个清单文件，告诉 Git"这些文件别管、别上传" |
| **`.env`** | 存密钥和密码的配置文件。**绝对不能上传到 GitHub** |
| **PM2** | 服务器上的"程序管家"。程序崩了自动重启，服务器重启也会自动拉起 |
| **Nginx** | 服务器的"门卫"。接收外部请求，再转发给内部的后端程序 |
| **Node.js** | 运行 JavaScript 后端程序的运行环境（类似给 Python 用的解释器） |
| **npm** | Node.js 的"应用商店"，用来安装依赖包 |
| **node_modules** | 装下来的依赖包所在目录。**体积巨大且不该上传 GitHub**，服务器上用 npm 命令重装 |
| **exec cwd** | PM2 显示的"工作目录" —— 也就是这个进程是在哪个文件夹里启动的 |
| **commit message** | 提交时写的说明，比如"修复打卡第2天报错" |
| **软链接（符号链接）** | 类似 Windows 的"快捷方式"。一个指到别处的指针 |

## 第 2 章：密钥保护（已经做好了）

### 2.1 现状

仓库根目录有一个 `.gitignore` 文件，内容是"黑名单"：

```gitignore
.env
*.key
*.pem
*.crt
*.p12
certs/
HTTPS 证书.zip
★*.txt
腾讯云子域名.txt
node_modules/
```

**含义：这些文件永远不会被上传到 GitHub。**

### 2.2 我已经核查过的结论

我对 GitHub 上的仓库**逐个文件检查过**（286 个文件）：

| 检查项 | 结果 |
|---|---|
| `.env`（含 AppSecret / 数据库密码 / COS 密钥 / JWT_SECRET） | ✅ **不在仓库里** |
| `HTTPS 证书.zip`（含 HTTPS 私钥） | ✅ **不在仓库里** |
| `★火山舟子账号密匙-亏了.txt` | ✅ **不在仓库里** |
| `★腾讯云子账号密匙-亏了.txt` | ✅ **不在仓库里** |
| `腾讯云子域名.txt` | ✅ **不在仓库里** |
| `node_modules/`（依赖包） | ✅ **不在仓库里** |
| `.env.example`（空模板，无真实值） | ✅ **在仓库里**（这是对的，新人要靠它知道填什么） |

**所以你不需要做任何补救操作，也不需要轮换密钥。**

### 2.3 为什么这件事这么重要

> **💡 两个层面的保护**
>
> **① 防止密钥泄露**
> 微信 AppSecret、数据库密码、支付私钥泄露出去 = 别人能冒充你登录小程序、
> 登进你的数据库、甚至动你的支付账户。**绝对不能进 GitHub。**
>
> **② 防止服务器配置被覆盖**（这个更隐蔽）
> `.env` 不在 Git 仓库里，意味着你每次 `git pull` **都不会把它冲掉**。
> 如果它在里面，你每次推送前都得手动改一遍服务器上的配置 —— 迟早会忘。

## 第 3 章：本机日常操作

> 什么时候用这一章：**你在电脑上改了代码之后**。

### 3.1 完整的四步

```powershell
cd "e:\9.小程序自己做\02-立了"
git add .
git commit -m "修复：打卡第2天不再报「这一天不存在」"
git push
```

### 3.2 逐条拆解

#### 第一步：进入项目目录

```powershell
cd "e:\9.小程序自己做\02-立了"
```

**在干什么**
`cd` = change directory（切换目录）。这行把你移到项目文件夹。

**为什么需要它**
Git 命令要在项目里执行，它靠当前目录往上找 `.git` 来确认"这是哪个仓库"。

**成功标志**
没有输出，直接回到 `PS E:\9.小程序自己做\02-立了>` 提示符。

**如果出错**
`cd : 找不到路径` → 检查路径有没有打错，特别是中文和数字。

---

#### 第二步：把改动放进暂存区

```powershell
git add .
```

**在干什么**
`add` = 加入。`.` 代表"当前目录下的所有东西"。
Git 里有个叫**暂存区**的东西，可以理解成**购物车** —— 你先把想提交的东西放进购物车，
确认无误后再结账（commit）。

**为什么分两步，不一步到位？**
因为 `add` 之后可以先看看购物车里有没有不该买的东西，发现问题还能拿出来。
**这是最后一道安全闸门。**

**成功标志**
没有输出。

**如果出错**
`fatal: pathspec '.' did not match any files` → 你不在项目目录里，回到第一步。

---

#### 第三步：提交（存一张快照）

```powershell
git commit -m "修复：打卡第2天不再报「这一天不存在」"
```

**在干什么**
把暂存区里的内容存成一个版本快照。`-m` 后面那句是**说明文字**。

**为什么说明文字很重要**
三个月后你回头看历史，全靠这句话知道当时改了什么。
写 `fix` 等于没写。

**成功标志**
看到类似这样的输出：

```
[main 43407ba] 修复：打卡第2天不再报「这一天不存在」
 3 files changed, 15 insertions(+), 2 deletions(-)
```

**如果出错**

| 报错 | 原因 | 怎么办 |
|---|---|---|
| `nothing to commit, working tree clean` | 没东西可提交（没改文件） | 正常，跳过 |
| `Please tell me who you are` | 没配身份 | 见下方 3.3 |

---

#### 第四步：推送到 GitHub

```powershell
git push
```

**在干什么**
把本地的提交上传到 GitHub。

**为什么不用写完整参数**
因为第一次推送时用了 `git push -u origin main`，`-u` 建立了"追踪关系"：
Git 记住了"这个仓库的默认远程叫 origin，默认分支叫 main"。
所以以后只写 `git push` 就行。

**成功标志**
看到：

```
To https://github.com/nvhrwc7bwh-ship-it/kuile.git
   43407ba..abcdef1  main -> main
```

> **💡 顺便解释你之前问的「为什么没问账号密码」**
> 跟公共库私有库**没关系** —— 两种都要认证。
> 真正原因是 **Git Credential Manager（凭据管理器）已经存了你的凭据**。
> 它的机制是：第一次推送弹窗问账号密码 → 加密后存进 Windows 凭据管理器 → 之后自动读取。
> 你以前推送那个初始提交时就存好了。

**如果出错**

| 报错 | 原因 | 怎么办 |
|---|---|---|
| `rejected: fetch first` | 远程有你本地没有的提交 | 先 `git pull`，再 `git push` |
| `Permission denied` | 凭据失效 | 见 7.4 节 |
| `fatal: could not read Username` | 没存凭据 | 见 7.4 节 |

### 3.3 如果出现「Please tell me who you are」

```powershell
git config --global user.name "kuile"
git config --global user.email "598615940@qq.com"
```

**在干什么**
告诉 Git "提交的人是谁"。这个信息会写进每一次提交记录。

**`--global` 是什么意思**
"全局" = 对你电脑上**所有** Git 仓库生效。不加就只对当前这个仓库生效。

**成功标志**
没有输出。

---

### 3.4 想知道改了哪些文件

```powershell
git status
```

**在干什么**
列出当前所有改动：哪些是新文件、哪些改了、哪些待提交。

**怎么读输出**

| 看到 | 含义 |
|---|---|
| `Changes to be committed` | 已放进购物车，待提交 |
| `Changes not staged for commit` | 改了但还没 `git add` |
| `Untracked files` | 新文件，还没 `git add` |
| `nothing to commit, working tree clean` | 一切就绪，没有待处理的改动 |

## 第 4 章：服务器环境确认

> 什么时候用这一章：**不确定服务器状态时**，或者换服务器后。

### 4.1 连上服务器

打开 FinalShell → 左侧会话列表双击你的服务器连接。

**成功标志**
左边黑色区域出现这样的提示符：

```
ubuntu@VM-0-6-ubuntu:~$
```

> **💡 提示符怎么读**
> `ubuntu` = 当前用户，`VM-0-6-ubuntu` = 主机名，`~` = 当前目录（`~` 是你的家目录 `/home/ubuntu`），
> `$` = "你是普通用户"（如果是 `#` 开头说明是 root 管理员）。

---

### 4.2 确认代码目录

```bash
cd /var/www/kuile/kuile
ls -la
```

**在干什么**
- `cd`：切换到仓库根目录
- `ls -la`：列出内容。`-l` 显示详细信息，`-a` 显示**隐藏文件**（`.git` 是隐藏的，不加 `-a` 看不到）

**成功标志**
输出里有这两项：

```
drwxrwxr-x  8 ubuntu ubuntu 4096 Nov 27 12:48 .git
drwxr-xr-x  7 ubuntu ubuntu 4096 Nov 27 12:48 正式上线版
```

**如果出错**
`ls: cannot access '.git'` → 走错层了。用这条找正确的位置：

```bash
find /var/www/kuile -name ".git" -type d 2>/dev/null
```

> **💡 这条命令怎么读**
> `find` 查找文件，`/var/www/kuile` 从这开始找，
> `-name ".git"` 只找名叫 .git 的，`-type d` 只找目录（d = directory），
> `2>/dev/null` 把权限不足的报错丢掉（否则会刷一堆 Permission denied 把结果淹掉）。

---

### 4.3 确认 PM2 在跑哪个目录

```bash
pm2 describe kuile-api | grep -E "script path|exec cwd"
```

**在干什么**
- `pm2 describe kuile-api`：显示这个进程的详细配置
- `grep -E "script path|exec cwd"`：只保留包含这两个关键词的行（`-E` 让 `|` 表示"或"）

**你机器上的正确输出**

```
│ script path       │ /var/www/kuile/kuile/正式上线版/02-后端/src/server.js │
│ exec cwd          │ /var/www/kuile/kuile/正式上线版/02-后端               │
```

**这行输出为什么重要**
它告诉你**后端进程实际在哪个文件夹跑**。
如果以后你改了目录，这里指向的路径会变 —— 那时候服务就起不来了。

---

### 4.4 确认配置生效

```bash
curl -m 5 -s http://127.0.0.1:3000/api/health; echo ""
```

**在干什么**
- `curl` = 用命令行访问网址
- `127.0.0.1` = 本机自己（`localhost`）
- `:3000` = 后端监听的端口
- `-m 5` = 最多等 5 秒（**很重要**，否则服务挂了会一直卡住）
- `-s` = 安静模式，不显示进度条
- `; echo ""` = 末尾补一个换行，让输出好看

**为什么用本机地址而不是你的域名**
故意绕开 Nginx 和证书，单独测后端本身。这样能"分层定位"问题：

| 结果 | 说明 | 下一步 |
|---|---|---|
| 有 JSON 返回 | Node + MySQL 都正常 | 问题在 Nginx/域名/证书 |
| 没返回/超时 | 问题在 Node 或数据库 | 跟 Nginx 无关，看日志 |

**正确输出**

```json
{"code":0,"data":{"service":"kuile-api","db":true,"env":"production","depositEnabled":false}}
```

**两个关键字段的判读**

| 字段 | 期望值 | 不对说明什么 |
|---|---|---|
| `db` | `true` | MySQL 没连上 → `sudo systemctl start mysql` |
| `env` | `production` | `.env` 没被读到 → 配置文件位置错了 |

> **💡 为什么 `env` 字段能当判据？**
> 这是**黑盒验证** —— 不看文件，直接问服务"你实际用的什么配置"。
> `config.js` 的逻辑是：先读 `.env`，读不到就用默认值 `development`。
> 所以它返回什么，就等于**实际**在用什么。

## 第 6 章：建一个一键更新脚本

> 做一次，以后每次更新只敲一行。

### 6.1 创建脚本

```bash
cat > /var/www/kuile/kuile/update.sh << 'EOF'
#!/bin/bash
set -e
cd /var/www/kuile/kuile
echo "▶ 拉取代码"
git pull
cd 正式上线版/02-后端
echo "▶ 装依赖"
npm install --omit=dev
echo "▶ 重启服务"
pm2 restart kuile-api
sleep 3
echo "▶ 健康检查"
curl -m 5 -sf http://127.0.0.1:3000/api/health && echo "" && echo "✅ 更新完成" || echo "❌ 更新失败，看日志：pm2 logs kuile-api --lines 50"
EOF
```

**这行命令在干什么**
`cat > 文件名 << 'EOF'` 是"把后面所有内容原样写进这个文件"。
结尾的 `EOF` 是结束标记 —— 写完那行 `EOF` 后，shell 才知道内容到此为止。

> **💡 为什么 `EOF` 要用单引号包住？**
> `'EOF'`（带引号）表示"内容里的 `$` 不展开"。
> 脚本里有 `$(...)` 这种写法，如果不加引号，shell 会在**创建脚本的时候**就把它执行掉，
> 写进文件的就成了执行结果而不是命令本身。

**`set -e` 是什么**
"任何一条命令失败就立刻停下"。

> **💡 为什么必须有它？**
> 没有它，假设"装依赖"失败了，脚本还会继续去重启服务，
> 最后你看到"✅ 更新完成"，但服务根本没起来 —— **错误被掩盖了**，
> 你会花半小时在一个已经失败的步骤上找原因。

**`&&` 和 `||` 是什么**
- `&&` = "前面成功才执行后面"
- `||` = "前面失败才执行后面"

脚本最后那行就是：健康检查成功 → 打印"✅ 更新完成"；失败 → 打印"❌"和排查命令。

**成功标志**
没有输出，直接回到提示符。

---

### 6.2 赋予执行权限

```bash

```

**在干什么**
`chmod` = change mode（改权限）。`+x` = 加上"可执行"。

> **💡 为什么必须加？**
> Linux 里文件默认**没有**执行权限。不加这行，直接跑会报 `Permission denied`。

**验证**

```bash

```

**成功标志**
第一列是 `-rwxr-xr-x` —— 第二个字符是 `x` 就对了。

### 7.3 `git pull` 冲突

```
error: Your local changes to the following files would be overwritten by merge:
```

**原因**：服务器上有人直接改了代码（用 FinalShell 拖文件改的），和 GitHub 上的版本冲突了。

**先看服务器上改了什么**

```bash
cd /var/www/kuile/kuile
git status
```

**如果那些改动不重要**（比如只是调试时临时改的），丢掉它们：

```bash
git checkout -- .
git pull
```

> **⚠️ 这会永久删除服务器上的手工修改。**
> 不确定要不要保留，**先备份**：
> ```bash
> cp -r /var/www/kuile/kuile/正式上线版 /var/www/kuile-手工修改备份
> ```

> **💡 正确的做法**
> 服务器上的代码**不应该手工改**。要改就在电脑上改，走 `git push` → `git pull`。
> 这样服务器上的代码永远和 GitHub 一致，出问题能追溯。

### 7.4 凭据问题

**现象**：`fatal: could not read Username` 或 `Permission denied (publickey)`

**先看远程地址对不对**

```bash
cd /var/www/kuile/kuile
git remote -v
```

**应该显示**

```
origin  https://github.com/nvhrwc7bwh-ship-it/kuile.git (fetch)
origin  https://github.com/nvhrwc7bwh-ship-it/kuile.git (push)
```

**如果地址不对**，改回来：

```bash
git remote set-url origin https://github.com/nvhrwc7bwh-ship-it/kuile.git
```

**如果地址对但认证失败** —— 说明 GitHub 那边换了密码或 Token 失效了。
在服务器上重新生成一把部署密钥（推荐，比用密码安全）：

```bash
ssh-keygen -t ed25519 -C "kuile-server"
cat ~/.ssh/id_ed25519.pub
```

把输出的内容复制到 GitHub → Settings → SSH and GPG keys → New SSH key。

然后把服务器的远程地址改成 SSH 形式：

```bash
git remote set-url origin git@github.com:nvhrwc7bwh-ship-it/kuile.git
```

**测试**：

```bash
ssh -T git@github.com
```

看到 `Hi nvhrwc7bwh-ship-it! You've successfully authenticated` 就成功了。

### 7.5 网络中断（传输到一半断掉）

**现象**（本次实际遇到）：

```
error: RPC failed; curl 92 HTTP/2 stream 0 was not closed cleanly: CANCEL (err 8)
error: 8226 bytes of body are still expected
fatal: early EOF
```

或者：

```
error: RPC failed; curl 56 GnuTLS recv error (-9): Error decoding the received TLS packet.
```

电脑上也可能报：

```
fatal: unable to access '...': Recv failure: Connection was reset
```

**怎么读这些报错**

| 这句 | 意思 |
|---|---|
| `Enumerating objects: 347, done` | ✅ GitHub 侧准备好了 |
| `Compressing objects: 100%` | ✅ 压缩完成，开始传 |
| `stream 0 was not closed cleanly` | ❌ **传输中途连接被掐断** |
| `early EOF` | 文件没读完，对端就断了 |

**这不是代码或仓库的问题，是网络问题。**

#### 方案 A：强制 HTTP/1.1（**最有效，实测解决**）

```bash
git config --global http.version HTTP/1.1
git config --global http.postBuffer 524288000
git pull
```

> **💡 为什么这招管用**
> 报错里明确写了 `HTTP/2 stream`。HTTP/2 在不稳定链路上更容易被中间设备（运营商 QoS、防火墙）掐断。
> 换成 HTTP/1.1 后，同样的 push 立刻成功了。
>
> **服务器和你的电脑都要设这一条** —— 两边都可能遇到。

#### 方案 B：关掉压缩

```bash
git config --global core.compression 0
git pull
```

#### 方案 C：只拉最新一个快照（传输量最小）

```bash
cd /var/www/kuile/kuile
git fetch --depth=1 origin main
git reset --hard FETCH_HEAD
```

> **💡 `--depth=1` 的意义**
> 只下载**一个提交**的快照，不要完整历史。
> 你要的是"代码更新到最新版"，历史在 GitHub 上有完整一份，服务器上不需要。

#### 方案 D：改用 SSH 通道

```bash
git remote set-url origin git@github.com:nvhrwc7bwh-ship-it/kuile.git
```

SSH 走 22 端口，和 HTTPS 的 443 是不同通道，干扰常常只针对其中一个。

#### 判断是小请求通还是大传输断

```bash
curl -I https://github.com --max-time 10
```

| 结果 | 说明 |
|---|---|
| 返回 `HTTP/1.1 200 OK` | 小请求通，问题在大流量传输 → 用方案 A |
| 超时或失败 | 网络整体不通 → 检查代理 |

#### 顺带一提：仓库瘦身能根治这个问题

本次把 `素材/`（53 MB PNG）从 Git 管理中移除后，仓库从 **60 MB 降到 260 KB**。
传输量差 200 倍，**中断概率几乎归零**。

> **💡 经验**
> 仓库超过 20 MB 就该考虑瘦身。图片、素材、构建产物这类
> 「服务器不需要、但会被反复提交」的东西，最容易拖垮更新流程。

### 7.6 服务起不来

```bash
pm2 logs kuile-api --err --lines 50
```

按错误类型处理：

| 错误 | 原因 | 解决 |
|---|---|---|
| `ER_ACCESS_DENIED_ERROR` | 数据库密码错 | 核对 `.env` 的 `DB_PASSWORD` |
| `ECONNREFUSED` | 数据库连不上 | `sudo systemctl status mysql` |
| `ER_BAD_DB_ERROR` | 库没建 | `sudo mysql -e "SHOW DATABASES;"` |
| `Missing required environment variable` | `.env` 少填了 | 检查 `.env` |
| `Script not found` | 目录变了 | `pm2 describe kuile-api \| grep "script path"` 看实际路径 |

### 7.7 数据库相关的错误对照

| 报错关键字 | 属于哪一层 | 排查方向 |
|---|---|---|
| `ECONNREFUSED` | 网络层（连都没连上） | MySQL 没启动、端口没监听、地址写错 |
| `ER_ACCESS_DENIED` | 服务器层（连上了但被拒） | 密码错、账号没授权 |
| `ER_BAD_DB_ERROR` | 服务器层 | 数据库 `kuile` 不存在 |
| `Unknown column` | 代码层 | **代码 bug**，不是配置问题 |

> **💡 分清「网络层」和「服务器层」能省很多时间**
> `ECONNREFUSED` 说明请求根本没到 MySQL，去查服务和端口。
> `ER_ACCESS_DENIED` 说明请求到了但被拒，去查密码和权限。

## 第 9 章：待技术人员后续处理

以下是本次不处理、但需要技术人员接手的事项。按风险从高到低排列。

### 9.1 数据库自动备份从未配置（**高风险**）

**现状**：`crontab -l` 返回 `no crontab for ubuntu` —— **一个定时任务都没配**。

**影响**：每天凌晨的自动备份**从未生效**。数据库一旦损坏或误删，**没有任何退路**。

**需要做的**

```bash
crontab -e
```

加入（注意路径是双层）：

```
17 3 * * * /bin/bash /var/www/kuile/kuile/正式上线版/04-部署脚本/backup-db.sh >> /var/log/kuile-backup.log 2>&1
```

然后 `crontab -l` 确认写入，并**手动跑一次验证**。

**另外**：脚本里的 COS 上传（异地备份）需要 `pip3 install coscmd` 并填 `COS_BUCKET` / `COS_SECRET_ID` / `COS_SECRET_KEY`，
目前是"只在本机备份，不够安全"的状态。

> **💡 还要做一次恢复演练**
> 在临时数据库上恢复一次，确认备份文件真的能用。
> **"没验证过的备份等于没有备份"** —— 这是行业里反复出过事的教训。

### 9.2 `.env` 里的域名还是模板值（**高风险**）

**现状**

```
API_BASE_URL=https://api.yourdomain.com
WECHAT_PAY_NOTIFY_URL=https://api.yourdomain.com/api/pay/notify
```

**真实域名应该是** `https://kuile.banshengcomp.com`

**影响**：微信支付回调会发到错误域名，**支付永远收不到通知**。
（目前 `DEPOSIT_ENABLED=false` 是内测免押金模式，所以暂时不影响。）

**改法**

```bash
cd /var/www/kuile/kuile/正式上线版/02-后端
vi .env
```

改完必须重启：

```bash
pm2 restart kuile-api
```

### 9.3 GitHub 仓库是公开的（中风险）

**现状**：`nvhrwc7bwh-ship-it/kuile` 是 Public。

**核查结论**：内容里**没有任何密钥**（我逐个文件检查过 286 个文件）。

**但仍建议改私有**，因为公开意味着任何人能 clone 你的代码，看到全部业务逻辑和规则参数。

**改法**：GitHub 仓库页 → `Settings` → 拉到底 `Danger Zone` → `Change visibility` → `Change to private`

### 9.4 目录是双层结构（低风险）

**现状**：`/var/www/kuile/kuile/正式上线版/`

**不影响运行**。PM2 跑的是内层那份，`deploy.sh` 已改成自动探测路径（以后不用管）。

**如果一定要整理成单层**，必须**同时**改这四处，漏一个就出事：

| 要改的地方 | 怎么改 |
|---|---|
| PM2 进程指向 | `pm2 delete kuile-api` → 用新路径 `pm2 start` → `pm2 save` |
| crontab 备份路径 | `crontab -e` 改路径 |
| `.env` 位置 | 移到新的 `02-后端/` 下 |
| `node_modules` | `npm install --omit=dev` 重装 |

**⚠️ 建议：稳定运行一两个月后再考虑。现在动它收益极小、风险不小。**

### 9.5 服务器还没做的一次性设置

服务器上还没设过 HTTP/1.1，**第一次拉取前必须设**，否则会遇到传输中断：

> **💡 为什么必须设**

> 仓库瘦身后只有 260 KB，风险已经很低，但设上更保险。
