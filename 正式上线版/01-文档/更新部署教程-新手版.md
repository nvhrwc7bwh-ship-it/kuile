## 第 0 章：先看懂名词

这一章解释本文出现的所有词。看不懂的地方随时回来查。

### 0.1 三个工具分别是什么

| 工具 | 它到底是什么 | 类比 |
|---|---|---|
| **Git** | 一个**记录文件版本**的软件。每个改动都会存成一张"快照"，随时能回到任意一个快照 | 游戏的存档系统 |
| **GitHub** | 一个**网上存代码的网站**。Git 把代码传上去，GitHub 负责保管和展示 | 公司的云端档案室 |
| **FinalShell** | 一个**远程操作服务器的图形界面工具**。左边敲命令，右边拖文件 | 腾讯云服务器上的"遥控器" |

> **💡 为什么你现在装了 Git 却还用不了？**
> Git 装在了 `D:\1、Software\Git\`，但**Cursor 的终端是安装之前就开着的**，
> 它还没刷新过"系统有哪些软件"的清单。
> **关掉 Cursor 的终端标签页重新开一个**，或者直接重启 Cursor，Git 就能用了。
> 我在下面教程里也会给一条"不重启也能用"的办法。

### 0.2 一句话解释整套流程

```
你的电脑  ──git push──▶  GitHub  ──git pull──▶  服务器  ──pm2 restart──▶  用户能用
 (改代码)              (存代码)               (取代码)                (重启服务)
```

**三个箭头就是你要记的全部内容。**

> **💡 为什么要绕 GitHub 这一圈？不能直接从电脑传到服务器吗？**
> 能，但有三个麻烦：
> 1. 传的是"当前这一刻的文件"，**服务器上到底跑的是哪个版本，没人说得清**
> 2. 传错了没法回退
> 3. 每次都要手动拖
>
> 走 GitHub 的话，服务器上的代码**和 GitHub 上的一模一样**，
> 而且 Git 记着每一个历史版本，随时能退回去。这就是所谓的"版本管理"。

### 0.3 其他高频名词

| 名词 | 解释 |
|---|---|
| **命令行 / 终端** | 用文字指令操作电脑的地方。FinalShell 左边那块黑的就是它 |
| **仓库（repository）** | 一个被 Git 管理的文件夹。里面多了一个隐藏的 `.git` 文件夹，用来存版本历史 |
| **提交（commit）** | 把当前改动存成一个"版本快照"，附带一句说明文字 |
| **推送（push）** | 把本地的提交上传到 GitHub |
| **拉取（pull）** | 从 GitHub 把最新内容下载到本地（服务器上执行的就是这个） |
| **分支（branch）** | 平行版本线。`main` 是主线，你日常用它就行 |
| **`.gitignore`** | 一个告诉 Git"这些文件别管、别上传"的清单文件 |
| **`.env`** | 存密钥和密码的配置文件。**绝对不能上传到 GitHub** |
| **PM2** | 服务器上的"程序管家"。程序崩了自动重启，服务器重启也会自动拉起 |
| **Nginx** | 服务器的"门卫"。负责接收外部请求，再转发给内部的后端程序 |
| **Node.js** | 运行 JavaScript 后端程序的运行环境（类似给 Python 用的解释器） |
| **npm** | Node.js 的"应用商店"，用来安装依赖包 |
| **node_modules** | 装下来的依赖包所在目录。**体积巨大且不该上传 GitHub**，服务器上用 npm 命令重新装 |
| **FinalShell** | 见 0.1 |
| **commit message** | 提交时写的说明，比如"修复打卡第2天报错" |

## 第 2 章：最重要的一步：防止密钥泄露

### 2.1 概念：Git 怎么决定收不收一个文件

Git 有一套规则叫 `.gitignore`，里面是一行行"黑名单"。
Git 在收集文件时，会问：**这个文件名在黑名单上吗？** 在就跳过。

> **⚠️ 这里有个关键误解要纠正**
> 你把 `.env` 从 `正式上线版/` 移到仓库根目录了 —— 这**只改变了位置，没改变保护**。
> `.gitignore` 是**按目录层级生效**的：`02-后端/.gitignore` 只管 `02-后端/` 里面的东西，
> 管不到上一层的 `正式上线版/.env`，更管不到根目录。
>
> **你还需要在仓库根目录新建一个 `.gitignore`** —— 那个才能管住整个仓库。

### 2.2 步骤一：新建根目录 `.gitignore`

在 `e:\9.小程序自己做\02-立了\` 目录下新建一个**名叫 `.gitignore`** 的文件。

> **💡 怎么新建这种"没有扩展名"的文件？**
> 1. 在资源管理器里右键 → 新建 → 文本文档
> 2. 名字改成 `.gitignore`（**注意前面有个点，末尾没有 `.txt`**）
> 3. 如果 Windows 弹出"要不要改扩展名"，选**是**
> 4. 如果它变成了 `.gitignore.txt`，用资源管理器 → 查看 → 显示 → 勾选"文件扩展名"，然后改名

**内容（整段复制进去）：**

```gitignore
# ---- 密钥与密码文件（最重要，绝不能上传）----
.env
.env.local
*.env
!.env.example

# ---- 证书与私钥 ----
*.key
*.pem
*.crt
*.p12
*.cer
certs/
HTTPS 证书.zip

# ---- 云账号密钥（文件名开头是 ★）----
★*.txt
腾讯云子域名.txt

# ---- 依赖包（体积巨大，服务器上用 npm 重装）----
node_modules/

# ---- 日志 ----
logs/
*.log

# ---- 系统与编辑器临时文件 ----
.DS_Store
Thumbs.db
.idea/
.vscode/
*.swp
```

**逐行解释：**

| 这行 | 作用 |
|---|---|
| `.env` | 忽略所有名为 `.env` 的文件 |
| `*.env` | 忽略所有以 `.env` 结尾的（比如 `prod.env`） |
| `!.env.example` | **例外规则**：把 `.env.example` 捞回来。它是"空模板"，让人知道该填什么，没有秘密，**应该上传** |
| `*.key` `*.pem` `*.crt` | 忽略所有证书和私钥文件 |
| `HTTPS 证书.zip` | 忽略这个压缩包 |
| `★*.txt` | 忽略所有以 `★` 开头的 txt（你的两个密匙文件） |
| `node_modules/` | 忽略依赖包目录（结尾的 `/` 表示"整个目录"） |

> **💡 为什么要写 `!.env.example`？**
> 因为 `*.env` 那行会把 `.env.example` 也排除掉（它的名字以 `.env` 开头）。
> 但 `.env.example` 是**模板**，是给别人填配置用的，必须在仓库里。
> `!` 读作"**不**（except）"，是 gitignore 里的"例外"写法。
> **顺序很重要**：例外规则要写在后面才生效。

### 2.3 步骤二：把敏感文件挪出仓库目录

光有 `.gitignore` 还不够 —— 万一以后手滑用了强制添加，规则就被绕过了。
**双保险：物理上把文件挪到仓库外面。**

在仓库外面建个文件夹，比如 `E:\亏了-私密文件\`，把下面四个文件挪进去：

- `.env`
- `HTTPS 证书.zip`
- `★火山舟子账号密匙-亏了.txt`
- `★腾讯云子账号密匙-亏了.txt`
- `腾讯云子域名.txt`

> **💡 但服务器上的 `.env` 怎么办？**
> **服务器上的那份不用动。** 服务器是另一台机器，
> 上面已经有你之前 clone 下来的代码和你配置好的 `.env`。
> 本地挪走只影响本地，不影响服务器。
>
> **⚠️ 唯一要注意的**：服务器上的 `.env` **必须放在 `正式上线版/02-后端/` 里**，
> 因为后端代码是按这个路径找它的：
> ```javascript
> // src/config.js 第 12 行
> const envPath = path.resolve(__dirname, '../.env');
> ```
> 稍后第 4 章会验证服务器上这个文件在不在正确位置。

## 第 3 章：让本地变成 Git 仓库并推上 GitHub

### 3.1 先让终端认得 Git

**情况**：Git 装好了，但当前终端还认不出它。

**办法 A（推荐，最省事）**：关掉 Cursor 底部的终端标签页，重新开一个。
如果还不行，**完全退出 Cursor 再打开**（不是关窗口，是退出程序）。

**办法 B（不重启的办法）**：直接用完整路径调用 Git。
下面所有命令我都写成完整路径，你可以照抄。

> 为了让教程好读，下文用 `git` 这个简写。
> 如果 `git` 认不出，就在前面加上完整路径：
> ```powershell
> $git = "D:\1、Software\Git\cmd\git.exe"
> ```
> 然后把 `git xxx` 改成 `& $git xxx`

### 3.2 步骤一：设置你的身份

Git 会给每次提交记录"是谁提交的"。第一次要先告诉它。

```powershell
cd "e:\9.小程序自己做\02-立了"
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

> **💡 `--global` 是什么意思？**
> "全局"= 对你电脑上的**所有** Git 仓库都生效。
> 不加 `--global` 就只对当前这个仓库生效。
> 这里用全局，因为你以后可能不止这一个项目。

### 3.3 步骤二：初始化仓库

```powershell
git init
```

> **💡 这行命令做了什么？**
> 在 `e:\9.小程序自己做\02-立了\` 里创建一个隐藏的 `.git` 文件夹。
> 这个文件夹里存着**所有版本历史**。
> 从这一刻起，Git 开始"盯着"这个目录里的所有文件。

**成功标志**：
```
Initialized empty Git repository in E:/9.小程序自己做/02-立了/.git/
```

### 3.4 步骤三：把文件加入暂存区

```powershell
git add .
```

> **💡 `git add .` 是什么意思？**
> `.` 代表"当前目录下的所有东西"。
> `add` 是"加入暂存区" —— 暂存区可以理解成一个**购物车**：
> 你把想提交的东西先放进购物车，确认无误后再结账（commit）。
>
> **为什么不是一步 commit？**
> 因为 `git add .` 之后你可以用 `git status` 检查购物车里有没有不该买的东西，
> 发现问题还能 `git rm --cached` 拿出来。**这一步就是最后一道安全闸门。**

### 3.5 步骤四：🔴 关键检查

```powershell
git status
```

**这一步千万别跳过。** 它会列出所有待提交的文件。

**你要逐条确认列表里【没有】这些：**

| 不该出现的 | 长什么样 |
|---|---|
| `.env` | `.env` |
| `正式上线版/02-后端/.env` | 完整路径 |
| `HTTPS 证书.zip` | `HTTPS 证书.zip` |
| `★火山舟子账号密匙-亏了.txt` | 带 ★ 的文件名 |
| `★腾讯云子账号密匙-亏了.txt` | 带 ★ 的文件名 |
| `腾讯云子域名.txt` | 完整文件名 |
| `node_modules` 开头的东西 | 成千上万行，全是依赖包 |

**如果出现了不该有的文件：**

```powershell
git rm --cached "文件名或路径"
```

> **💡 `--cached` 是什么意思？**
> "只从暂存区移除，**不删除磁盘上的文件**"。
> 文件还在你电脑上，只是不进 Git 了。正是你要的效果。

**如果出现了 `node_modules` 成千上万行** —— 说明 `.gitignore` 没生效，
检查一下 `.gitignore` 文件是不是建在了正确的位置（仓库根目录），内容有没有存盘。

**确认干净后**，按 `q` 或 `Ctrl+C` 退出这个界面。

### 3.6 步骤五：提交

```powershell
git commit -m "首次提交：亏了小程序完整代码"
```

> **💡 `-m` 后面那句是干什么的？**
> 是这次提交的**说明文字**。以后你在服务器上看历史时，
> 全靠这句话知道哪次改了什么。
> **写清楚很重要** —— 我见过有人写"fix"然后三个月后完全想不起来改了啥。

### 3.7 步骤六：连上 GitHub

先在 GitHub 网页上准备好仓库地址。假设你的 GitHub 用户名是 `zhangsan`，
仓库名叫 `kuile`，那地址就是：

```
https://github.com/zhangsan/kuile.git
```

> **💡 如果还没在 GitHub 建过仓库？**
> 1. 打开 <https://github.com> → 点右上角 `+` → `New repository`
> 2. Repository name 填 `kuile`
> 3. **Public（公开）/ Private（私有）选 Private** ← 更安全
> 4. ⚠️ **不要勾选** "Add a README file"、"Add .gitignore"、"Choose a license"
>    （勾了会导致远程和本地对不上，徒增麻烦）
> 5. 点 `Create repository`

然后连接：

```powershell
git remote add origin https://github.com/你的用户名/kuile.git
```

> **💡 `origin` 是什么？**
> 它是远程仓库的**昵称**。你以后敲 `git push` 不带参数时，
> Git 默认就推给 `origin`。就像给通讯录里的联系人起了个名字。

### 3.8 步骤七：推送

```powershell
git branch -M main
git push -u origin main
```

**推送时会弹出要密码**：

| 输入什么 | 说明 |
|---|---|
| 用户名 | 你的 GitHub 用户名 |
| 密码 | ⚠️ **不是 GitHub 密码！** 见下面 |

> **💡 密码要用 Token（令牌）**
> GitHub 在 2021 年底就取消了用账号密码推送，必须用 Token。
> 1. 打开 <https://github.com/settings/tokens>
> 2. `Generate new token (classic)`
> 3. `Note` 随便填个名字，比如 `kuile`
> 4. **勾选 `repo` 权限**（或者 `public_repo`，只勾一个就行）
> 5. 拉到底点 `Generate token`
> 6. **复制那串字符**（只显示一次，关掉就看不到了）
> 7. 粘贴到密码框
>
> 粘贴时终端里**不会显示任何字符**（连星号都没有），这是正常的，粘完直接回车。

### 3.9 验证成功

```powershell
git status
```

看到这一行就对了：

```
On branch main
nothing to commit, working tree clean
```

再打开 GitHub 网页刷新，应该能看到你的文件了。

## 第 4 章：服务器端确认和准备

上面的步骤都在**你的电脑**上做。这一章在**腾讯云服务器**上做。

### 4.1 用 FinalShell 连上服务器

1. 打开 FinalShell
2. 点"新建连接" → 选"SFTP"（会自动带出终端）
3. 填写：
   - 名称：随便起，比如 `亏了服务器`
   - 主机：你的服务器公网 IP
   - 端口：`22`（SSH 默认端口）
   - 用户名：`root`
   - 密码：你的服务器密码
4. 点"连接"

> **💡 为什么连上后右边有个文件面板？**
> 那是 SFTP 面板，可以**像资源管理器一样拖拽文件**。
> **这就是你第一次部署时上传代码的方式。**

### 4.2 确认服务器上的代码是 clone 来的

在 FinalShell 左边的终端里输入：

```bash
cd /var/www/kuile
ls -la
```

**看输出里有没有 `.git` 这一项。**

| 结果 | 说明 | 怎么办 |
|---|---|---|
| 有 `.git` | ✅ 太好了，正是我们要的 | 继续第 4.3 节 |
| 没有 `.git` | 你是拖拽上传的 | 走第 4.5 节的迁移方案 |

### 4.3 确认 `.env` 在正确位置（这步别跳）

```bash
ls -la /var/www/kuile/正式上线版/02-后端/.env
```

> **💡 为什么必须是这个路径？**
> 后端代码里写死了要在这个位置找配置文件：
> ```javascript
> // src/config.js 第 12 行
> const envPath = path.resolve(__dirname, '../.env');
> ```
> `__dirname` 是"这个文件所在的目录"（即 `02-后端/src/`），
> `'../.env'` 是"往上退一层找 .env"，合起来就是 `02-后端/.env`。
>
> **找不到会怎样？** 后端启动时读不到配置，会用**默认值**兜底：
> - `JWT_SECRET` 变成公开的默认密钥 → **任何人都能伪造你的用户身份登录**
> - `WECHAT_APPID` 变空 → 微信登录直接失败
>
> **这是本次教程最需要你确认的一件事。**

如果输出 `No such file or directory`，说明 `.env` 不在正确位置，需要挪：

```bash
# 找到它到底在哪
find /var/www/kuile -name ".env" -type f 2>/dev/null
# 然后挪到正确位置（把上面的路径换成实际找到的）
mv /实际路径/.env /var/www/kuile/正式上线版/02-后端/.env
```

### 4.4 确认后端服务在跑

```bash
pm2 list
```

看 `status` 那一列：

| 显示 | 含义 |
|---|---|
| `online` | ✅ 正常 |
| `errored` | ❌ 启动失败，要看日志 |
| `stopped` | 停了 |

再确认数据库通：

```bash
curl http://127.0.0.1:3000/api/health
```

应该返回一段 JSON，里面有 `"db": true`。

### 4.5 如果服务器上不是 clone 的（迁移方案）

你的服务器上已经有能跑的服务，**这个方案要非常小心**，建议先备份。

**第一步：备份**

```bash
cd /var/www
cp -r kuile kuile-backup-$(date +%F)
```

> **💡 `$(date +%F)` 是什么？**
> 一个"命令套命令"的写法。`date +%F` 输出今天的日期（如 `2026-11-28`），
> `$(...)` 把这个结果塞进文件名。备份目录就会叫 `kuile-backup-2026-11-28`。
> **万一出错了，`mv kuile-backup-2026-11-28 kuile` 就能立刻回到原样。**

**第二步：装 Git**（服务器上一般没有）

```bash
apt update && apt install -y git
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

**第三步：克隆到临时目录**

```bash
cd /var/www
git clone https://github.com/你的用户名/kuile.git kuile-new
```

**第四步：搬运不在仓库里的私密文件** ← 最关键

```bash
cp /var/www/kuile/正式上线版/.env /var/www/kuile-new/正式上线版/02-后端/.env
mkdir -p /var/www/kuile-new/正式上线版/02-后端/certs
cp /var/www/kuile/正式上线版/02-后端/certs/* /var/www/kuile-new/正式上线版/02-后端/certs/
```

> **💡 为什么必须搬？**
> `.env` 和 `certs/` 被 `.gitignore` 排除了，**根本不在 GitHub 上**。
> `git clone` 下来的新目录**没有这两个东西**。
> 不搬过去，服务启动时会报"缺少必需的环境变量"然后直接退出。

**第五步：切换**

```bash
cd /var/www
mv kuile kuile-old
mv kuile-new kuile
```

**第六步：装依赖 + 重启 + 验证**

```bash
cd /var/www/kuile/正式上线版/02-后端
npm install --omit=dev
pm2 restart kuile-api
sleep 3
curl http://127.0.0.1:3000/api/health
```

**第七步：观察一两天，确认没问题再删备份**

```bash
rm -rf /var/www/kuile-old
```

## 第 5 章：以后每次更新的标准流程

搭好之后，更新代码就是**固定的 6 条命令**。

### 5.1 本机（改完代码后）

```powershell
cd "e:\9.小程序自己做\02-立了"

# ① 看看改了哪些文件（可选，但推荐养成习惯）
git status

# ② 把改动放进暂存区
git add .

# ③ 提交（写清楚这次改了什么）
git commit -m "修复：打卡第2天不再报「这一天不存在」"

# ④ 推上 GitHub
git push
```

### 5.2 服务器（拉取并重启）

在 FinalShell 的终端里：

```bash
# ① 拉取最新代码
cd /var/www/kuile
git pull

# ② 装依赖（这次没加新依赖的话，这步可以跳过）
cd 正式上线版/02-后端
npm install --omit=dev

# ③ 重启后端
pm2 restart kuile-api

# ④ 验证
curl http://127.0.0.1:3000/api/health
```

### 5.3 什么时候需要额外操作

| 你改了什么 | 需要额外做什么 |
|---|---|
| 后端业务逻辑 | 只需 5.1 + 5.2 |
| `.env`（比如 `DEPOSIT_ENABLED`） | 额外 `pm2 restart`（已包含） |
| `migrations/*.sql`（数据库表结构） | 额外 `npm run migrate` |
| `nginx-kuile.conf` | `cp` 到 `/etc/nginx/conf.d/` + `nginx -t` + `nginx -s reload` |
| 小程序前端代码 | **后端不用动**。用微信开发者工具重新上传版本、提审 |

> **💡 关于 `npm run migrate` 要特别小心**
> 我核实过 `scripts/migrate.js`：它用一张叫 `schema_migrations` 的表记录
> 「哪些迁移文件已经执行过」，**重复跑会自动跳过**，是安全的。
>
> **但是！** `migrations/001_init.sql` 里有 **24 处 `DROP TABLE IF EXISTS`**。
> 也就是说：**如果 `schema_migrations` 这张表被误删了，再跑一次 migrate
> 会把 24 张表全部 DROP 重建 —— 生产数据全部消失。**
>
> **所以：永远不要手动删除 `schema_migrations` 表，也别改它的名字。**
>
> **好消息**：我这次修的 bug **没有改任何表结构**，所以这次更新**不用跑 migrate**。

### 5.4 建议：写一个更新脚本

服务器上可以放一个一键脚本，以后只敲一行：

```bash
cat > /var/www/kuile/update.sh << 'EOF'
#!/bin/bash
set -e
cd /var/www/kuile
echo "▶ 拉取代码"
git pull
cd 正式上线版/02-后端
echo "▶ 安装依赖"
npm install --omit=dev
echo "▶ 重启服务"
pm2 restart kuile-api
sleep 3
echo "▶ 健康检查"
curl -sf http://127.0.0.1:3000/api/health && echo "" && echo "✅ 更新完成" || echo "❌ 更新失败，看日志：pm2 logs kuile-api --lines 50"
EOF
chmod +x /var/www/kuile/update.sh
```

以后更新只敲：

```bash
/var/www/kuile/update.sh
```

> **💡 `set -e` 是什么？**
> "任何一条命令失败就立刻停下"。
> 没有它的话，假设装依赖失败了，脚本还会继续去重启服务，
> 最后你看到"更新完成"，但服务根本没起来 —— **错误被掩盖了**。
>
> **💡 `cat > 文件 << 'EOF'` 是什么写法？**
> 「把后面所有内容原样写进这个文件」。
> 结尾的 `EOF` 是结束标记。用单引号包住 `EOF` 是为了让里面的 `$` 不被 shell 展开。

## 第 6 章：出了问题怎么排查

### 6.1 先看这个对照表

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `git` 命令"不是内部或外部命令" | 终端没刷新 | 关掉终端标签重开，或用完整路径 `D:\1、Software\Git\cmd\git.exe` |
| `git push` 提示密码错误 | 用了 GitHub 密码 | 换成 Token（见 3.8） |
| `git push` 提示 `rejected` | 远程有你本地没有的提交 | `git pull` 先拉再推 |
| 服务器 `git pull` 报冲突 | 服务器上有手工改过的文件 | 见 6.3 |
| 服务起不来 | 看日志 | `pm2 logs kuile-api --err --lines 50` |
| 接口全 500 | 数据库连不上 | `sudo systemctl status mysql` |
| 健康检查失败 | 分层排查 | 见 6.2 |

### 6.2 分层排查大法

```bash
# 第一层：服务本身活着吗？
curl http://127.0.0.1:3000/api/health
```

| 结果 | 说明 | 下一步 |
|---|---|---|
| 有 JSON 返回 | Node 服务和数据库都正常 | 问题在 **Nginx / 域名 / 证书** |
| 连不上/超时 | 问题在 **Node 或数据库** | 跟 Nginx 无关，看 `pm2 logs` |

```bash
# 第二层：公网通吗？
curl https://kuile.banshengcomp.com/api/health
```

> **💡 为什么要分两次？**
> 一次排查掉一半的可能性，比盲目改配置快得多。

### 6.3 服务器上代码被手工改过，导致 pull 冲突

如果你之前在服务器上直接改过代码，`git pull` 会报错。

**先看看服务器上到底改了什么：**

```bash
cd /var/www/kuile
git status
```

**如果那些改动不重要（服务器上的改动是临时的）**，直接丢掉：

```bash
git checkout -- .          # 丢弃所有未提交的修改
git pull                   # 再拉一次
```

> **⚠️ 这会永久删除服务器上的手工修改。**
> 如果你不确定那些改动要不要保留，**先备份**：
> ```bash
> cp -r /var/www/kuile/正式上线版 /var/www/kuile-手工修改备份
> ```

### 6.4 数据库相关的错误对照

| 报错关键字 | 含义 | 解决 |
|---|---|---|
| `ECONNREFUSED` | 连都没连上（网络层） | `sudo systemctl start mysql` |
| `ER_ACCESS_DENIED` | 连上了但密码/权限不对 | 核对 `.env` 的 `DB_USER`/`DB_PASSWORD` |
| `ER_BAD_DB_ERROR` | 数据库不存在 | `sudo mysql -e "SHOW DATABASES;"` 看有没有 `kuile` |
| `Unknown column` | 查了不存在的列 | 这是代码 bug，不是配置问题 |

### 7.4 每次更新后的验证清单

- [ ] `pm2 list` → status 是 `online`，**restarts 数字没在涨**
- [ ] `curl http://127.0.0.1:3000/api/health` → `"db": true`
- [ ] `curl https://kuile.banshengcomp.com/api/health` → 有 JSON
- [ ] `pm2 logs kuile-api --lines 50 --err` → 没有新报错
- [ ] 小程序里实际走一遍改了的功能

> **💡 为什么强调 "restarts 数字没在涨"？**
> PM2 的 `restarts` 列是**重启次数**。如果它在涨，说明服务在**反复崩溃重启**。
> 这种情况下接口会"时好时坏"，日志里能看到崩溃原因。
> **这是个很重要的健康信号，别只看 `online` 就放心。**
