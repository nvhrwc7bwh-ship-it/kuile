# 第 0 章：开始之前，先看这一段

第 0 章：开始之前，先看这一段

## 0.1 你需要准备什么

- [x] 一台 Windows 电脑（你正在用的这台就行）
- [ ] 一个手机号（用来注册各种平台，要能收验证码）
- [ ] 一个银行卡（实名认证和支付要绑卡）
- [ ] 一个企业营业执照（**重要，见下方说明**）
- [ ] 一个人身份证（法人身份证，用于认证）
- [ ] ¥500 ~ ¥2000 的预算（服务器 + 域名 + 认证 + 备案，可能更多）

## 0.2 营业执照：这是最容易卡住的一步

微信小程序的「企业主体」认证、微信支付商户号，都**必须有营业执照**。

| 主体类型 | 需要什么 | 能不能收押金（支付） | 建议 |
|---|---|---|---|
| 个人 | 身份证 | ❌ **不能** | 不适合本产品 |
| 个体工商户 | 个体户营业执照 + 法人身份证 | ✅ 能 | 门槛最低，推荐 |
| 企业 | 企业营业执照 + 对公账户 | ✅ 能 | 最规范 |

> **你的产品要收押金**（用户押钱，达标退钱），所以**必须**用有支付权限的主体。
>
> **结论**：去当地市场监督管理局或政务服务中心办一个「个体工商户营业执照」。
>
> - 名称随便起（跟产品名相关更好，比如「XX 网络科技工作室」）
> - 经营范围要包含「互联网信息服务」或「软件开发」
> - 费用：通常免费或几十元
> - 耗时：当场办结的当天拿，异地可能 3-5 天
>
> ⚠️ **如果暂时办不了营业执照**，可以先用「个体工商户」或者选择「小程序 + 暂不开通押金」的方式上线，押金功能后续再开。但这会推迟上线时间。

# 第 1 章：注册与认证账号

## 1.1 微信公众平台（小程序账号）

**这是小程序的"户口本"。**

- [ ] 打开 <https://mp.weixin.qq.com/>
- [ ] 点右上角「立即注册」
- [ ] 选「小程序」
- [ ] 填邮箱（**这个邮箱要常用**，以后接收审核结果）
- [ ] 激活邮箱（收激活邮件 → 设密码）
- [ ] 选主体类型 → 填营业执照信息
- [ ] 填「管理员」信息（要扫管理员微信）
- [ ] 管理员微信扫码验证
- [ ] 完成注册

> **💡 原理：为什么注册的是「主体」而不是「个人」**
> 微信生态里，账号是挂在**主体**（个人 / 个体户 / 企业）下面的。
> 主体决定了你能调哪些「接口能力」—— 比如 `wx.requestPayment`（发起支付）、
> `wx.chooseMedia`（拍照上传）这类能力，**个人主体是拿不到的**。
> 更关键的是：主体决定了**钱进谁的口袋**。个人主体没有「商户号」，
> 也就没法收款，押金这个产品核心功能直接做不了。
> 所以主体不是填完就完事，它是后面所有能力的「资格前提」。

**注册成功后你会拿到 2 个重要东西（记下来）：**

| 名称 | 在哪里找 | 长什么样 | 用来干什么 |
|---|---|---|---|
| **AppID（小程序 ID）** | 开发管理 → 开发设置 → AppID | `wx1234567890abcdef` | 后端要填 |
| **AppSecret（小程序密钥）** | 开发管理 → 开发设置 → AppSecret →「重置」 | 32 位乱码 | 后端要填，**泄露=账号被冒用** |

> **💡 原理：AppID 和 AppSecret 是一对「公开身份」和「私密钥匙」**
>
> - `AppID` 是公开的，相当于门店招牌 —— 所有人都能看到，它的作用是**标识「是哪一个小程序」**。
> - `AppSecret` 是私密钥匙，相当于仓库钥匙 —— 有了它，任何人都能冒充你的小程序
> 去调微信的接口（换 openid、发模板消息等）。
>
> **那微信怎么区分「真用户」和「假用户」？**
> 靠 `wx.login()`：小程序端调这个接口，微信返回一个**临时 code**（5 分钟内有效、只能用一次），
> 后端拿这个 code + AppSecret 去微信服务器换 `openid`（这个用户在你小程序里的唯一编号）。
> **AppSecret 只在服务器上用，从不下发给小程序端** —— 这是整套登录安全的地基。

> **⚠️ AppSecret 一定要保密**
>
> - 不要发到群里、微信里
> - 不要截图发朋友圈
> - 不要提交到 Git 仓库
> - 填进 `.env` 文件，那个文件最后要设权限为「只有自己能看」

- [ ] **记下 AppID** → 填到后面 `.env` 的 `WECHAT_APPID`
- [ ] **记下 AppSecret** → 填到 `.env` 的 `WECHAT_APPSECRET`

> **⚠️ 这两处也要填，漏了小程序登录不了：**
> - `.env`（后端）里的 `WECHAT_APPID` / `WECHAT_APPSECRET` —— 后端拿它们去微信换 openid
> - `03-小程序前端/project.config.json` 里的 `appid`（现在是 `touristappid`）
>   —— 开发者工具识别「这是我的小程序」，**正式版不填这个就传不上去**
>
> **两个地方必须是同一个 AppID**，不一致会表现为「能打开但登录失败」。

### 认证（企业认证）

- [ ] 微信公众平台左侧「设置」→「基本设置」→「微信认证」
- [ ] 选认证类型：「企业」
- [ ] 填营业执照信息 + 对公账户
- [ ] 微信支付打款验证（打一笔随机金额到你对公账户，你确认金额）
- [ ] 认证费用：**¥300 元/年**
- [ ] 等待审核：**1-7 个工作日**

> **💡 原理：「打款验证」在验证什么？**
> 它验证的是**「你真的是这个主体的法人/负责人」**，而不是「你手上有这个营业执照的照片」。
> 流程是：微信往你的对公账户打一笔随机金额（比如 0.03 元），
> 你在银行 App 里看到这笔钱的金额，把它填回后台。
> **只有能操作这个银行账户的人才能看到那笔随机金额** ——
> 这就从「材料造假」升级成了「资金控制权验证」，是实名认证里最强的一档。
> 个体工商户常用「法人个人卡」做验证，原理一样。

> **💡 关于认证费**：如果你的小程序涉及「减肥」「体重」这类内容，
> **微信大概率会要求你提交《互联网信息服务许可证》或相关资质**。
> 这个在第 12 章「合规红线」里详细讲，请务必读。

## 1.2 腾讯云账号

- [ ] 打开 <https://cloud.tencent.com/>
- [ ] 用微信或手机号注册
- [ ] 完成实名认证（个人或企业实名都可以，但买服务器建议企业）
- [ ] **开通微信支付所需的资质也要在这里做**（见第 7 章）

> **💡 原理：为什么服务器、数据库、存储桶都放在同一家（腾讯云）？**
> 因为**内网互通**。你的服务器要连数据库、要读写图片存储桶，
> 如果它们在不同的云厂商，就必须走公网 —— 那意味着：
> ① 数据在公网裸奔（有被截获的风险）；② 流量费按公网单价收（贵）；
> ③ 延迟高、还可能因为安全组配置失误直接暴露数据库。
>
> 同一家云厂商 + 同地域 + 同可用区，它们之间走**内网**（腾讯云内部高速网络，不收费、不加密但不出公网）。
> 这是「云原生部署」最基础的一条布局原则：**把要频繁通信的东西放在一起**。

# 第 2 章：域名与证书

## 2.1 为什么必须要域名

微信小程序正式版**只允许调用 HTTPS 域名**，不能直接用 IP 地址。
而且域名要能**备案**（中国大陆的硬性要求）。

> **💡 原理：微信为什么不给小程序「内网直连」的自由？**
> 小程序本质是「跑在微信里的网页 + JS」。微信出于两个原因收紧了网络访问：
> ① **用户安全**：如果小程序能随便请求任意 IP，用户手机上的隐私（位置、通讯录、相册）
>    就可能被恶意小程序拿去传给第三方服务器。限制成「只能请求你在微信后台白名单里登记的域名」，
>    等于让用户能一眼看出「这个小程序会把我的数据发到哪里」。
> ② **平台可控**：微信要能保证所有小程序的流量都走 HTTPS（加密），
>    并且能对恶意小程序做拦截和封禁。
>
> 这就是「**服务器域名白名单**」的由来 —— 第 9.4 节配的那三行就是这个机制。

## 2.2 买域名

- [ ] 打开 <https://dnspod.cloud.tencent.com/>
- [ ] 搜索你想要的域名，比如 `kuile.com` / `kuileapp.com`
- [ ] 建议买 `.com` 或 `.cn`，`.top` `.xyz` 便宜但可能不被审核接受
- [ ] 买 1 年即可（后面可续费）
- [ ] 建议同时买一个 `api.你的域名` 的子域名解析（免费）

> **💡 原理：「域名」和「IP 地址」的关系**
> IP 地址是服务器的「门牌号」，但它会变（换服务器、扩容都可能变）。
> 域名是「贴在门上的名字」，通过 DNS 解析（域名系统）可以查到对应的 IP。
>
> **为什么接口要用单独的** `api.` **子域名？**
> ① **隔离故障**：以后前端页面放 `www.你的域名`，接口放 `api.你的域名`，
>    两边可以独立部署、独立扩容、独立配证书，互不影响。
> ② **权限分离**：前端域名可以配 CDN（缓存静态资源、加速），
>    接口域名**绝对不能**配 CDN —— 接口的响应是每时每刻都不同的用户数据，
>    被 CDN 缓存了就是「A 用户看到了 B 用户的数据」，这是安全事故。
> ③ **清晰可辨**：日志、监控里一眼看出请求是打向哪一块。

## 2.3 备案（ICP 备案）

**这是耗时最长、最容易卡人的一步，没有捷径。**

- [ ] 腾讯云控制台 → 搜索「备案」→ 首次备案
- [ ] 填主体信息（个人或企业）
- [ ] 填网站信息：
  - 网站名称：你的产品名
  - 网站服务内容：互联网信息服务 / 工具类
  - 网站域名：`api.你的域名`
- [ ] 上传营业执照扫描件、身份证、手写签名的《备案信息真实性承诺书》
- [ ] 小程序负责人**人脸核验**（用微信扫脸，微信小程序特有）
- [ ] 腾讯云初审（1-2 个工作日）→ 管局审核（**7-20 个工作日**）
- [ ] 备案通过后会给你一个**备案号**（如：京ICP备XXXXXXXX号）

> **💡 原理：为什么国内一定要备案？**
> 备案是「互联网信息服务准入许可」的登记制度，由工信部管。
> 核心逻辑是：**谁在互联网上对公众提供服务，必须留下可追溯的实名信息**。
> 服务器放在中国大陆境内时，运营商会强制要求域名已完成备案才允许绑定，
> 这是一个「网络空间实名制」的技术抓手。
>
> **备案要提交什么、为什么这些材料有效？**
>
> - 营业执照/身份证 → 证明「这个网站背后是谁」
> - 主体负责人**人脸核验** → 比对证件和人脸，确认本人操作（防冒用材料代办）
> - 域名所有权证明 → 证明你真的控制这个域名
> - 网站服务内容 → 决定后续要遵守哪类内容规范
>
> **🔴 一个坑**：备案期间你的域名**是不通的**（运营商会拦截未备案域名的请求）。
> 所以本地开发时可以用 `http://127.0.0.1:3000` 或者在开发者工具里勾
> 「不校验合法域名」，完全不受影响 —— **备案和开发是可以并行的**。

> **⏱ 备案通常要 1-3 周。**
> **💡 强烈建议：备案提交后，就立刻去做第 3~7 章（买服务器、开数据库、申请微信支付），别干等。**
>
> **📌 备案期间能做什么？**
>
> - 服务器可以先买、代码可以先写、可以先用 `http://` 在开发工具里测试
> - 只是在真机正式版上不能访问 —— 不影响开发

## 2.4 HTTPS 证书

- [ ] 腾讯云控制台 → 搜索「SSL 证书」
- [ ] 选「免费证书」→ 申请
  - 域名填 `api.你的域名`
  - 验证方式选「DNS 解析」→ 给你两条 DNS 记录
- [ ] 去 DNS 解析添加这两条记录（验证完可以删掉）
- [ ] 等待签发（**几分钟到几小时**）
- [ ] 下载 **Nginx 格式**的证书（里面有两个文件：`fullchain.pem` 和 `privkey.pem`）

> **💡 原理：HTTPS 是怎么工作的（不需要密码学基础版）**
>
> 你和服务器之间先做一次「握手」，核心是三步：
>
> 1. 服务器把它的**证书**给你看，证书里有一对密钥：
>
>    **公钥**（可以公开，用来加密）和**私钥**（绝不公开，用来解密）。
> 2. 你的浏览器用这个**公钥**加密一把随机的「会话密钥」，发给服务器。
>
>    （用公钥加密的东西，只有私钥能解开 —— 这就是非对称加密的作用）
> 3. 服务器用**私钥**解开，之后双方就用这把会话密钥对称加密通信，
>
>    而且互相验证过了对方身份。
>
> **证书的作用是「让浏览器相信这个公钥是真的」** ——
> 证书由 CA（证书颁发机构）签发，浏览器内置了这些 CA 的公钥，
> 能验证签名就说明「这个证书是真的 CA 发的」，进而相信里面的域名和公钥。
>
> **⚠️ 证书会过期**（免费证书一般 3 个月），到期不换，浏览器会直接报红。
> 建议：上线时就在日历上设一个「每月提醒」的闹钟，或者用腾讯云的自动续期功能。

> **保存好这个压缩包**，第 8 章部署时要用。

# 第 3 章：腾讯云服务器

## 3.1 买服务器

- [ ] 腾讯云控制台 → 搜索「轻量应用服务器」（**推荐**，比 CVM 简单便宜）
- [ ] 地域选**离用户近的**（用户主要在国内就选「广州」或「上海」）
- [ ] 配置：
  - **镜像**：选「系统镜像」→「Ubuntu 22.04 LTS」（**推荐新手**，文档多）
  - **实例套餐**：2核 4G 起步（如果预算紧，2核2G 也能跑，但并发高了会卡）
  - **系统盘**：60GB SSD
  - **带宽**：3-5 Mbps（图片走 COS 不占服务器带宽，API 用不了多少）
  - **购买时长**：1 年
- [ ] 设置 root 密码（**记牢！这是登录服务器的密码**）
- [ ] 购买

> **💡 原理：为什么选「轻量应用服务器」而不是「云服务器 CVM」？**
> 两者底层都是虚拟机，但**管理方式不同**：
>
> - CVM 是**裸虚拟化**（KVM 虚拟出裸金属再装系统），要自己装 Nginx、防火墙、快照策略，
> 灵活但步骤多。
> - 轻量应用服务器是**已经打包好的镜像**（预装了 Nginx、MySQL、Docker 等常见软件），
> 控制台直接给「一键重装、防火墙规则、备份、SSH 密钥登录」这些按钮。
>
> 对本项目（一个 Node.js 后端 + Nginx + 自建 MySQL）来说，轻量服务器完全够用，
> 而且**你的操作界面是图形化的**，出错一键重装系统，比 CVM 手工救火友好得多。
>
> **💡 2核4G 够不够？**
> 算一下：Node.js 空闲约 100MB，一个请求的峰值约 2-5MB，MySQL 连接池 10 个连接约 50MB
> + InnoDB 缓冲池 1G（见第 4 章 4.3 节的调优），Nginx 约 20MB
> → 实际内存占用 **1.2GB 左右**。2核2G 也能跑，但缓冲池要调小，更容易吃紧。
> 但 2核4G 的价值在于**并发余量**：打卡照片上传、AI 判定这种耗时操作会占住线程。
>
> **💡 带宽为什么 3-5M 就够？**
> 因为**大文件不走服务器** —— 打卡照片是直传腾讯云 COS（后端只签个名），
> 服务器只传 JSON（几 KB）。真正吃带宽的是照片，但照片走的是 COS 的 CDN 通道。
>
> **💡 现在这台上要跑三个东西了**（比原方案多一个）：
>
> ```
> ┌─────────────────────────────────────┐
> │  轻量应用服务器（2核4G / Ubuntu 22.04）│
> │                                     │
> │   Nginx      :80/:443   ← 对外唯一入口 │
> │   Node 后端  :3000      ← 只监听本机  │
> │   MySQL 8.0  :3306      ← 只监听本机  │
> └─────────────────────────────────────┘
> ```
> **注意 Node 和 MySQL 都只监听 `127.0.0.1`** ——
> 对外只暴露 80 和 443 两个端口，攻击面最小。

## 3.2 第一次登录服务器

> **工具**：Windows 上用「Windows Terminal」（自带）或下载「MobaXterm」/「FinalShell」（图形化，推荐新手）

- [ ] 在腾讯云控制台的服务器列表里，点「登录」，选择「网页登录」（OrcaTerm）
- [ ] 或用本地终端：
  ```
  ssh root@你的服务器公网IP
  ```
  第一次连接会问 `Are you sure you want to continue connecting?` → 输入 `yes`
  然后输密码（**输入时屏幕不显示字符，是正常的**）

> **💡 原理：SSH 是什么？**
> SSH（Secure Shell）= **能加密的远程命令行**。
> 你在自己电脑上敲命令，实际是在服务器上执行的。
>
> - **为什么第一次要输** `yes`：SSH 通过服务器的「主机密钥指纹」来防止
> **中间人攻击**（有人冒充你的服务器骗你密码）。第一次连接时，
> 本地没有这个指纹，SSH 让你确认一次并存下来；以后如果指纹变了会直接报警。
> - **为什么密码不显示字符**：Linux 的密码输入不回显（防止肩窥和录屏泄露长度）。
> 看到「什么反应都没有」是正常的，盲打完回车即可。
> - **为什么能用 root 登录**：root 是 Linux 的**超级管理员**（拥有系统的全部权限）。
> 日常运维用普通用户 + `sudo` 更安全，但初期为了简单，用 root 完全可以。

## 3.3 服务器初始化

在服务器上依次执行：

### 3.3.1 更新系统

```bash
apt update && apt upgrade -y
```

> **💡 原理：为什么上线前一定要先更新？**
> 系统自带的软件包（尤其是 OpenSSL、Nginx、Node.js 依赖的系统库）经常有安全漏洞。
> 这些漏洞的公告是公开的 —— 意味着**攻击者也知道**。
> 一台没打补丁的服务器放到公网上，通常撑不过几天就会被自动化扫描工具盯上。
> `apt update` 是「刷新软件源列表」（告诉你有哪些新版本），
> `apt upgrade` 是「把已安装的旧版本换成新版本」。

### 3.3.2 安装基础工具

```bash
apt install -y curl wget git nginx mysql-server mysql-client unzip
```

> **💡 原理：这几个工具各自干什么？**
>
> | 工具 | 用途 | 本项目里在哪用 |
> |---|---|---|
> | `curl` | 发 HTTP 请求 | 测试 `/api/health`、写健康检查告警 |
> | `wget` | 下载文件 | 下载 Node.js 安装脚本 |
> | `git` | 版本控制 | 用 Git 方式部署时 clone/pull |
> | `nginx` | Web 服务器 | 反向代理 + HTTPS 终结 + 限流 |
> | `mysql-server` | **数据库服务端** | 第 4 章自建 MySQL |
> | `mysql-client` | 数据库命令行客户端 | 手工查数据、备份（`mysqldump`） |
> | `unzip` | 解压 | 解压证书、代码包 |
>
> **💡 `mysql-server` 和 `mysql-client` 的区别？**
> - `mysql-server` = **数据库本体**（真正存数据的服务）
> - `mysql-client` = **命令行工具**（`mysql`、`mysqldump` 这些）
>
> Ubuntu 会把两者一起装上（`mysql-server` 依赖 `mysql-client`），
> 但分开写出来更清楚 —— **服务端是「被依赖的」，客户端是「你天天用的」**。
>
> **💡 Nginx 是什么，为什么不能只用 Node.js？**
> Node.js 本身就是个 HTTP 服务器，为什么还要 Nginx？因为 Nginx 擅长做四件 Node 不擅长的事：
> ① **HTTPS 终结**：TLS 握手、证书管理在 Nginx 里做，Node 只处理解密的明文 —— 这是最常见的架构。
> ② **静态文件**：直接读磁盘返回图片/JS/CSS，不过 Node 进程 —— 省内存、速度快。
> ③ **反向代理**：对外只暴露 80/443，把请求转给内部 3000 端口的 Node。
> ④ **限流**：按 IP 限制请求频率，防刷（第 12 章会配）。
>
> 这个架构叫「**前后端分离部署**」，生产环境几乎都这么干。

### 3.3.3 安装 Node.js 20

```bash
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
apt install -y nodejs
node -v    # 应该显示 v20.x.x
```

> **💡 原理：Node.js 是什么？**
> Node.js 让 JavaScript 能跑在服务器上（原本 JS 只能在浏览器跑）。
> 它的特点是**单线程 + 事件循环** —— 一个请求没读完时不阻塞，而是去处理下一个请求，
> 所以用 Node 写「大量并发、每个请求都很快」的后端特别合适。
>
> 本项目后端全是「查一下数据库、返回 JSON」，属于典型的 I/O 密集型，Node 是最佳选择。
>
> **💡 为什么要用 Nodesource 那个** `curl | bash`**？**
> Ubuntu 官方源里的 Node 版本往往很旧（可能还是 16 或 18）。
> Nodesource 提供了 NodeSource 自己的软件源，加上之后 `apt install nodejs`
> 就能装到最新 LTS（20）。那个 `curl | bash` 就是在**把这个源加进你的系统并刷新列表**。
>
> **⚠️ 关于** `curl | bash` **这类命令**
> 它字面意思是「下载一个脚本然后立刻用 root 执行」。方便，但**你必须知道自己在执行什么**。
> 官方源可信，但养成习惯：先 `curl` 下载看一眼内容，再执行。
> 这个习惯能挡掉绝大多数「复制粘贴被篡改」的攻击。

### 3.3.4 安装 PM2（进程管家）

```bash
npm install -g pm2
pm2 startup systemd -u root --hp /root
pm2 save
```

> **💡 原理：PM2 是什么？**
> 一个「进程保姆」。后端服务跑起来后交给它看着：
> 程序崩了它自动重启，服务器重启它自动拉起。**不装的话，服务器一重启服务就挂了。**
>
> **💡 三条命令分别在干什么？**
>
> - `npm install -g pm2`：**全局安装** PM2（`-g` = global，装到系统级目录，
> 任何目录下都能用）。对比：不带 `-g` 是装在当前项目里，只能在项目里用。
> - `pm2 startup systemd -u root --hp /root`：让 Linux 的 **systemd**（系统的服务管理器）
> 在开机时启动 PM2 守护进程。systemd 是 Linux 的「开机自启总管」，
> 所有「开机就该跑起来的东西」都向它登记。
> - `pm2 save`：把**当前 PM2 正在跑的程序列表**存到磁盘。
> 这条别漏 —— `startup` 只是让 PM2 起来了，但 PM2 起来后要读这个存档才知道要拉起哪些服务。
> **只做 startup 不做 save，等于服务器重启后 PM2 起来了但什么都没跑。**

### 3.3.5 放行端口（腾讯云安全组）

- [ ] 腾讯云控制台 → 服务器 → 「安全组」→ 「修改规则」
- [ ] 添加规则：
  | 应用类型 | 协议 | 端口 | 来源 | 用途 |
  |---|---|---|---|---|
  | 自定义 | TCP | 22 | 你的 IP 或 0.0.0.0/0 | SSH 远程登录 |
  | 自定义 | TCP | 80 | 0.0.0.0/0 | HTTP（跳转 HTTPS + 备案验证） |
  | 自定义 | TCP | 443 | 0.0.0.0/0 | HTTPS（小程序接口） |

- [ ] **不需要、也绝对不要开放 3306（数据库端口）**

> **💡 原理：安全组是什么？为什么它和服务器里的防火墙是两层？**
> 安全组是**云厂商在虚拟机外面**包的一层网络过滤规则。
> 流量必须先过安全组，才到得进你的服务器内部。
> （服务器内部还有一层 `ufw`/`iptables`，腾讯云镜像默认关着或只开 22/80/443。）
>
> **两层防火墙是「纵深防御」** —— 就算内层配错，外层还能挡一道。
>
> **🔴 端口 3306 绝对不要开**
> MySQL 端口暴露在公网上，等于告诉全世界「这里有个数据库，来猜密码」。
> 全世界每秒都有几千台机器在扫 3306 端口，弱密码几小时内必被爆破。
>
> **💡 本项目是自建 MySQL，连「放行内网 IP」这一步都不需要**
> 因为数据库就装在这台机器上，而且第 4 章会把 `bind-address` 设成 `127.0.0.1`
> —— **只接受本机连接**。
>
> 也就是说：**数据库在操作系统层面就没有对外的监听端口**，
> 安全组里加不加 3306 都一样（但还是别加，形成肌肉记忆）。

### 3.3.6 关闭不需要的服务

```bash
# 看看当前监听的端口
ss -tulpn
```

> **💡 原理：**`ss -tulpn` **在看什么？**
>
> - `s` = socket（套接字，即网络通信端点）
> - `t`/`u` = TCP / UDP
> - `l` = listening（正在监听，即「等待连接」）
> - `p` = process（显示占用它的程序）
> - `n` = 不解析域名（显示数字 IP，快）
>
> **为什么要定期看这个？**
> 因为「你以为关掉了但其实还开着」是安全事故里最常见的一类。
> 用 `ss` 扫一遍，看看有没有你不认识的服务在监听 —— 尤其注意 **22 之外的远程管理端口**
> 和 MySQL/Redis/MongoDB 这类数据服务。
>
> **💡 部署完成后的正确状态应该是**：
> ```
> 22    （SSH）      ← 你自己用
> 80    （HTTP）     ← 跳转 HTTPS
> 443   （HTTPS）    ← 对外唯一业务入口
> 3000  （Node）     ← 只监听 127.0.0.1
> 3306  （MySQL）    ← 只监听 127.0.0.1
> ```
> **凡是 `0.0.0.0:3000` 或 `0.0.0.0:3306` 都是不对的**，
> 说明配置没生效，要回去检查 `bind-address`。

### 3.4 上传代码到服务器

> **💡 为什么这一步要放在第 4 章（数据库）之前？**
>
> 因为**后面第 4 章的 4.6 / 4.7 / 4.8 三小节都要用到代码**：
>
> | 步骤 | 需要什么 | 来自哪 |
> |---|---|---|
> | 4.6 填 `.env` | `.env.example` 模板 | 代码 |
> | 4.7 建表 | `migrations/001_init.sql` + `mysql2` | 代码 + 依赖 |
> | 4.8 备份 | `04-部署脚本/backup-db.sh` | 代码 |
>
> **代码还没上来，这些一步都做不了。**
> 所以顺序是：**铺代码 → 配数据库 → 补齐密钥 → 启动服务**。

#### 方式 A：用 Git（推荐）

- [ ] 把 `正式上线版` 目录传到 GitHub / Gitee / Coding 仓库
- [ ] 在服务器上：
  ```bash
  mkdir -p /var/www
  cd /var/www
  git clone 你的仓库地址 kuile
  cd kuile/正式上线版
  ```

#### 方式 B：直接拖拽上传（新手友好）

- [ ] 下载「MobaXterm」或「FinalShell」
- [ ] 新建 SFTP 连接，填服务器 IP、root、密码
- [ ] 把 `正式上线版` 整个文件夹拖到 `/var/www/kuile/`

上传后目录应该是：

```
/var/www/kuile/正式上线版/
├── 01-文档/
├── 02-后端/
├── 03-小程序前端/
├── 04-部署脚本/
└── 05-上线执行清单/
```

- [ ] **装依赖**（第 4 章的验证命令要用到 `mysql2`）：

```bash
cd /var/www/kuile/正式上线版/02-后端
npm ci --omit=dev 2>/dev/null || npm install --omit=dev
```

- [ ] 确认装上了：
```bash
ls node_modules/mysql2 >/dev/null && echo "✓ 依赖装好了"
```

> **💡 原理：SFTP 是什么？和「传文件」有什么区别？**
> SFTP = SSH File Transfer Protocol，**走 SSH 通道加密传文件**。
> 和普通 FTP 的区别：FTP 是明文传输（文件内容在网络上是裸的），
> SFTP 是在 SSH 的加密通道里跑的，和你 `ssh` 登录用的是同一套密钥体系。
>
> **💡 为什么推荐 Git 而不是拖拽？**
>
> | | 拖拽上传 | Git |
> |---|---|---|
> | 传文件大小 | 全量传（慢） | 只传改动部分（快） |
> | 版本历史 | 没有 | **每次改动都有记录，可回滚** |
> | 改错了怎么办 | 重新拖一遍 | `git log` 找到好版本，`git checkout` 切回去 |
> | 谁改的 | 不知道 | 有提交记录 |
> | 传输是否加密 | 看工具 | SSH 加密 |
>
> 本项目部署手册第 8 节专门有「回滚」一节 —— **有 Git 才能一键回滚**。
> 建议至少会用 Git 的基础三条命令：`clone`（首次拉）、`pull`（更新）、
> `log`（看历史）。这三个不需要懂原理，照着抄就行。
>
> **💡 `npm ci` 和 `npm install` 的区别？**
>
> - `npm ci`：**严格按** `package-lock.json` **精确安装**，版本一个不差，
>   并且会**先删掉已有的 `node_modules`**（保证干净）。
> - `npm install`：按 `package.json` 里的 `^2.19.2` 这类范围装，
>   **可能装到更新的小版本**。
>
> **生产环境用 `npm ci`**，因为「昨天能跑的，今天也能跑」很重要。
> `--omit=dev` 是跳过开发依赖（测试框架之类），省空间、缩小攻击面。
>
> 脚本里写的是 `npm ci --omit=dev 2>/dev/null || npm install --omit=dev` ——
> **前一条失败会自动退到后一条**，兼容没有 lock 文件的情况。

# 第 4 章：数据库（自建 MySQL 8.0）

> **本章是自建方案。** 数据库就装在第 3 章那台服务器上，
> **不额外购买腾讯云托管数据库**。整套配置约 30 分钟。

> **💡 先说清楚「为什么可以自建」**
>
> 托管数据库贵，贵在它替你扛了一堆责任：
>
> | 托管版包了什么 | 自建后谁来扛 |
> |---|---|
> | 主从高可用（主库挂了自动切） | 你 —— 只有一台，挂了就是全站不可用 |
> | 每日自动备份 + 秒级回档 | 你 —— 自己写脚本（本章 4.7 给了现成的） |
> | 监控告警（连接数、慢查询、磁盘） | 你 —— 第 12 章的巡检清单 |
> | 版本升级不 downtime | 你 —— 升级窗口要停服 |
> | 控制台可视化 | 你 —— 只有命令行 |
> | 免运维（打安全补丁） | 你 —— 得自己跟 CVE |
>
> **MySQL 软件本身是 GPL 开源的，免费。** 差值就是你为「SLA」付的钱。
>
> **💡 本项目的代码完全不需要托管版才有的能力**（逐条核对过）：
> `FOR UPDATE` 行锁（支付回调防重复）、`JSON` 列、`ON DUPLICATE KEY UPDATE`、
> 外键 `ON DELETE CASCADE`、事务、连接池 —— 全是标准 MySQL 8.0 功能，**零改代码**。
>
> **💡 自建的最大好处：数据库只监听 `127.0.0.1`**
> —— 不对公网开放，**所以完全不需要配置数据库安全组**。
> 托管版要在控制台配「安全组只放行服务器内网 IP」，那是新手最容易配错的地方，
> 配错了数据库就暴露在公网上。自建直接消灭了这个问题。
>
> **📋 本章前置条件**
>
> - [x] 第 3 章 服务器初始化完成
> - [x] **第 3.4 节「上传代码到服务器」已完成** ← 4.6 / 4.7 / 4.8 都要用到代码
>
> **本章分两段：**
>
> | 小节 | 依赖代码吗 | 内容 |
> |---|---|---|
> | 4.1 ~ 4.5 | ❌ 不依赖 | 纯服务端操作：装、加固、调优、建库、调时区 |
> | 4.6 ~ 4.8 | ✅ **依赖代码** | 填 `.env`、建表、配备份 |

## 4.1 装 MySQL 8.0

- [ ] SSH 登录服务器
- [ ] 安装 MySQL 服务器：

```bash
sudo apt update
sudo apt install -y mysql-server
```

- [ ] 确认版本（必须 8.0 以上，5.7 不支持 `JSON` 列的完整功能）：

```bash
mysql --version
```

- [ ] 启动并设为开机自启：

```bash
sudo systemctl start mysql
sudo systemctl enable mysql
sudo systemctl status mysql    # 看到 active (running) 就对了
```

> **💡 原理：`systemctl enable` 和 `start` 的区别？**
> - `enable` = **设置开机自启**（写进开机启动清单）
> - `start` = **现在立刻启动**
>
> 两个都要做。只 `enable` 的话，当前还没跑起来；只 `start` 的话，重启服务器就没了。

> **💡 原理：Ubuntu 22.04 自带的 MySQL 是 8.0，不用额外加源**
> 很多人以为要像 Node.js 那样先加 Nodesource 源 ——
> 那是因为 **Node.js 官方源里的版本太旧**，而 Ubuntu 官方仓库里 **MySQL 8.0 是标准配置**，
> `apt install mysql-server` 直接就是 8.0.x。
>
> **本项目需要 MySQL 8.0 的原因**：`migrations/001_init.sql` 里用了 `JSON` 类型
> 和 `JSON_ARRAY()`（存见证席的档位历史），5.7 支持不完整，8.0 才是完整体验。

## 4.2 安全加固（必做，3 步）

> **💡 原理：为什么装完 MySQL 不能直接用？**
> Ubuntu 的 MySQL 默认配置对「本机自用」是安全的，但我们要把它暴露给 Node 进程，
> 同时**绝对不能让它出现在公网上**。下面三步就是把这个边界锁死。

### ① 只监听本机

```bash
sudo vi /etc/mysql/mysql.conf.d/mysqld.cnf
```

找到 `[mysqld]` 段，确认或加上这一行：

```ini
bind-address = 127.0.0.1
```

改完重启：

```bash
sudo systemctl restart mysql
```

验证：

```bash
sudo ss -tulpn | grep 3306
```

**应该只看到 `127.0.0.1:3306`，不应该看到 `0.0.0.0:3306` 或 `*:3306`。**

> **💡 原理：`bind-address` 是 MySQL 最重要的安全开关**
>
> `bind-address = 127.0.0.1` 意思是「**只接受从本机 loopback 过来的连接**」。
> 别人从公网发来的请求在 TCP 层就被拒绝了 —— **根本没进到 MySQL 的认证逻辑**。
>
> 对比托管版：云数据库的实例本身就绑在「内网地址」上，你还得额外配安全组。
> 自建版把安全边界收在**一个配置文件**里，反而更彻底。

### ② 禁止 root 远程登录

同样在 `mysqld.cnf` 的 `[mysqld]` 段：

```ini
skip-name-resolve
```

> **💡 原理：这一行在干什么？**
>
> 默认情况下，MySQL 收到连接请求时会**反向 DNS 查询**客户端的主机名
> （拿 IP 反查名字，再去 `user` 表里找匹配 `host` 的账号）。
>
> 问题有两个：
> ① **慢**：DNS 查询是网络 IO，每次连接都要等一下
> ② **不安全**：如果 DNS 被污染，攻击者可以让 MySQL 误以为你的连接来自 `localhost`，
>    从而用 root 账号连上 —— **这是一个真实的绕过手段**。
>
> 加上 `skip-name-resolve` 后，MySQL **只认 IP，不反查主机名**。
> 代价是：`user` 表里的 `host` 字段不能再写主机名（只能写 `127.0.0.1` 或 `%`），
> 这正是我们要的。

### ③ 删掉匿名用户

```bash
sudo mysql_secure_installation
```

按提示走，**关键几项选**：

| 提示 | 选什么 |
|---|---|
| Set a root password for the current user? | **Y**（设个 root 密码，记牢） |
| Remove all anonymous users? | **Y** |
| Disallow root login from remote? | **Y** |
| Remove test database? | **Y** |
| Reload privilege tables? | **Y** |

> **💡 原理：`mysql_secure_installation` 在改什么？**
>
> 它做的是**收紧 MySQL 默认账号体系**。默认装完的 MySQL 有：
> - `root@localhost`（密码为空）
> - `''@'localhost'`（**匿名用户**，任何密码都能进！）
>
> 匿名用户是**教科书级的后门**：正常情况下你改 root 密码不影响它，
> 攻击者可以用任何用户名密码登录。清掉它是最基本的动作。
>
> **「Disallow root login from remote」为什么也要选？**
> root 权限太大，一旦被拿到就是整个实例沦陷。
> 我们日常用**专门的业务账号** `kuile`，不需要 root 远程。

## 4.3 内存调优（2核4G 机器必做）

```bash
sudo vi /etc/mysql/mysql.conf.d/mysqld.cnf
```

在 `[mysqld]` 段加上：

```ini
# ---- 内存 ----
# 缓冲池：MySQL 用来缓存表和索引的内存
# 默认会占物理内存的 50%~75%，2核4G 上会吃掉 2~3G，
# 加上 Node + Nginx 很容易触发 OOM Killer（进程被内核杀掉）
innodb_buffer_pool_size = 1G
innodb_log_buffer_size = 32M

# 最大连接数（本项目连接池是 10，留足余量即可）
max_connections = 100

# 性能监控模块：内测期用不上，关掉省内存
performance_schema = OFF
```

改完重启：

```bash
sudo systemctl restart mysql
```

验证生效：

```bash
sudo mysql -e "SHOW VARIABLES LIKE 'innodb_buffer_pool_size';"
```

> **💡 原理：为什么 MySQL 默认会吃掉你一半的内存？**
>
> `innodb_buffer_pool_size` 是 InnoDB 的「工作台」——
> **数据库读数据时先把数据页（默认 16KB）从磁盘读进这个内存池**，再从内存给你。
>
> 原理上，这个池应该装得下「最热的那部分数据」，让绝大多数查询不用碰磁盘。
> MySQL 的自动估算逻辑在没有历史数据时，会保守地按物理内存的 50~75% 来设 ——
> 对一台专用的数据库服务器这是对的，**但你这里是「数据库 + Node + Nginx」挤在一台 4G 机器上**。
>
> **💡 原理：OOM Killer 是什么？为什么它会让服务「莫名重启」？**
>
> 当物理内存耗尽，Linux 内核的 **OOM Killer** 会挑一个进程杀掉以释放内存。
> 它通常会挑**占用内存最多的那个** —— 在你的机器上，那就是 MySQL。
>
> **后果**：MySQL 被杀 → Node 连不上数据库 → 接口全 500 → MySQL 重启后短暂恢复 →
> 再次被压垮 → **循环**。表现就是「服务时好时坏、日志里有一堆
> `Lost connection` 和 `MySQL server has gone away`」。
>
> **手动把缓冲池限制在 1G**，就是给 Node 和 Nginx 留够呼吸空间。

## 4.4 建库和建账号

```bash
sudo mysql
```

进去之后（提示符变成 `mysql>`）执行：

```sql
-- 建库：字符集必须是 utf8mb4
-- 【为什么不能用 utf8】MySQL 里的 utf8 实际是 utf8mb3 的别名，
-- 只支持 3 字节字符，【存不了 emoji】。用户昵称里来个 👊 就会报错。
CREATE DATABASE kuile CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 建业务账号：只给 kuile 这个库的权限
-- 【为什么不用 root 跑业务】这是「最小权限原则」。
-- 万一业务代码有 SQL 注入，攻击者拿到的是 kuile 账号，
-- 只能读写 kuile 库，动不了别的库，也删不了审计流水表。
-- 一句话：让「被偷走的钥匙」只能开一扇门，而不是整栋楼。
CREATE USER 'kuile'@'localhost' IDENTIFIED BY '你的密码';

-- 授权
GRANT ALL PRIVILEGES ON kuile.* TO 'kuile'@'localhost';

-- 立即生效
FLUSH PRIVILEGES;

-- 验证
SHOW DATABASES;
SELECT user, host FROM mysql.user WHERE user = 'kuile';
```

退出：

```sql
exit;
```

> **💡 原理：`@'localhost'` 里的 host 是什么意思？**
>
> MySQL 的账号是 `(用户名, 来源主机)` 二元组 —— 同名用户可以有好几个，
> 分别对应「从哪来的连接」。
> `kuile@localhost` 表示「只接受来自**本机 socket 连接**的 kuile」。
>
> 如果你写 `kuile@'%'`，意思是「**任何来源**的 kuile 都能用这个密码连」。
> 在自建 + 只监听 127.0.0.1 的前提下，`%` 也无害，
> 但**写成 `localhost` 更精确**，万一以后你改了 `bind-address`，
> 这个账号也不会自动跟着暴露出去。

## 4.5 校准时区（★ 极易踩坑，务必做）

```bash
# 1. 服务器时区设为 UTC
sudo timedatectl set-timezone UTC

# 确认
timedatectl | grep "Time zone"

# 2. MySQL 时区也设为 UTC
sudo mysql -e "SET GLOBAL time_zone = '+00:00';"
```

**并且**在 `mysqld.cnf` 的 `[mysqld]` 段加上（否则重启后失效）：

```ini
default-time-zone = '+00:00'
```

重启 MySQL 验证：

```bash
sudo systemctl restart mysql
sudo mysql -e "SELECT @@global.time_zone, NOW(), UTC_TIMESTAMP();"
```

**应该看到 `+00:00`，且 `NOW()` 和 `UTC_TIMESTAMP()` 完全相同。**

> **🔴 原理：为什么这一步不做会「结算日期算错一天」？**
>
> 这是一个非常隐蔽的坑，展开讲：
>
> **代码里两种时间来源是混用的：**
> - JavaScript 侧：`db.js` 里配了 `timezone: 'Z'`，
>   意味着 JS 的 `Date` 对象**一律按 UTC 解释**。
>   代码里所有「当前时间」都是 UTC 字符串。
> - SQL 侧：像 [flagService.js](../../正式上线版/02-后端/src/services/flagService.js) 里的
>   `NOW()`、`DEFAULT CURRENT_TIMESTAMP`，用的是 **MySQL 服务器的本地时区**。
>
> **如果不统一会怎样？**
> 假设服务器时区是 `Asia/Shanghai`（UTC+8）：
> - 定时任务里 `WHERE prep_end_at <= NOW()` —— `NOW()` 返回北京时间
> - 而 `prep_end_at` 是 JS 传进来的 **UTC** 字符串
>
> **两者差 8 小时！** 结果是「筹备期结束」这件事会**提前 8 小时**触发，
> 而「结束日结算」会**延迟 8 小时** —— 也就是**结算日期整体偏移了一天**。
>
> **用户看到的表现**：凌晨 0 点没打卡，但系统第二天早上才判断卡；
> 或者说好 30 天的 Flag，第 29 天晚上就结算了。
>
> **💡 为什么托管版也有这个坑？**
> 云数据库的时区取决于你选的区域，**同样可能和你服务器不一致**。
> 自建并不新增风险 —— 但自建你有完全的控制权，**更容易做对**。
> 这一步做完，两个系统就统一在 UTC 上了。

```

> **💡 这一节只填「数据库」相关的字段。**
> 其余密钥（微信、COS、豆包、支付）分别在第 1、5、6、7 章拿到，
> 统一在 [8.2 补齐 .env 其余字段](#82-补齐-env-其余字段) 填。

DB_USER=kuile
DB_PASSWORD=你在 4.4 步设的密码
DB_POOL_SIZE=10
```

验证连接（**在服务器上直接跑**）：

```bash
cd /var/www/kuile/正式上线版/02-后端
node -e "
const c = require('./src/config');
const mysql = require('mysql2/promise');
(async()=>{const conn=await mysql.createConnection({host:c.db.host,port:c.db.port,user:c.db.user,password:c.db.password,database:c.db.database});
const [r]=await conn.query('SELECT NOW() AS now, @@global.time_zone AS tz');
console.log(r); await conn.end();})();
"
```

**应该输出 `now` 和 `UTC_TIMESTAMP()` 一致的结果。**

- [ ] `.env` 权限设好：`chmod 600 .env`

> **💡 原理：为什么 `DB_HOST` 填 `127.0.0.1` 而不是内网地址？**
>
> 因为**数据库和 Node 进程在同一台机器上**。
> `127.0.0.1` 走的是**回环接口（loopback）** —— 数据根本不出网卡，
> 是操作系统内核直接内存拷贝，延迟是**微秒级**。
>
> 而「内网地址」要走真实的网卡和交换机，延迟高得多，还占用带宽。
>
> **还有一层安全含义**：`127.0.0.1` 明确表达了「只有本机能连」，
> 即使有人误改了 `bind-address`，这个配置也是一道防线。

### ④ 恢复演练（★ 这是最容易被跳过、也最重要的一步）

> **💡 原理：为什么「没验证过的备份等于没有备份」？**
>
> **备份和恢复是两套逻辑。** 备份只管「把数据复制出去」，
> 恢复时才管「复制出来的东西能不能用」。
>
> 真实案例：某公司自动备份每天跑、状态全绿，
> 真出事时恢复才发现 —— 备份文件是空的、格式不兼容、中间缺了关键几天的数据。
>
> **每季度做一次演练**：拿一份备份恢复到临时实例，跑几个查询确认数据完整。

**在一台临时机器（或本地）上验证：**

```bash
# 1. 下载备份
gunzip -c kuile-20261127-031722.sql.gz > /tmp/test.sql

# 2. 导进一个测试库（不要导进生产库！）
mysql -u root -p -e "CREATE DATABASE kuile_restore_test;"
mysql -u root -p kuile_restore_test < /tmp/test.sql

# 3. 抽查数据
mysql -u root -p kuile_restore_test -e "SELECT COUNT(*) FROM user;"
mysql -u root -p kuile_restore_test -e "SELECT COUNT(*) FROM flag;"
mysql -u root -p kuile_restore_test -e "SELECT COUNT(*) FROM deposit_ledger;"

# 4. 确认 24 张表都在
mysql -u root -p kuile_restore_test -e "SHOW TABLES;" | wc -l

# 5. 演练完删掉测试库
mysql -u root -p -e "DROP DATABASE kuile_restore_test;"
```

- [ ] 表数量是 24
- [ ] `user` / `flag` / `deposit_ledger` 的行数和线上对得上
- [ ] 演练完成后已删除测试库

> **💡 原理：为什么备份必须存到「异地」？**
>
> 自建 MySQL 的数据就在这台服务器的硬盘上。
> 如果备份也只存在这台机器上，那「盘坏了」= 数据和备份一起没了 = **备份白做**。
>
> 所以备份必须多存一份到别的地方 —— 这里用 **COS**（你已经有 COS 了，顺手）。
> COS 在腾讯云的存储集群上，和你的服务器是**物理隔离**的，
> 服务器整机损坏也不会影响它。

> **💡 原理：`mysqldump` 到底做了什么？**
>
> 它**不是复制二进制文件**，而是把数据翻译成一系列 SQL 语句
> （`CREATE TABLE` + 一串 `INSERT INTO`）。
>
> 好处：可读、可跨版本、可以只导部分表、恢复时不会因版本差异出问题。
> 缺点：数据量大时慢（而且导出期间若有写入，可能导出到「半个事务」的状态）。
>
> **本项目数据量小（内测期几十条），速度完全不是问题。**
>
> **💡 原理：`--single-transaction` 这个参数为什么重要？**
> InnoDB 引擎下，这个参数会用一个**一致性快照**导出，
> **不会锁表**，导出期间线上照常读写。对生产库非常重要。
> 不加的话，`mysqldump` 默认会锁表 —— 你导出一次，全站就卡住了。

### ⑤ 日常巡检

- [ ] 每周看一眼备份有没有成功：`ls -lh /var/backups/kuile/`
- [ ] 每月看一眼磁盘还剩多少：`df -h`
- [ ] 每季度做一次恢复演练

> **💡 原理：磁盘满了会导致什么后果？**
> **MySQL 写不进去** —— 数据库依赖磁盘持久化。
> 磁盘满 → 写入报错 → 服务大面积 500。这是「一个资源耗尽导致全站故障」的典型案例。
>
> **哪样东西最容易吃满磁盘？** 一般是**日志**。
> PM2 的日志不自动清理，跑几个月能到几个 GB。
> 根治办法是装 `pm2-logrotate-daily`（按天切割 + 定期清理）。

## 4.9 常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| `ERROR 2003 (Can't connect)` | MySQL 没启动 | `sudo systemctl start mysql` |
| `ERROR 1045 (Access denied)` | 密码错，或账号的 host 不匹配 | 核对 `.env` 的 `DB_PASSWORD`；`SHOW USER` 查 host |
| `Unknown database 'kuile'` | 库没建 | 回 4.4 步执行 `CREATE DATABASE` |
| `ER_NOT_SUPPORTED_AUTH_MODE` | 账号用的是 `caching_sha2_password`，老客户端不支持 | `ALTER USER 'kuile'@'localhost' IDENTIFIED WITH mysql_native_password BY '你的密码';` |
| 服务时好时坏、日志有 `server has gone away` | 内存不足，MySQL 被 OOM Killer 杀了 | 做 4.3 步的内存调优 |
| 结算日期整体差一天 | 时区不统一 | 做 4.5 步 |

> **💡 `ER_NOT_SUPPORTED_AUTH_MODE` 是自建 MySQL 8.0 最常踩的一个坑。**
>
> MySQL 8.0 默认的认证插件是 `caching_sha2_password`（更安全），
> 但如果你的 `mysql2` 驱动版本较老或某些工具不支持，就会报这个错。
>
> **解决**：把账号改用老插件 `mysql_native_password`：
> ```sql
> ALTER USER 'kuile'@'localhost' IDENTIFIED WITH mysql_native_password BY '你的密码';
> FLUSH PRIVILEGES;
> ```

# 第 5 章：对象存储（图片存哪儿）

打卡照片不能存服务器（占带宽、占磁盘、重装就没了），要存在**对象存储**里。

## 5.1 开通 COS

- [ ] 腾讯云控制台 → 搜索「对象存储 COS」
- [ ] 新建存储桶：
  - 名称：`kuile-prod-1250000000`（**唯一，全网不能重名**，后面改成你自己的）
  - 所属地域：和服务器一致
  - 访问权限：**「私有读写」**（更安全，我们后端签名访问）
  - 版本控制：关闭
  - 服务端加密：开启

> **💡 原理：什么是「对象存储」，和「文件服务器」差在哪？**
>
> 传统文件服务器是**给一台机器挂一块硬盘**，然后用「路径」访问：`/photos/2026/11/a.jpg`。
> 它的前提是**必须有一台长期在线的机器扛着这个盘**。
>
> 对象存储（COS / S3 / OSS）是把文件拆成一个个「对象」放在**分布式的存储集群**里，
> 你通过 API 拿着「桶名 + 对象名」去取。特点：
>
> - **不用管机器**：桶是一直存在的，重装服务器、换服务器，照片都还在
> - **容量无上限**：加个桶就多几十 TB
> - **便宜**：比云硬盘便宜一个量级
> - **能抗并发**：几千个人同时下载同一张照片没问题
>
> **本项目的照片是「打卡证据」，是要长期留存的** ——
> 用户可能几个月后翻出来申诉「我明明达标了」。用服务器磁盘的话，
> 一次重装全没了；用 COS 就是长期可靠保存。
>
> **💡 为什么桶名要全网唯一？**
> 因为 COS 的访问 URL 里包含桶名：`https://kuile-prod-1250000000.cos.ap-guangzhou.myqcloud.com/xxx.jpg`。
> 这个 URL 是**全球公开的寻址方式**，桶名重复会导致 URL 冲突。
> 所以桶名必须全网唯一 —— 这也是为什么它长得像「kuile-prod-你的APPID」。

## 5.2 拿密钥

- [ ] 腾讯云控制台 → 访问管理 → API 密钥管理
- [ ] 「新建密钥」
- [ ] 记下：
  - `SecretId`（AKID 开头的长字符串）
  - `SecretKey`（32 位）
- [ ] ⚠️ **这个密钥是账号最高权限，立刻存好。丢了只能重建，重建后所有旧密钥失效。**

> **💡 原理：SecretId / SecretKey 是什么？**
>
> 它们是**云厂商给程序用的「账号密码」**，用来证明「这个请求确实是我发的」。
> 机制是**签名的，不是明文传密码**：
>
> 1. 程序把请求内容（路径、参数、时间戳）拼成一段字符串
> 2. 用 SecretKey 做一次加密运算（HMAC），得出一个 `signature`
> 3. 把 `SecretId`（公开的编号）+ `signature`（签名）一起发出去
> 4. 云厂商用自己存的 SecretKey 重算一遍签名，对得上才放行
>
> **SecretKey 全程不出现在网络请求里** —— 就算全程被抓包，攻击者也拿不到密钥本身。
> 这比「用户名密码明文 POST」安全得多，是所有云 API 的标准做法。
>
> **🔴 为什么说它是「账号最高权限」？**
> 因为云 API 密钥通常**不区分细粒度权限** —— 拿到它基本等于拿到整个腾讯云账号的操作能力。
> 所以：
>
> - 绝不能提交进 Git（`.env` 必须在 `.gitignore` 里）
> - 绝不能贴到聊天窗口 / 截图
> - 如果怀疑泄露，**立刻在控制台禁用并重建**（重建后旧的立刻失效）
> - 更安全的做法是用**子账号 + 最小权限**（只给 COS 相关权限），主账号密钥根本不落到你的代码里

### 填进 .env

| 配置项 | 值 |
|---|---|
| `COS_REGION` | 你选的地域，如 `ap-guangzhou` |
| `COS_BUCKET` | 你的存储桶名 |
| `COS_SECRET_ID` | 刚拿的 SecretId |
| `COS_SECRET_KEY` | 刚拿的 SecretKey |
| `COS_CDN_URL` | `https://你的桶名.cos.你的地域.myqcloud.com` |

## 5.3 配置访问权限（图片要能被前端显示）

打卡照片是**公开的**（这是产品设计：大家要能看到打卡证据）。

- [ ] 存储桶 → 「权限管理」→「存储桶访问权限」→ 选择「公有读私有写」
- [ ] 「安全策略」→ 删除所有默认 deny 规则，添加：
  ```json
  {
    "version": "2.0",
    "statement": [
      {
        "effect": "allow",
        "principal": { "qcs": ["qcs::cam::anyone:anyone"] },
        "action": ["cos:GetObject"],
        "resource": ["qcs::cos:ap-guangzhou:1250000000:kuile-prod-1250000000/*"]
      }
    ]
  }
  ```

> **💡 原理：「公有读私有写」到底是什么意思？**
> 桶的访问权限分三档：
>
> | 权限 | 谁能读 | 谁能写/删 | 用在哪 |
> |---|---|---|---|
> | 私有读写 | 只有你（且要有密钥） | 只有你 | 存身份证照片、合同等敏感材料 |
> | 公有读私有写 | **任何人**（有 URL 就能看） | 只有你 | **本项目的打卡照片** |
> | 公有读写 | 任何人 | 任何人 | ❌ 绝对不要，等于对全网开放 |
>
> **为什么打卡照片可以公开读？**
> 因为它就是「公开的证据」—— 见证人要看、围观用户要看、AI 要能下载。
> 让前端直接读 COS 的好处是：**照片流量完全不过你的服务器**，不占服务器带宽、不占 Node 进程。
>
> **「有 URL 就能看」不代表「会被搜到」** ——
> 公开读只是「不鉴权即可访问这个确定的地址」，文件不会出现在搜索引擎里，
> 而且 URL 里有随机成分，不容易被遍历。
>
> **💡 但注意 AI 判定这一环**：AI 模型要能下载到你的照片，
> 所以桶必须是 AI 服务器能访问到的。本项目用「公有读」正好满足。
>
> **⚠️ 合规提醒**：虽然照片可以公开，但**照片本身可能拍到不该公开的东西**
> （比如家里的背景、桌上的其他物品）。第 9.5 节的隐私指引、第 11.2 节的审核风险都提到这一点。
> 产品层面要考虑在打卡页提示「请只拍体重秤和手写词」。

> **📌 说明**：本项目的 COS 上传走的是**服务端签名**（后端签好再传），
> 所以上面的「公有读」主要是为了前端能直接显示图片。
> 如果你想更严格，可以让前端也走后端代理取图 —— 但那要多一次服务器转发，图片多了会慢。

# 第 6 章：豆包 AI 模型

本项目用豆包（火山方舟）的**视觉模型**做打卡照片判定：读秤面读数、读手写词、判照片质量。

## 6.1 开通火山方舟

- [ ] 打开 <https://console.volcengine.com/ark>
- [ ] 用手机号注册并**实名认证**（个人认证即可）
- [ ] 开通「方舟大模型」服务（免费额度足够前期用）

> **💡 原理：为什么选豆包（火山方舟）而不是 OpenAI / Claude？**
> 三个现实原因：
> ① **合规与网络**：国内服务器访问国外模型 API 需要「翻墙」，不稳定且有法律风险。
>    国内云厂商的模型 API 是境内合规的。
> ② **延迟**：国内调用国内模型，延迟通常 200-500ms；调境外可能 2-5 秒。
>    本项目打卡时要等 AI 判定结果，延迟直接影响体验。
> ③ **成本与合规备案**：境内模型服务的商用有明确的资质路径，也更容易做数据不出境。
>
> **💡 什么是「视觉模型 / 多模态」？**
> 最早的 AI 只能处理文字（读文本、生成文本）。
> 「多模态」模型能**同时理解多种信息形式** —— 比如「图 + 文字」。
> 本项目需要 AI 看一张打卡照片，回答：
>
> - 体重秤上显示的数字是多少？（OCR 能力）
> - 手写纸上写的是什么字？（手写识别，比 OCR 难）
> - 这张照片是不是正常拍的（不是风景照、不是截图、不是修过的）？
>
> 这三件事都是「看图说话」，只有视觉模型能做。

## 6.2 创建 API Key

- [ ] 左侧「API Key 管理」→「创建 API Key」
- [ ] 复制保存（**只显示一次**）

> **💡 原理：API Key 是什么？**
> 平台发给你的一串随机字符，等于**你自己的账号钥匙**。
> 每次调模型接口都要在请求头里带上它，平台靠它判断「这个请求有没有付费配额、算在谁头上」。
>
> **它和第 5.2 节的 COS 密钥是同一个模式**（标识 + 签名），但用途不同：
> COS 密钥证明「我是这个云账号的主人」，AI 的 API Key 证明「我有权调用这个模型」。
>
> **⚠️ 只显示一次**：这跟密码管理器一个道理 —— 平台不保存你的明文密钥，
> 只存它的哈希值。所以丢了只能重建，没有找回。

## 6.3 开通视觉模型

- [ ] 左侧「开通管理」→ 搜索 `doubao-1-5-vision` → 开通
- [ ] 「开通管理」→ 找到 `doubao-1-5-vision-pro-250528` → 点「查看」
- [ ] 选「开通 Endpoint（接入点）」→ 名字随便填（如 `kuile-checkin`）
- [ ] 创建后复制 **Endpoint ID**（形如 `ep-20250101000000-xxxxx`）

### 填进 .env

| 配置项 | 值 |
|---|---|
| `ARK_API_KEY` | 第 6.2 步的 API Key |
| `ARK_ENDPOINT_ID` | 第 6.3 步的 Endpoint ID |
| `ARK_MODEL` | `doubao-1-5-vision-pro-250528` |
| `AI_VERIFY_ENABLED` | `true`（先用 `false` 测试通了再开） |

> **💡 原理：什么是「Endpoint（接入点）」？为什么要它，不要直接用模型名？**
>
> **Endpoint 是一个「指向某个具体模型部署资源的固定地址」**。
> 类比：模型是「一款产品」，Endpoint 是「你在某个仓库存的那一批货的货架号」。
>
> **为什么必须用 Endpoint 而不是模型名？**
> ① **模型名会变**：模型升级是常规操作（比如 `1-5-vision` 升到 `1-6-vision`）。
>    如果你直接写模型名，某天模型一升级，你的提示词调优、参数、输出格式可能全部要重来。
>    用 Endpoint 就把「用哪个版本」这个决定**冻结在配置里**，将来换版本只改一行 `.env`，
>    代码和调优成果都不用动。
> ② **多版本共存**：你可以同时开两个 Endpoint（老版跑存量、新版跑测试），
>    灰度对比效果再切。
> ③ **配额与计费独立**：每个 Endpoint 有自己的配额，用量能分开统计。
>
> **本项目为什么特别需要它？** 因为我们要求「提示词版本化 + 判定可追溯」
> （第 6.4 节）。判定结果要能还原「当时是用哪个模型、哪版提示词判的」，
> Endpoint ID + 提示词版本号就是这件事的锚点。

## 6.4 ⚠️ 关于 AI 判定的产品决策（重要）

**本项目的设计是：AI 只做初筛，不直接定生死。**

| AI 判定 | 系统怎么处理 |
|---|---|
| 通过 (pass) | 打卡成功 |
| 存疑 (doubt) | 转人工复核，**不惩罚用户** |
| 驳回 (rejected) | 转人工复核队列，**不直接判负** |

**为什么这样设计？**

- AI 会看错（光照、角度、秤的型号都会影响识别）
- 如果 AI 驳回就直接判负，用户会大量投诉
- 但也不能完全不审核，否则会有人用别人的照片打卡

> **💡 原理：为什么「AI 初筛 + 人工兜底」是正解？**
>
> 这是**自动化系统设计的通用原则**，叫「**人在回路（Human in the Loop）**」。
>
> 核心思路是：**按「误判代价」来分配决策权**。
>
> - 误判代价**高**（判错要扣钱、封号）→ 必须人工终审
> - 误判代价**低**（只是多一次复核）→ 可以让 AI 先做，把 90% 的常规情况消化掉
>
> 本项目里，AI 判「通过」的绝大多数情况（用户老老实实打卡）不需要人工介入，
> 效率高；AI 判「存疑 / 驳回」的比例很低（可能只有 1-5%），
> 人工只需要处理这一小撮，**成本可控**。
>
> 如果反过来让 AI 全权决定：一旦它把正常打卡判成驳回，用户直接被扣分扣押金，
> 投诉量会瞬间压垮客服，而且微信审核也会质疑「凭什么机器说了算」。
>
> **💡 留痕为什么是合规刚需？**
> 半年后用户来申诉「凭什么判我作弊」，你必须能回答：
> 「当时的照片是什么样子、AI 怎么判的、用的哪版提示词、耗时多少」。
> 所以 `ai_review` 表必须存**模型原始返回**（JSON，不能只存结论）+ `prompt_version`。
> 只存结论的话，等于把证据扔了 —— 出了事无法自证。

**你要做的事：**

- [ ] 上线初期把 `AI_VERIFY_ENABLED` 设成 `false`，先人工看几天
- [ ] 观察 AI 的判定准确率（后台 `ai_review` 表能查）
- [ ] 准确率稳定后再改成 `true`
- [ ] **准备一个人工复核的通道**（可以是微信群 + 人工处理 `checkin` 表里 `status='rejected'` 的记录）

> **💡 原理：为什么「上线初期先关掉 AI」是个聪明做法？**
>
> 1. **攒样本**：关掉 AI，你的 `ai_review` 表就记录不了判定结果了 ——
>
>    所以更准确的做法是：开 AI 但**保留人工全量复核**，攒够 500+ 条带人工标签的数据，
>     再用这批数据算 AI 的准确率（准确率 = AI 判对的数量 / 总数）。
>
> 50 条样本得出的准确率误差极大，500 条才有统计意义。
> 2. **避免第一印象伤害**：上线第一天就因为 AI 误判把一个真实用户判负，
>    这个用户会立刻发朋友圈骂你 —— 冷启动阶段最怕的就是这种口碑事故。
> 3. **摸清模型边界**：不同体重秤型号、光线环境、手机型号的识别难度不一样，
>    先人工看看哪些场景模型容易错，再决定要不要调提示词。

# 第 7 章：微信支付（押金）

> **这是整个项目最关键、也最容易卡住的一章。**
> 押金功能做不了，产品核心价值（失败扣钱）就没有了。
> **建议：拿到营业执照当天就来做这一章。**

> **💡 先理解一件事：押金在这个产品里到底扮演什么角色？**
>
> 很多人以为押金是「收入」。不是 —— 它是**履约保证金**。
>
> 想象一个场景：用户立了个「30 天减 5 公斤」的 Flag，说押 500 块。
>
> - 达标了 → 500 块**一分不少**退给他
> - 没达标 → 按规则扣一部分（比如 30% = 150 块），350 块退回
>
> **这个机制的作用是「让承诺有成本」**。
> 如果不收押金，一个用户可以立 100 个 Flag 只挑有把握的做，
> 打卡记录就变成了一堆「只晒 successes」的营销素材 —— **数据全污染了**。
> 押金让「立了就要做完」这件事有了真实的代价，
> 所以打卡记录才有可信度，见证席的判定才有意义。
>
> 这也解释了产品规则里为什么写着「**押金不是平台收入**」「**不能分给见证人**」——
> 因为它从设计上就不是「赚来的钱」，是「暂存的履约保证金」。
> 这条红线不是道德要求，是**产品逻辑的必然**：一旦平台能拿押金赚钱，
> 平台就有动机去鼓励用户失败，整个产品就变成了赌博。

## 7.1 前置条件检查

- [ ] 营业执照已办好
- [ ] 已完成微信小程序**企业认证**（300 元）
- [ ] 有对公银行账户（**个体工商户也可以用法人个人卡，但要确认微信支付支持**）

> **💡 原理：微信支付是「四要素绑定」的体系**
>
> 要让「用户在小程序里付钱 → 钱进你的账户」跑通，微信需要知道四件事：
>
> | 要素 | 是谁 | 在本项目里 |
> |---|---|---|
> | **谁在收钱** | 商户号 `mch_id` | 你的营业执照主体 |
> | **钱付给谁** | 商户号绑定的结算银行账户 | 对公账户 / 个体户法人卡 |
> | **在哪个小程序里收** | 商户号绑定的 AppID | 你的小程序 |
> | **谁来操作** | 操作员（你的微信） | 商户平台管理员 |
>
> **四个要素缺一个都收不了钱**，而且微信的校验很严：
> 比如「商户号绑定的 AppID」必须是**同一个主体**下的小程序 ——
> 用个人主体的 AppID 去绑企业主体的商户号，会直接被拒。
>
> 这也是为什么「营业执照」是一切的前提：它是这四个要素能互相对上的**根**。

## 7.2 申请商户号

- [ ] 打开 <https://pay.weixin.qq.com/>
- [ ] 点「注册商户号」
- [ ] 选主体类型 → 填营业执照信息
- [ ] 填结算银行账户（对公账户，或个体户的法人银行卡）
- [ ] 签署协议
- [ ] 审核：**1-3 个工作日**

**审核通过后你会拿到：**

- **商户号 (mch_id)**：形如 `1900000000`
- 需要**绑定小程序 appid**（在商户平台的「产品中心」→「AppID 授权管理」里绑定）

> **💡 原理：商户号是什么？为什么不直接用小程序 AppID 收款？**
>
> **AppID 是「小程序这个应用」的身份，商户号是「收钱这个主体」的身份 —— 两者是不同的概念。**
>
> 想象一家公司开了 10 个小程序，可能还想做 App、公众号、网页。
> 商户号是「公司这个收款账户」，AppID 只是「一个收款入口」。
> 一个商户号可以绑多个 AppID，**钱统一进这个商户号的结算账户**。
>
> **所以「商户号」才是你真正的「收银台编号」**，所有支付、退款、对账都以它为准。
> 这也是为什么第 12 章的合规红线强调「押金逐用户独立记账」——
> 钱进了一个池子，但账必须按人分开记（`deposit_ledger` 表就是干这个的）。

## 7.3 申请 API 权限（关键！）

> ⚠️ **新手最容易漏的一步**：光有商户号没用，得单独开通 API 权限。

- [ ] 商户平台 →「产品中心」→「AppID 授权管理」→ 绑定你的小程序 appid
- [ ] 「产品中心」→「产品设置」/「开发配置」→ 找到 **「API 权限」**（也叫「支付接口权限」）
- [ ] 申请开通：
  - ☑ **JSAPI 支付**（小程序用的就是这个）
  - ☑ **退款接口**（押金要退，必须开！）
  - ☑ **订单查询接口**（对账用）
- [ ] 等待开通（即时或 1 个工作日）

> **💡 原理：什么是 JSAPI 支付？它和「扫码支付」「H5 支付」的区别？**
>
> 微信支付按「用户在哪个场景付钱」分成好几种产品：
>
> | 产品 | 用户怎么付 | 用在哪 |
> |---|---|---|
> | **JSAPI 支付** | 在微信里点一下直接扣款 | **小程序内支付（就是本项目）** |
> | 扫码支付 | 扫商家的二维码 | 线下门店 |
> | H5 支付 | 在浏览器里 | 非微信内的网页 |
> | Native 支付 | 商家系统生成二维码 | 电脑端扫码 |
>
> **本项目必须用 JSAPI**，因为用户是在小程序里点「确认并支付」，
> 体验是「一键扣款」，连密码都不用输（因为微信已经登录并绑定了支付方式）。
>
> **💡 为什么「退款接口」必须一起开？**
> 这是很多人踩坑的地方 —— 只开了「支付」没开「退款」，结果是：
> 用户付了 500 块，你达标了要退钱，**调退款接口直接报错「无权限」**。
> 而这时候钱已经收了，你退不掉 —— 这是**已经发生的用户资金损失**，不是「以后再说」。
> 所以开权限时，**支付、退款、查询三个必须一起开**。
>
> **💡 为什么还需要「订单查询接口」？**
> 微信支付完成会**主动回调**你的服务器（`notify_url`），这是主路径。
> 但回调**可能丢**（网络抖动、你的服务当时正好在重启、微信重试次数用尽）。
> 所以必须有「主动查询」作为兜底 —— 主动问微信「这笔订单到底成没成」。
> 本项目在 `GET /api/pay/order/:orderId` 里就是这么做的，
> 查到的状态是 SUCCESS 但本地还没处理，就立刻补上处理（详见附录 B.3）。

## 7.4 生成 API 密钥

- [ ] 商户平台 →「账户中心」→「API 密钥」
- [ ] 设置 **APIv3 密钥**（32 位，只显示一次，**立刻保存**）
  - ⚠️ 这个密钥用来给回调报文解密，**填错会导致微信支付回调永远验签失败**
- [ ] 设置 **API 证书**（用商户平台下载的证书工具生成）
  - 工具下载：<https://kf.qq.com/faq/120911VrYVrA20200908NJXqP.html>
  - 生成后会得到 `apiclient_key.pem`（**这个就是你的商户私钥**）
  - 同时会显示 **证书序列号**（Serial Number）

### 填进 .env

| 配置项 | 值 | 在哪拿 |
|---|---|---|
| `WECHAT_PAY_MCH_ID` | 商户号 | 商户平台首页 |
| `WECHAT_PAY_API_V3_KEY` | APIv3 密钥 | 账户中心 → API 密钥 |
| `WECHAT_PAY_SERIAL_NO` | 证书序列号 | 生成证书时显示 |
| `WECHAT_PAY_PRIVATE_KEY` | 私钥内容 | `apiclient_key.pem` 文件的全部内容 |
| `WECHAT_PAY_NOTIFY_URL` | `https://api.你的域名/api/pay/notify` | 你自己填 |

> **💡 原理：微信支付 APIv3 的「三把钥匙」分别管什么？**
>
> 微信支付 APIv3 用了一套**非对称加密 + 对称加密结合**的方案，三个要素各管一段：
>
> | 要素 | 类型 | 作用 | 对称的东西 |
> |---|---|---|---|
> | **商户私钥**（`apiclient_key.pem`） | 非对称（RSA） | 给**你发出去的请求**签名 | — |
> | **商户证书序列号** | 标识 | 告诉微信「用哪把公钥验我的签」 | — |
> | **平台证书** | 非对称 | 验**微信发回来的报文**签名 | — |
> | **APIv3 密钥** | 对称（AES-256-GCM） | — | **加密回调报文里的敏感数据** |
>
> **拆开说这两层**：
>
> **① 签名层（防伪造）**
> 你要给微信发「退款请求」，得证明「这确实是我发的」，不然任何人都能用你的商户号退款。
> 做法：用你的**私钥**给请求内容算一个签名，微信用你的**公钥**验证。
> 私钥永远不离开你的服务器。
>
> **② 加密层（防偷看）**
> 微信回调给你的报文里包含用户姓名、openid 等敏感数据。
> 这部分用 **APIv3 密钥对称加密**（同一个密钥加密解密）。
> 密钥在双方之间约定好，只有你和微信知道。
>
> **🔴 为什么 APIv3 密钥填错就「永远验签失败」？**
> 因为解密失败 → 拿不到明文 → 没法算签名 → 校验必然不通过。
> 表现是：微信回调返回 500，日志里报「解密失败」或「验签失败」。
> **排查口诀见附录 B.3**。

> **💡 关于私钥怎么填**：
> `.env` 里换行会出问题。最简单的办法是**把私钥存成文件**：
>
> ```bash
> # 在服务器上
> mkdir -p /var/www/kuile/正式上线版/02-后端/certs
> # 然后把 apiclient_key.pem 上传到这个目录
> ```
>
> 然后 `.env` 里填 `WECHAT_PAY_PRIVATE_KEY_PATH=./certs/apiclient_key.pem`
>
> **为什么存成文件更好？**
> ① **不会被换行搞坏** —— `.env` 是「一行一个 KEY=VALUE」的格式，
>    多行内容塞进去必然出问题（要么被截断，要么解析失败）。
> ② **更好管理** —— 私钥可以单独设权限（`chmod 600`），还能单独轮换。
> ③ **不会被日志误打** —— 私钥内容打印到日志里就是重大安全事故。

## 7.5 配置支付回调地址

- [ ] 商户平台 →「产品中心」→「开发配置」→「支付回调地址」
- [ ] 填：`https://api.你的域名/api/pay/notify`
- [ ] ⚠️ 这个地址**必须能被公网访问**，而且要能在 5 秒内响应

> **💡 原理：什么是「支付回调（notify_url）」？为什么必须要有它？**
>
> **问题在于：用户付款这个动作，发生在微信的服务器上，你的服务器根本不知道。**
>
> 想象没有回调的世界：
>
> 1. 用户在你的小程序里点了「确认并支付」
> 2. 微信弹窗，用户输入密码，**钱扣了**
> 3. 这一步全部发生在**微信的服务器**里，你的服务器全程不知情
> 4. 如果不通知你，你的数据库里这局还是「未支付」状态 —— 用户付了钱却看不到 Flag 生效
>
> **回调就是微信主动来敲你的门**：「订单 KL2026xxx 已支付成功，金额 500 元，请处理。」
> 微信会 **POST** 到你配的 `notify_url`，你回一个 `{"code":"SUCCESS"}` 表示「收到了，处理好了」。
>
> **💡 为什么强调「5 秒内响应」？**
> 微信的回调机制是：**超时 → 重试**（会重推多次，最多 15 次，间隔递增）。
> 如果你的服务器处理太慢（数据库慢、代码有 bug），微信会以为是「没收到」，
> 于是不停重推。这带来两个问题：
> ① 你的服务器被反复打（雪崩风险）
> ② **更危险**：如果你的回调处理逻辑不幂等，重复处理会导致**重复加钱、重复退款**。
>
> 本项目的做法是：回调里**只做记账**（改订单状态、写押金流水、更新 Flag），
> 尽量控制在 100ms 内返回，重活儿（比如结算）交给别的地方做。
> 这就是附录 A 里「幂等」这个词的实际含义 —— **同一笔回调推 15 次，结果和推 1 次一样**。

## 7.6 ⚠️ 押金功能的三条前置条件（产品规则，不能跳过）

我们的产品规则明确要求，**押金功能要在这三件事都完成之后才开放**：

- [ ] **① 推送已上线** —— 用户必须能收到「断卡了」「结算了」的通知，否则没人知道发生了什么
  - 推荐：腾讯云 TPNS（移动推送）或直接用微信订阅消息
  - 简易方案：用微信「订阅消息」发通知（小程序原生能力，不需要额外服务）
- [ ] **② 退款流程已跑通并压测** —— 必须实测「3 个工作日内到账」
  - [ ] 用 ¥0.01 元或小额真实支付一次
  - [ ] 手动发起退款，确认到账
  - [ ] 记录实际到账时间
- [ ] **③ 客服 SLA 已就位** —— 升级投诉率红线 0.05%
  - 准备一个客服微信 / 客服邮箱 / 反馈表单
  - 定义响应时限（如 24 小时内响应）

> **💡 原理：为什么押金上线有「前置条件」？**
>
> 这三条不是流程上的繁琐规定，而是**因为收押金意味着你开始对用户的真金白银负责**。
>
> **① 推送为什么是前提？**
> 押金模式下用户是「有代价地参与」的。没有通知，
> 用户不知道自己的 Flag 断了、不知道钱被扣了 —— 他会在某天莫名其妙发现余额少了。
> **主动扣用户钱却不告知，是最容易引发投诉和举报的行为。**
>
> **② 退款为什么必须实测？**
> 「代码写好了」不等于「钱能退回来」。退款是**反向的、异步的、多系统协作**的流程：
> 你的服务器 → 微信支付 → 微信 → 银行 → 用户账户。
> 每一环都可能出问题（证书过期、金额算错、订单状态不对）。
> **没实测过的退款流程 = 没验证过的承诺。**
> 而且微信的退款是**异步**的：接口返回「已受理」，钱实际到账要等银行处理（通常几分钟到 3 个工作日）。
> 你必须知道真实的到账时间，才能对客服承诺「3 个工作日内」。
>
> **③ 客服为什么是前提？**
> 收押金 = 必然有「为什么扣我钱」「为什么没退我钱」的咨询。
> 产品规则定的是**咨询率 < 1%、升级投诉率 < 0.05%** ——
> 意思是一万个人里，最多 5 个会闹到要监管/媒体介入。
> 要达到这个数，你得有能力在 24 小时内响应每一个咨询。
> 没有客服 = 投诉直接落到差评和监管投诉，**成本远高于提前准备的客服成本**。

> **💡 实操建议**：**本次正式上线采用「内测阶段暂不收取押金」的方式**
> （详见第 7.7 节），等推送和退款都验证好了，再打开押金支付。
> 这样能提前 2 周上线，且完全合规。

### 7.7.2 怎么配置

**只需在** `.env` **里改一行：**

```ini
# 内测阶段保持 false
DEPOSIT_ENABLED=false
```

改完**重启服务**才生效：

```bash
cd /var/www/kuile/正式上线版/02-后端
pm2 restart kuile-api
```

**验证生效：**

```bash
curl https://api.你的域名/api/health
```

返回的 JSON 里应该有：

```json
{ "code": 0, "data": { "depositEnabled": false } }
```

`depositEnabled: false` 就对了。

> **💡 原理：为什么用「配置开关」而不是「直接删掉支付代码」？**
>
> 开关的价值在于**「改一行配置就能切回去」**。
> 如果为了内测把支付逻辑删了，正式上线时就要重新写一遍 —— 容易出错，还来不及测。
> 用开关的话，正式收押金时**只改一个值 + 重启**，代码一行都不用动，
> 而且这段「内测模式」的代码路径本身也被测试覆盖着。
>
> **💡 原理：为什么「押金金额照常记录，实收记 0」？**
>
> 因为这两个数字**回答的是两个不同的问题**：
>
> | 字段 | 含义 | 内测期的值 |
> |---|---|---|
> | `deposit_amount`（名义押金） | 「这一局承诺押多少」 | **500 元**（照常记） |
> | `deposit_paid`（实收押金） | 「实际收到了多少钱」 | **0 元** |
>
> **为什么要分开记？**
> ① **内测期你需要知道「用户想押多少」** —— 这决定了档位设计合不合理、
>    信用分上限设得对不对、用户愿不愿意为这个产品付出成本。
>    如果内测期全记 0，你就完全不知道「有多少人愿意押 2000 块」这个关键信息，
>    等于白测了。
> ② **「实收」必须真实** —— 结算逻辑只认 `deposit_paid`。
>    这就保证了：内测期的局，结算时**不会扣钱、也不会退钱**，
>    因为实收是 0，那笔钱从来没进过你的账。
>
> **🔴 这条设计还顺手避免了一个严重资损事故**：
> 如果内测期把名义押金记成 2000 元、实收记 0，而结算时按「名义押金」去算退款，
> 那么等你正式上线后，一个内测期建的局结算时**会退一笔你从没收到过的钱** ——
> 直接亏钱。同理反过来，收了钱却不退则是违规。
> 所以本项目的结算**只看实收金额**，不看全局开关 —— 这样无论开关什么时候翻转，
> 「收过的钱一定退，没收过的钱绝不退」这条铁律都不会破。

> **💡 原理：为什么弹窗用** `wx.showModal` **而不是** `wx.showToast`**？**
>
> - `showToast`：几秒后自动消失，轻提示，适合「已保存」这类不需要用户确认的信息。
> - `showModal`：必须用户点一下才消失，**带明确按钮文字**，适合「需要用户知悉并做出选择」的场景。
>
> 这里选 `showModal` 的原因：
> ① **「暂不收取押金」是一条重要告知**，不能一闪而过 —— 用户可能需要截图或记住。
> ② **它解释了「为什么没让我付钱」** —— 如果只用一个一闪而过的 Toast，
>    用户会以为出了 bug（付不了钱），然后来投诉。
> ③ **「知道了」按钮给了明确的结束感**，点掉就继续走流程，不会卡住。
>
> **💡 为什么点掉之后 Flag 照样创建成功？**
> 因为「暂不收取押金」是**平台单方面免收**，不是「用户放弃支付」。
> 如果点了弹窗就不创建 Flag，用户会以为「立 Flag 失败了」，
> 然后得重新填一遍表 —— 这是很糟糕的体验。
> 正确做法：**提示 + 放行**，用户的目标正常成立。

### 7.7.4 ⚠️ 内测期必须注意的三件事

- [ ] **不要对外宣称「押金」能用** —— 内测期用户搜小程序时如果看到「押金 500 元」
  ```
  却又不用付钱，会产生困惑。建议在体验版/内测群里说明「内测期免押金」。
  ```
- [ ] **不要给内测用户承诺退款时限** —— 因为压根没收钱，也就不存在退款。
  ```
  如果有用户问「我的押金什么时候退」，回复「内测阶段未收取，无需退款」。
  ```
- [ ] **正式收押金前，先做一轮「内测局 + 正式开关」的混合测试** ——
  ```
  在 `tests/beta-deposit.test.js` 里已经覆盖了这个场景：
  内测期建的局，即使后来打开开关，结算时**不会**退一笔没收到过的钱；
  正式期建的局，即使后来关掉开关，结算时**照常**退款。
  ```

> **💡 原理：为什么正式上线前要专门测「开关中途翻转」？**
>
> 因为这是**最容易在真实运营中发生、也最难被发现的场景**：
>
> | 场景 | 如果代码写错了会怎样 |
> |---|---|
> | 内测期建了局 → 你打开了开关 → 这局才结算 | 退一笔**从没收到过**的钱 = **直接亏钱** |
> | 正式期建了局 → 你关了开关 → 这局才结算 | 收了钱不退款 = **违规 + 用户投诉** |
>
> 这两个场景在「开关一直不变」的正常测试里**根本不会暴露**。
> 所以必须专门写测试把它们构造出来。本项目已在 `tests/beta-deposit.test.js` 里覆盖。

> - 换了服务器（那就重新走 3.4）
>

## 8.2 补齐 .env 其余字段

> **💡 数据库那几行在 [4.6 填进 .env](#46-填进-env) 已经填好了。**
> 这一步把**前面各章拿到的其它密钥**补进去。

```bash
cd /var/www/kuile/正式上线版/02-后端

```

要补的字段（每个后面都有注释说明它从哪来）：

| 字段 | 来自哪一章 |
|---|---|
| `API_BASE_URL` | 第 2 章（你的正式域名） |
| `WECHAT_APPID` / `WECHAT_APPSECRET` | 第 1.1 节 |
| `COS_BUCKET` / `COS_SECRET_ID` / `COS_SECRET_KEY` / `COS_CDN_URL` | 第 5 章 |

```bash

```

> **💡 原理：**`.env` **是什么？为什么要单独一个文件？**
>
> **代码和配置必须分离。**
> 代码是「要公开的」（要进 Git、要给同事看、要能被搜到），
> 配置是「你独有的秘密」（密钥、密码、你的服务器地址）。
>
> 如果密钥写死在代码里，会出三个问题：
> ① 代码一开源，密钥就公开了
> ② 换服务器要改代码 → 改完得重新部署
> ③ 开发、测试、生产三套环境要用不同密钥，代码没法同时跑三套
>
> `.env` **就是「一个 KEY=VALUE 一行的纯文本配置表」**，程序启动时读它。
> 本项目**没有引入 dotenv 依赖**，而是在 `src/config.js` 里手写了 20 行解析代码 ——
> 少一个第三方包就少一份供应链风险，也少一份「这包怎么装的」的困惑。
>
> **💡 为什么** `chmod 600`**？**
> `chmod` = change mode（改权限）。`600` 表示：
> **属主（root）可读可写，其他人（组和其他用户）零权限**。
> 服务器上可能有多个运维账号、甚至有第三方运维工具在跑，
> 权限收紧能防止别人 `cat .env` 直接看到你的商户私钥。
>
> **🔴** `.env` **绝对不能进 Git。** 确认 `.gitignore` 里有它。

## 8.3 一键部署

```bash
cd /var/www/kuile/正式上线版
chmod +x 04-部署脚本/deploy.sh
./04-部署脚本/deploy.sh
```

脚本会依次做：装依赖 → 建表 → 启动服务 → 配 Nginx → 健康检查。

> **💡 原理：脚本里的** `set -e` **是什么意思？**
> `set -e` = **任何一条命令失败就立刻退出**。
> 没有它的话，假设「建表失败」了，脚本还会继续往下跑「启动服务」，
> 最后你看到「部署成功」，但服务根本起不来 —— **错误被掩盖了**，
> 你会花半小时在一个已经失败的步骤上找原因。
>
> **💡 脚本里几个关键动作在干什么？**
>
> - `npm ci --omit=dev`：**按** `package-lock.json` **精确安装生产依赖**。
> `npm ci` 保证每次装出来的版本完全一致（`npm install` 可能因为 `^` 版本号装到更新版），
> `--omit=dev` 跳过开发依赖（测试框架之类），省空间、缩小攻击面。
> - `node scripts/migrate.js`：执行建表。**幂等** —— 重复跑不会出错。
> - `pm2 start src/server.js --name kuile-api`：让 PM2 启动后端并给它起个名字。
> 之后 `pm2 logs kuile-api`、`pm2 restart kuile-api` 就是靠这个名字找到它。

## 8.4 配置 HTTPS 证书

```bash
# 把第 2.4 步下载的证书上传到 /etc/nginx/ssl/kuile/
mkdir -p /etc/nginx/ssl/kuile
# （用 MobaXterm 把 fullchain.pem 和 privkey.pem 拖进去）

# 修改 nginx 配置里的域名
vi /etc/nginx/conf.d/kuile.conf
# 把所有 yourdomain.com 换成你的真实域名

# 检查并重载
nginx -t
nginx -s reload
```

> **💡 原理：**`fullchain.pem` **和** `privkey.pem` **为什么是两个文件？**
>
> - `privkey.pem`：**私钥** —— 用来解密客户端发来的会话密钥、给响应签名。**绝不外泄。**
> - `fullchain.pem`：**证书链** —— 包含你的证书 + 中间 CA 证书 + 根 CA 证书。
>
> **为什么要「链」？** 证书不是自证的，是「上家担保下家」：
> 根 CA（浏览器内置信任）签了中间 CA，中间 CA 签了你的证书。
> 浏览器要顺着这条链一路验到根，才能确认你的证书是真的。
> 只给一张自己的证书，浏览器不知道该信谁，就报「证书无效」。
>
> **`fullchain` 里的 `full` 就是「完整链条」**的意思。
> （有些工具导出的是只有一张的 `cert.pem`，那在某些客户端上会失败。）
>
> **💡** `nginx -t` **是什么？**
> **先测试再重载**。Nginx 的配置解析失败时，**默认不会影响正在运行的服务**（老配置继续用），
> 但如果直接 reload 失败你就得进服务器改文件了。
> `-t` = test，只检查语法不实际加载。**改完 Nginx 配置永远先** `-t`**。**

## 8.5 验证部署

在服务器上执行：

```bash
# 本地健康检查
curl http://127.0.0.1:3000/api/health
```

应该返回：

```json
{"code":0,"msg":"ok","data":{"service":"kuile-api","version":"1.0.0","db":true,"env":"production","depositEnabled":false}}
```

- [ ] `db` 是 `true` → 数据库连上了
- [ ] `depositEnabled` 是 `false` → **内测阶段免押金模式已生效**（第 7.7 节）
- [ ] 浏览器打开 `https://api.你的域名/api/health` → 也能看到 → **HTTPS 配好了**

```bash
# 看日志
pm2 logs kuile-api
```

> **💡 原理：为什么要做「本地 + 公网」两次健康检查？**
>
> 这是在**分层定位故障**：
>
> - `curl http://127.0.0.1:3000/api/health` **通** → 说明 **Node 后端和数据库都正常**，
> 问题在 **Nginx 或域名/证书**这一层。
> - `curl http://127.0.0.1:3000/api/health` **不通** → 问题在 **Node 或数据库**，跟 Nginx 无关。
>
> 一次排查掉一半的可能，比盲目改配置快得多。
>
> **💡 为什么健康检查要单独存在一个接口？**
> 因为它是**给机器看的**，不是给人看的：
>
> - 监控脚本每 5 分钟调一次，失败就告警（第 12.2 节）
> - 部署脚本跑完调一次，失败就知道部署没成功
> - 你手动调一次，5 秒钟知道服务状态
>
> 它必须是**无登录、不依赖数据库之外任何东西**的极简接口 —— 才能真正反映「服务能不能用」。

## 9.4 配置服务器域名（微信后台）

**这一步不做，小程序会报「不在以下 request 合法域名列表中」。**

- [ ] 微信公众平台 →「开发管理」→「开发设置」→「服务器域名」
- [ ] 「request 合法域名」→ 添加 `https://api.你的域名`
- [ ] 「uploadFile 合法域名」→ 添加 `https://api.你的域名`
- [ ] 「downloadFile 合法域名」→ 添加 `https://api.你的域名`（如果有用到下载）
- [ ] 每个月可以改 **5 次**，改完要等几分钟生效

> **💡 原理：这三类域名白名单分别在管什么？**
>
> | 类型 | 对应的小程序 API | 本项目用在哪 |
> |---|---|---|
> | **request** | `wx.request` —— 普通的接口调用 | 所有的后端 API |
> | **uploadFile** | `wx.uploadFile` —— **上传文件** | 上传打卡照片到 COS |

> 把用户手机里的文件传到任意服务器。微信把它单独拎出来管控，
> 你要配了才说明「你承认这个服务器可以接收你用户的文件」。
>
> **💡 为什么「每个月只能改 5 次」？**
> 这是**防滥用**设计。域名白名单如果能随便改，
> 攻击者拿到你的小程序账号后就能把流量引到自己的服务器去偷数据。
> 限制修改次数 = **改域名是一个需要「冷静一下」的操作**，能挡掉很多临时起意的劫持。
>
> **📌 注意**：这个列表**只支持域名，不支持 IP 和端口** ——

## 9.5 检查隐私合规（容易被拒的点）

  - **体重数据**（用户自己填的）→ 用途：打卡记录
  - **打卡照片** → 用途：**AI 打卡判定 + 公开展示为打卡证据**
  - **位置信息**（如果你有做定位）→ 不用就不声明
- [ ] 每项都要写清楚「收集什么、为什么收集、怎么用、存多久、给谁」

> **💡 原理：为什么「隐私保护指引」是硬性的？**
>
> 《个人信息保护法》+ 微信平台规则要求：**收集个人信息前，必须明确告知用户**，
> 并取得同意。这叫「**告知同意**」原则。
>
> 微信的落地方式是：在小程序里内置一个「隐私保护指引」页面，
> 用户首次用到相关功能时会弹窗让用户确认。没配这个，**直接拒绝审核**。
>
> **💡 关键在于「用途」要具体到能理解，不能写套话**
>
> | 写法 | 审核结果 |
> |---|---|
> | 「收集用户信息用于改善体验」 | ❌ 太模糊，等于没说明 |
> | 「收集体重数据用于生成打卡记录与达标判定」 | ✅ 具体、用户能判断 |
> | 「收集打卡照片用于 AI 识别秤面读数，并在目标详情页公开展示为打卡证据」 | ✅ 更具体 |
>
> 审核员要判断的是：**这个用途用户能接受吗？会不会超出预期？**
> 所以写得越具体，越能证明你「没有超出用户预期」。

# 第 10 章：测试

> **💡 先理解一件事：为什么测试要分这么多层？**
>
> 测试不是「把所有功能点一遍」，而是**分层拦截不同类型的问题**，越靠前的层越快越便宜：
>
> ```
> ① 规则对账测试   （0.1 秒）  改规则算错了？          → 纯函数断言，不用起数据库
> ② 数据层一致性   （0.1 秒）  SQL 字段名拼错了？      → 静态比对代码和建表 SQL
> ③ 业务编排集成   （0.5 秒）  流程顺序错了？          → 内存数据库跑完整流程
> ④ 内测押金专项   （0.5 秒）  内测免收押金逻辑对吗？  → 专门覆盖钱相关的分支
> ⑤ 接口冒烟测试   （3 秒）    接口没注册？鉴权失效？   → 起真服务打 HTTP
> ⑥ 手动功能测试   （2 天）    用户能顺畅用吗？        → 真机手动点
> ```
>
> **前 4 层是** `npm test` **一条命令跑完的（110 项断言，5 秒）**，
> 任何改代码都该跑。第 5、6 层是上线前的最后把关。

## 10.1 后端规则自检（每次改代码都要跑）

- [ ] 在 `02-后端` 目录下执行：
  ```bash
  npm test
  ```
- [ ] 应该看到：
  ```
  通过 60 项，失败 0 项        ← 规则对账测试
  ✅ 数据层一致性检查通过（24 张表全部对齐）
  通过 19 项，失败 0 项        ← 业务编排集成测试
  通过 18 项，失败 0 项        ← 内测押金专项测试
  通过 13 项，失败 0 项        ← 接口冒烟测试
  ```

> **💡 原理：为什么规则要写成「断言」而不是「文档」？**
>
> 想象你把「7 天档断卡 1 次直接失败」这条规则写在文档里。
> 三个月后有人改了 `breakState` 函数 → 断 1 次不再判负了。
> **文档不会报警，但测试会。**
>
> 断言（assertion）就是「我断言这里必须是 X，不对就报错退出」。
> `rules.test.js` 里有 60 条断言，每条对应一条产品规则。
> 改规则 → 测试要么全绿（改对了），要么立刻报红（改坏了）。
>
> **💡 这叫「回归测试」**
> **回归** = 改了新东西之后，**旧的东西有没有被搞坏**。
> 测试自动帮你记住「哪些行为是不能变的」，不用靠人肉记忆。
>
> **💡 为什么规则要集中在** `domain/rules.js` **且不碰数据库？**
> 因为**纯函数**可以瞬间测试完（60 条断言 0.1 秒）。
> 如果规则里混杂着数据库查询，测试就得起 MySQL，慢且脆。
> 这个设计让「改规则 → 验证」这个循环从「半天」缩短到「1 秒」。

## 10.2 完整功能测试清单

### 登录

- [ ] 第一次打开小程序，自动登录成功
- [ ] 关闭小程序再打开，还是登录状态（不要求重新登录）
- [ ] 「我的」页显示正确的昵称和信用分 60

> **💡 原理：「自动登录」是怎么做到的？为什么不要求用户输密码？**
>
> 微信小程序有个特性：**用户的微信身份是已知的**。
> 小程序调 `wx.login()` → 微信给一个临时 code → 后端拿 code 换 openid → 后端发一个 token 存本地。
>
> 之后每次请求带上 token，后端查数据库确认「这个 token 对应哪个用户」。
> 整个过程用户**零感知** —— 因为在微信里，登录状态本来就在。
>
> **为什么这不是「不安全」？**
> 因为拿不到 code（它只在微信内部流转）就换不到 openid，
> 而 openid 只有微信能给出。你的服务器是**唯一**能确认「这个人是谁」的地方。
>
> **💡 为什么 token 存数据库而不是只放在内存？**
> ① **多实例支持**：以后扩到多台服务器，内存里的 session 不共享，数据库里的共享。
> ② **可作废**：用户换设备、注销账号时，直接删掉数据库里的那行 token 就立刻失效。
> ③ **过期可管**：`expires_at` 字段 + 每次校验时对比，30 天自动失效。

### 立 Flag

- [ ] 首页 →「立一个 Flag」→ 填表 → 下一步 → 选周期 → 下一步
- [ ] 第一个 Flag 应该显示「新人保护：第 1 个 Flag 免费」
- [ ] 提交后跳转到目标详情页，状态是「筹备中」
- [ ] 信用分 45（受限）时，90 天周期应该是灰的，提示「信用分不够」
- [ ] 信用分 45 时押金只能选 100/200，300 及以上要灰掉并提示「信用分不够」

> **💡 原理：「新人保护」为什么存在？**
>
> 第一件事最难。用户的心理是「我要先试试水」，
> 如果第一次就要押 500 块且有扣款风险，他大概率直接不试了 —— **产品就永远失去这个用户**。
>
> 所以第一个 Flag 免费（押金 0）。这不是「让利」，
> 而是**降低首次尝试的门槛**，让用户先体验到「打卡 - 见证 - 结算」的完整闭环，
> 建立信任之后再谈押金。
>
> **💡 原理：「置灰」是什么设计？为什么不是直接隐藏？**
>
> 直接隐藏 = 用户根本不知道有 90 天档这个选项。
> 置灰 + 提示「信用分不够」= **告诉用户「有这个选项，你现在还不行」**，
> 反而制造了目标（「我要把信用分提上去才能立 90 天的」）。
>
> **这是「渐进披露」和「目标激励」的设计** —— 前者不藏信息，后者把限制变成动力。
> 但前提是**给了明确的行动方向**（怎么才能解锁），否则就是纯粹的打压。

### 押金（内测阶段，⭐ 本次重点测）

- [ ] 选押金那一页，**档位显示和正式版完全一样**（100/200/500/1000 都正常显示、可选）
- [ ] 信用分不够的档位**照常置灰**并提示「信用分不够」
- [ ] 点「确认并支付」→ 弹出弹窗，标题「内测阶段」，内容「**内测阶段，暂不收取押金**」
- [ ] 点「知道了」→ 提示「立好了」→ **正常进入目标详情页**，状态是「筹备中」
- [ ] 确认**没有调起微信支付**（不会弹出微信的付款界面）
- [ ] 「我的」页里这一局的押金金额**照常显示**（如 500 元）
- [ ] 广场 / 目标详情页里这一局的押金**照常显示**

> **💡 原理：为什么内测期还「显示押金」但不真收？**
>
> 这三个动作对应三个不同的目的，缺一不可：
>
> | 动作 | 目的 |
> |---|---|
> | **界面显示押金档位** | 测试用户对「押多少」的决策（这直接影响产品价值验证） |
> | **数据库记录名义押金** | 后台统计「多少用户愿意押 2000 块」 |
> | **实际收 0 元** | 避免在没有退款通道、没有推送时收用户的钱（合规红线） |
>
> 如果连显示都去掉，你就测不出任何东西 —— 用户根本不知道这个产品跟押金有关。
>
> **💡 原理：为什么结算时不能扣钱？**
> 因为「实收 = 0」。你从没收到过这笔钱，也就不存在「扣收」和「退款」——
> 退款给一个没付过钱的人，就是**凭空亏一笔钱**；
> 扣一个没付过钱的人的钱，是**无依据的罚款**。
> 所以结算时实收为 0 → 扣 0、退 0，**完全自洽**。
>
> **💡 原理：为什么信用分还是要照常扣？**
> 因为**信用分衡量的是「承诺的兑现情况」，和钱是两件事**。
> 用户没打卡、没达标，这就是没兑现承诺，信用分该扣就得扣 ——
> 否则内测期的数据就全是「成功样本」，完全失真。
> 信用分是产品运转的核心信号，不能因为没收钱就放水。

### 打卡

- [ ] 筹备期结束（24 小时后）才能打卡 —— 或者改数据库手动推进
- [ ] 打卡页拍一张照片，填体重和手写词，提交
- [ ] 提示「已提交，正在判定」，然后出现「打卡通过」
- [ ] 打卡历史里能看到这一天

> **💡 原理：为什么打卡页要「轮询」而不是「等一个结果」？**
>
> 因为 AI 判定要 1-5 秒，这期间 HTTP 请求不能一直挂着 ——
> 服务器要处理其他用户的请求，一个请求占着 5 秒，100 个并发就把服务占满了。
>
> 所以架构是：**提交打卡 → 立刻返回「已提交」→ 前端每 2 秒查一次状态 → 变成 ok/rejected 就停**。
> 最多查 15 次（30 秒）。
>
> **为什么不用 WebSocket？** 因为判定是秒级的短任务，轮询实现简单、不会漏消息、
> 对服务器压力可忽略。WebSocket 在小程序里要额外配置（域名白名单、wss 协议、心跳），
> 很多场景用不上。

>

>
> - 5 位上限：见证人太少（1 位）→ 判定容易被个人偏见左右；
> 太多 → 没人愿意每天盯着，也降低单个见证人的责任感。
> - 48 小时过期：邀请发出后不回复就自动失效，避免**名单被「僵尸邀请」占满**。
> 见证席席位是稀缺的（直接影响强度档位 T0/T1/T2/T3），

> 因为「体重秤上的数字是不是真的」这件事，**机器也未必能百分百判断**。
> 3 个人各看各的，比 1 个人看更可靠 —— 而且**责任分散**：
> 如果只有一个人判定，那个人就是「唯一裁判」，压力大、也容易被缠上。
> 规则还规定：作弊票达 1/3 才成立 —— **不能因为一票就判死**。

> **💡 原理：为什么要用「¥0.01 元」测试？**
>
> 两个原因：
> ① **验证链路**：0.01 元和 500 元的支付流程**完全一样**（同样的下单、支付、回调、退款），
>    但退款时你只亏 1 分钱。用 500 元测，测 20 遍就是 1 万块。
> ② **验证金额精度**：0.01 元 × 35% = 0.0035 元 —— 这正好能测出**浮点精度 bug**。
>    如果代码有浮点误差（比如用了 `0.1 + 0.2 !== 0.3` 这类计算），
>    小额测试就会暴露出来 —— 用 500 元测反而可能因为四舍五入看不出来。
>
> **💡 为什么退款必须核对「实际到账时间」？**
> 微信的退款是**异步**的：接口返回「已受理」，钱实际到账要等银行处理。
> 你必须知道真实的到账时间，才能对客服承诺「3 个工作日内」。
> **没测过的承诺不叫承诺，叫猜。**

### 结算

- [ ] 手动把一个 Flag 的结束日期改到过去 → 等 1 分钟 → 定时任务应该自动结算
- [ ] 达标的情况：信用分按档位系数增加
- [ ] 失败的情况：押金按比例扣收，信用分减少
- [ ] **内测阶段**：失败时押金扣收是 **0 元**（不是 35%），信用分照常扣

> **💡 原理：为什么结算靠「定时任务轮询」而不是「精确定时器」？**
>
> 因为断卡判定依赖「自然日的边界」（凌晨 0 点才算断卡），
> 而结束日结算也要在**特定日期**触发。
> 如果给每个 Flag 都建一个精确的定时器（每 7 天触发一次），
> 几万个 Flag 就是几万个定时器，内存和调度都会出问题，而且**服务器重启就全丢了**。
>
> 轮询方案：每 60 秒扫一遍数据库，问三个问题：
> ① 有没有筹备期到期该转「进行中」的？
> ② 有没有打卡日过了还没打卡该判断卡的？
> ③ 有没有结束日到了该结算的？
>
> **60 秒的精度对「天」级业务完全够用**，而且天然是**幂等**的
> （扫到已处理的就跳过，重复扫也不会出错），服务器重启也不影响。
>
> **💡 原理：为什么失败结算要「先改状态再算钱」？**
> 代码里第一步就是 `UPDATE flag SET status = 'settling'`。
> 原因：**防并发重复结算**。如果两个定时任务同时扫到同一个该结算的 Flag，
> 没有中间状态的话可能退两次款。改成 `settling` 后，第二个任务扫到就跳过了。
> 这是数据库并发控制的经典手法 —— **用一个中间状态当「正在处理」的锁**。

## 11.2 ⚠️ 审核高风险点（提前规避）

> **这是本文档最重要的一节。** 减肥类小程序被拒率很高，主要原因如下：

| 风险点 | 微信的态度 | 怎么规避 |
|---|---|---|
| **「减肥」「瘦身」** | 容易被认为是**医美/健康医疗服务** | 类目选「工具」，文案强调「打卡工具」「习惯养成」而非「减肥疗效」 |
| **押金 / 保证金** | 会被认为是**资金募集**或**赌博** | 明确写「押金在达标后 100% 原路退还，不用于任何经营用途」，并提供完整协议 |
| **涉及他人判定、扣钱** | 会被认为是**有争议的第三方裁决** | 强调「判定仅影响信用分，不直接产生金钱后果；押金金额与判定结果无关」 |
| **用户上传照片并公开** | 涉及隐私 | 隐私指引写明；提供「举报违规内容」入口；照片内容需人工审核机制 |
| **AI 自动判定** | 需要说明 | 审核备注里写明「AI 仅作辅助初筛，最终由人工复核」 |
| **无资质却涉健康** | 需要《互联网信息服务许可证》 | 视情况办理，或去掉所有医疗健康表述 |

> **💡 原理：微信审核的核心判断标准是什么？**
>
> 微信审核员本质上在做一件事：**评估这个小程序会不会给平台和用户带来风险**。
> 风险主要来自四个方向：
>
> | 风险方向 | 具体顾虑 | 对应你的规避手段 |
> |---|---|---|
> | **触及监管红线** | 涉及医疗、金融、赌博等需牌照的业务 | 类目选工具、押金说明清晰 |
> | **损害用户利益** | 先收钱后不办事、押金不退 | 明确写「100% 原路退回 + 3 个工作日」 |
> | **第三方裁决争议** | 扣钱/处罚的判定权在谁手里、用户能不能申诉 | 押金金额与判定结果无关，只与是否达标有关 |
> | **内容风险** | 用户上传的图片可能违规（色情、暴力） | 举报入口 + 人工巡查机制 |
>
> **💡 特别注意「押金 / 保证金」这一行 —— 为什么会引起资金募集的联想？**
>
> 因为在监管视角里，「用户交钱 → 平台按某个规则把钱分给一部分人」，
> 这个结构长得非常像**资金池**或**博彩**（用户出钱、有人赢、有人亏）。
>
> 而本产品恰好是**「用户出钱、平台全都不赚（失败时也只退不赚）」** ——
> 平台不是收款方也不是分配方，钱只在用户之间流转。
> **这个区别必须在审核备注里讲清楚**，因为审核员看不到你的代码，只能看你写的说明。
>
> **💡 关于「AI 自动判定」这一行**
> 微信对「机器代替人做决定」是谨慎的 —— 因为一旦出错，责任主体不清。
> 你的产品设计恰好规避了这点：**AI 只做初筛，最终由人工复核**，
> 而且「判定结果不直接影响钱，只影响信用分」。
> 这两点写清楚，审核员就没有理由拒。

> **💡 小技巧：审核备注要「主动交代」，不要「等着被问」**
>
> 审核员每天看几百个申请，只看你写的那几行字。
> 主动把「押金怎么退」「AI 怎么用」「隐私怎么保护」讲清楚，
> 是在**降低审核员的不确定性**。
> 反过来，藏起来只会让他更怀疑 —— 一个提到押金但没解释清楚的小程序，
> 比一个老老实实写清楚的小程序危险得多。

## 11.3 审核备注模板（重要！）

审核备注是审核员了解你产品 fastest 的途径。**照抄下面这个模板改改**：

```
【产品说明】
本小程序是「打卡习惯养成工具」，帮助用户公开立下阶段目标并按日打卡，
由受邀的见证人进行阶段性确认。

【押金说明】
1. 押金是用户自愿缴纳的履约保证金，不是会员费、不是平台收入。
2. 用户达成目标后，押金 100% 原路退回至原支付账户。
3. 未达成目标时，仅按用户信用等级对应的比例（20%-40%）部分扣除，
   其余部分原路退回。扣除金额与见证人判定结果无关，
   仅依据「是否达到目标体重」和「打卡天数是否达标」自动计算。
4. 押金逐用户独立记账、专款专用，退还时限不超过 3 个工作日。
5. 用户可在「我的」页面查看押金金额与退还记录。
6. 如有争议，可通过「我的 - 客服/申诉」联系处理。

【AI 判定说明】
打卡照片由 AI 模型进行辅助审核（识别体重秤读数与手写词），
AI 结论仅作为初筛提示，最终是否计为有效打卡由平台人工复核确认，
不会仅凭 AI 结论作出处罚。

【测试账号】
（如果没有特殊说明可以删掉这段）
```

> **💡 如果本次仍是「内测阶段暂不收取押金」，审核备注加这一段：**
>
> ```
> 【当前阶段说明】
> 本小程序目前处于内测阶段，暂不开启真实押金收取功能。
> 用户选择押金档位仅用于记录其承诺额度，实际不收取任何款项，
> 也不涉及退款。内测阶段结束、支付与退款通道完整验证后，
> 才会开放真实收取，届时将严格按照上述押金规则执行。
> ```
>
> **💡 为什么内测期也要主动写这段？**
> 因为审核员看到「押金」两个字就会警惕。如果你不说，
> 他可能自己推断「这个功能有问题」；你主动说明是**有计划的、可解释的产品阶段**，
> 反而消除了疑虑。
>
> **⚠️ 但要注意一致性**：如果审核备注写「暂不收取押金」，
> 而实际上线后用户却被扣了钱（或者被要求付款），那就是**虚假陈述**，
> 属于更严重的问题。**说什么都要和实际做的一致。**

# 第 12 章：上线后运营与合规

## 12.1 合规红线（这些必须长期遵守）

来自产品规则，**不能因为上线压力就妥协**：

- [ ] **押金退还时限 ≤ 3 个工作日** —— 写进客服话术，定期抽查
- [ ] **押金逐用户独立记账、专款专用** —— 不能把不同用户的押金混在一起
- [ ] **押金不是平台收入** —— 失败扣收的钱不能分给见证人（**这是硬红线**）
- [ ] **押金不能和会员费混在同一个支付按钮里**
- [ ] **押金协议必写六项**：
  1. 退还条件
  2. 退还流程
  3. 处理时限（≤3 个工作日）
  4. 扣除标准与计算方式
  5. 不可扣除的情形（平台原因、不可抗力）
  6. 争议处理与申诉渠道
- [ ] **咨询率 < 1%、升级投诉率 < 0.05%**
- [ ] **用户内容审核机制**（打卡照片公开，必须有人工巡查）

> **💡 原理：为什么「押金不是平台收入」是硬红线，不能商量？**
>
> 这条红线的价值在于**保护用户，也保护产品本身**。三个层面：
>
> **① 用户层面**：一旦平台能靠押金赚钱，用户的利益就和平台利益**对立**了。
> 平台会希望更多用户失败（失败才有「收入」），
> 于是判定会变严、扣款比例会悄悄上调 —— **用户会感到「规则在针对我」**。
>
> **② 合规层面**：「平台从用户保证金中获利」在监管眼里非常接近**资金募集**。
> 一旦被认定为非法吸收公众存款或变相博彩，面临的是**罚款 + 下架 + 刑事责任**，
> 不是补个手续能解决的。
>
> **③ 产品层面**：这个产品的全部价值建立在「打卡记录可信」上。
> 如果平台能靠押金赚钱，那**见证席判定就会变成给平台赚钱的工具**，
> 而不是「朋友之间的监督」。产品的灵魂就没了。
>
> **一句话：押金不是商业模式，是信任机制。** 一旦变成收入，信任就没了。

> **💡 原理：为什么押金协议必须写「不可扣除的情形」？**
>
> 因为**只写扣除规则不写例外，等于给自己埋雷**。
> 用户遇到「平台故障导致我没打上卡」「系统算错了体重」这类情况时，
> 没有例外条款就无法申诉，争议只能靠吵架解决。
>
> 这六项是**监管和消费者权益保护的基本要求**，也是客服话术的骨架。

## 12.2 必备的运维能力

### 日常监控

- [ ] 服务器 CPU / 内存监控（腾讯云有「云监控」，配告警）
- [ ] 后端服务监控：`pm2 monit`，或配 PM2 的 `pm2-logrotate-daily`
- [ ] 数据库慢查询监控
- [ ] **每天看一眼日志有没有报错**：`pm2 logs kuile-api --lines 100`

> **💡 原理：为什么要装** `pm2-logrotate-daily`**？**
> PM2 会把所有日志写进文件，**不限制大小**。
> 跑上几个月，日志文件能涨到几个 GB ——
> 而磁盘满了会导致**数据库写不进去、服务直接挂掉**。
> `pm2-logrotate-daily` 让日志按天切割、保留 N 天、自动压缩清理。
>
> **💡 原理：日志文件为什么值得定期看？**
> 很多故障在**变成用户可见的问题之前**，日志里已经有征兆了
> （比如某类请求开始大量报错、某个耗时突然变长）。
> 每天花 2 分钟扫一眼，能在故障扩大前发现。

### 数据备份（极其重要！）

- [ ] 数据库自动备份：`04-部署脚本/backup-db.sh` 已配置 crontab（第 4.8 节）
  - 每天凌晨 3:17 自动跑，本地保留 7 天 + 上传 COS 异地
- [ ] **每周**看一眼备份有没有成功：`ls -lh /var/backups/kuile/`
- [ ] **每季度**做一次恢复演练（第 4.8 节 ④）—— **没验证过的备份等于没有备份**
- [ ] COS 开启版本控制或跨区域复制（可选）

> **💡 原理：为什么「备份」不等于「能恢复」？**
>
> **没验证过的备份等于没有备份**，这句话是运维界的血泪教训。
>
> 真实案例：某公司自动备份每天都跑、状态全绿，
> 真出事时恢复时才发现 —— 备份文件是空的、格式不兼容、中间缺了关键几天的数据。
>
> 原因通常是：**备份和恢复用的是两套逻辑**。
> 备份只管「把数据复制出去」，不管「复制出来的东西能不能用」。
>
> **所以必须定期做「恢复演练」**：
> 拿一份备份，**恢复到一个临时实例上**，跑几个查询，确认数据完整、时间点正确。
> 建议每季度演练一次。
>
> **💡 自建 MySQL 比托管版更需要重视备份**
> 托管版有「主从自动切换」，你的单机版**挂了就是挂了**。
> 唯一能救你的就是备份 —— 而它只有在**验证过**的时候才救得了你。
>
> **💡 特别强调「异地」**
> 备份只存在这台服务器的硬盘上，等于没备份（盘坏了数据和备份一起没）。
> `backup-db.sh` 会上传到 COS —— COS 在腾讯云的存储集群上，
> 和你的服务器是**物理隔离**的，整机损坏也不影响它。

### 告警

- [ ] 服务挂了要有人知道 —— 配一个「健康检查 + 告警」：
  ```bash
  # 每 5 分钟检查一次，失败就发邮件/企微
  */5 * * * * curl -sf http://127.0.0.1:3000/api/health || echo "服务异常" | mail -s "亏了服务挂了" you@email.com
  ```

> **💡 原理：为什么告警要「自动」而不是「每天手动看」？**
>
> 因为故障发生的时间点，和你看监控的时间点，是**两个独立的随机变量**。
> 如果凌晨 3 点服务挂了、你在早上 9 点才看到 —— 那 6 小时的宕机，
> 用户已经经历了一切：打卡打不进去、见证席判不了、结算跑不了。
>
> **告警的意义就是把「发现延迟」从「小时级」压到「分钟级」。**
>
> **💡** `crontab` **的语法**
> `*/5 * * * *` 是「五个星号」格式：
> `分 时 日 月 星期` —— 这里的意思是「**每 5 分钟**执行一次后面的命令」。
>
> **💡 为什么用** `curl -sf` **而不是** `curl`**？**
> `-s` = silent（安静，不输出内容）、`-f` = fail（HTTP 出错时返回非 0 退出码）。
> 加了这两个参数，**服务返回 500 或连不上时，**`curl` **的退出码就是非 0**，
> `||` 就会触发告警。
> 如果不加，curl 拿到 500 响应体照样退出 0，**告警永远不会触发** —— 这是个很常见的坑。

## 12.3 用户增长（冷启动）

产品规则里定义的几个关键数字：

- [ ] **M1 阶段核心 8 页**全部可用
- [ ] 首批种子用户：**找 10-20 个真实想减肥的朋友**先用起来
- [ ] 「立据」分享链路要通：用户能把 Flag 分享到微信群
- [ ] 见证席召集令要能发出去（**这是冷启动的关键机制**）

> **💡 原理：为什么这个产品是「双边冷启动」，比普通产品更难？**
>
> 普通产品只需要**一侧**：有用户就有内容，用户看内容（抖音、快手）。
>
> 本产品需要**两侧同时在场**：必须有「想减肥的人」立 Flag，
> 也必须有「愿意当见证人的人」来判定。**只有一侧，产品完全跑不起来**：
>
> - 只有想减肥的人 → 没见证人 → 没人看你的打卡 → 立 Flag 没意义 → 不发了
> - 只有见证人 → 没 Flag → 没事可判 → 退出
>
> 所以产品设计上必须有**「发起者带见证人一起入局」**的机制
> （比如分享 Flag 时同时邀请见证人），这就是冷启动最关键的一环。

## 12.4 迭代节奏

- [ ] 建立一个「用户反馈收集表」（可以是腾讯问卷或金数据）
- [ ] 每周看一次反馈
- [ ] 每次改后端规则后，**必须重跑** `npm test`
- [ ] 每次改前端后，**必须 bump** `config/index.js` **里的版本注释**，让用户强制刷新

> **💡 原理：为什么要「bump 版本注释让用户强制刷新」？**
>
> 因为**小程序会缓存旧版本的代码**。用户上周打开的是旧代码，
> 你这周修了 bug 并发布了，但用户不主动下拉刷新，他用的还是旧代码 ——
> **你会收到「明明已经修了怎么还是这样」的反馈**。
>
> bump 版本号 + 提示刷新，是小程序端**强制更新缓存**的标准做法。

| **ICP 备案** | 在中国大陆公开网站必须做的登记 | 第 2.3 章 |
| **PM2** | 进程管家，程序崩了自动重启 | 部署时安装 |
| **环境变量 / .env** | 存密钥的配置文件 | `02-后端/.env` |
| **商户号 (mch_id)** | 你的收款账号 | 微信支付商户平台 |
| **APIv3 密钥** | 支付接口的密码 | 微信支付商户平台，**填错支付回调永远失败** |
| **回调 / notify_url** | 微信支付完成后通知你的地址 | `https://api.你的域名/api/pay/notify` |
| **签名 / 验签** | 确认「这条消息真的是微信发的」 | 支付回调必须验签，否则会被伪造 |
| **幂等** | 同一件事重复做，结果不变 | 支付回调会重复通知，必须防重 |
| **对象存储 / COS** | 专门存图片文件的服务 | 打卡照片存这里 |
| **CDN** | 图片加速分发 | 可选 |
| **视觉模型** | 能「看图」的 AI | 豆包 vision 模型，读秤面读数 |
| **视觉模型 / 多模态** | 同上 | 同上 |
| **定时任务 / 轮询** | 服务器定期自动检查 | 每 60 秒判断断卡和结算 |
| **事务 / Transaction** | 一组操作要么全成功要么全失败 | 支付回调的账务处理 |
| **灰度 / 灰掉** | 不可点击的置灰状态 | 押金档位不够时的显示 |
| **SLA** | 服务水平协议，承诺多久响应 | 客服 24 小时内响应 |
| **冷启动** | 用户还不够多的时候 | 靠种子用户和分享拉新 |
| **首版 / M1** | 第一个能用的版本 | 本项目当前阶段 |
| **🆕 押金总开关** | 「要不要真收钱」的开关 | `.env` 的 `DEPOSIT_ENABLED` |
| **🆕 名义押金** | 「这一局承诺押多少」 | `deposit_amount`，内测期照常记录 |
| **🆕 实收押金** | 「实际收到多少钱」 | `deposit_paid`，内测期为 0 |

> **💡 给三个新名词的详细解释：**
>
> 这三个是本次改动引入的概念，第 7.7 节有完整说明，这里只做速查：
>
> | 名词 | 一句话 | 关键点 |
> |---|---|---|
> | **押金总开关** | `.env` 里的 `DEPOSIT_ENABLED` | `false` = 内测免收，`true` = 正式收 |
> | **名义押金** | 承诺押多少 | 内测期照常记录，用于统计用户决策 |
> | **实收押金** | 真的收到多少 | 结算只认它 —— 实收 0 就不扣不退 |
>
> **为什么必须分成两个？** 因为「承诺」和「到账」是两件事。
> 结算逻辑只认「到账」，这样无论开关什么时候翻转，都不会出现
> 「退一笔从没收到的钱」或「收了钱却不退」。

# 附录 B：出问题时的排查顺序

**从上往下查，90% 的问题在前三步就能找到。**

> **💡 通用原则：先定位「哪一层坏了」，再修那一层。**
>
> 一个小程序出问题的链路有 5 层：
>
> ```
> 小程序代码 → 网络 → Nginx → Node 后端 → MySQL
> ```
>
> **每一层都有自己专属的诊断命令**。用对命令，能省掉 90% 的瞎猜时间。

## B.1 小程序报「不在合法域名列表中」

1. 检查 `config/index.js` 的 `BASE_URL` 是不是 HTTPS 域名
2. 检查微信公众平台「服务器域名」是否加了
3. 改完等 5 分钟再试
4. 开发阶段可勾选开发者工具的「不校验合法域名」

> **💡 原理：为什么改完要等几分钟？**
> 微信后台改域名白名单是**异步生效**的 —— 后台改完之后，
> 微信的**配置下发**（推送到各地的小程序网关）需要一点时间。
> 立刻去试可能还是用旧配置，看起来像「配了没用」。
> **这不是 bug，是设计。**

## B.2 小程序报「登录失败」/ 接口超时

```bash
# 1. 服务器上服务还活着吗
pm2 list
pm2 logs kuile-api --lines 50

# 2. 端口通吗
curl http://127.0.0.1:3000/api/health

# 3. Nginx 通吗
curl https://api.你的域名/api/health

# 4. 数据库连得上吗
pm2 logs kuile-api | grep -i "数据库"
```

> **💡 原理：为什么按这个顺序查？**
> 这是**从内到外**逐层排除：
>
> - `pm2 list` 显示 `online` 吗？不 online → 服务根本没起来，看日志。
> - `curl 127.0.0.1:3000` 通吗？不通 → **问题在 Node 或数据库**，跟 Nginx 无关。
> - `curl https://你的域名` 通吗？不通 → **问题在 Nginx / 证书 / 域名解析**。
>
> **为什么先查本机再查公网？** 因为本机测试排除了「网络」这个变量。
> 如果跳过它直接测公网，域名解析、DNS 污染、证书过期、网络运营商问题会一起混进来。

## B.3 支付一直失败 / 回调不生效

按这个顺序查：

1. **API 权限开了吗？**（JSAPI 支付 + 退款 + 订单查询）
2. **APIv3 密钥对吗？**（复制粘贴时不要带空格、换行）
3. **回调地址能访问吗？** 自己访问 `https://api.你的域名/api/pay/notify` 看有没有返回
4. **证书序列号对吗？**
5. 看日志：`pm2 logs kuile-api | grep -i 微信支付`
6. 在商户平台看「交易查询」里这笔单的状态

> **🔑 支付问题 90% 是这三样之一**：API 权限没开、APIv3 密钥填错、回调地址不通。

> **💡 原理：怎么区分「支付没成功」和「支付成功了但系统没收到通知」？**
>
> 看**商户平台的订单状态**：
>
> - 订单状态 = 支付成功，但你的数据库里还是「未支付」→ **回调没到**，查回调地址和验签。
> - 订单状态 = 支付中/待支付 → **用户根本没付成功**，查前端调起支付那一步。
> - 订单状态 = 已支付且你的系统也处理了 → 问题在**后续业务逻辑**（比如结算）。
>
> **这三种情况的现象都是「用户说付了钱但 Flag 没生效」，但根因完全不同** ——
> 不先分清就会查错方向。

## B.4 AI 判定不生效

1. `.env` 里 `AI_VERIFY_ENABLED` 是 `true` 吗？
2. `ARK_API_KEY` 对吗？`ARK_ENDPOINT_ID` 对吗？
3. 日志里搜：`pm2 logs kuile-api | grep "AI"`
4. 方舟控制台看调用量和报错
5. **照片能不能被公网访问？** AI 要能下载到你的照片 —— 在浏览器里打开 COS 链接试试

> **💡 原理：第 5 条是最容易漏的一条**
> AI 模型在你的云端服务器上，它要**自己去下载你 COS 上的照片**。
> 如果 COS 桶是「私有读」且没配公开读，AI 就下载不到 ——
> **你会看到模型返回「无法识别」，但完全不知道为什么。**
> 排查方法很简单：把照片 URL 贴到浏览器里，能打开就行。

## B.5 打卡一直停在「正在判定」

1. 照片上传成功了吗？（看日志有没有「照片已上传 COS」）
2. AI 服务通吗？
3. **前端轮询上限是 15 次 × 2 秒 = 30 秒** —— 超时就提示用户稍后去打卡历史看
4. 手动查：`SELECT * FROM checkin WHERE flag_id='xxx'`

> **💡 原理：为什么轮询要设上限？**
> 没有上限的话，AI 服务挂掉时前端会**无限轮询** —— 用户手机一直耗电耗流量，
> 服务端一直被打。这是典型的「**没有兜底的无限循环**」。
> 30 秒是个权衡：正常 AI 判定 1-5 秒就够，30 秒给了 10 倍余量；
> 超了就让用户去「打卡历史」里看最终结果（后台是异步补上的）。

## B.6 数据库连不上

> **💡 本项目是自建 MySQL，和后端在同一台服务器上，
> 所以排查顺序和托管版完全不同 —— 先看服务起没起。**

1. **MySQL 服务在跑吗？**：`sudo systemctl status mysql`
2. **MySQL 只监听本机吗？**：`sudo ss -tulpn | grep 3306`
   —— 应该看到 `127.0.0.1:3306`。如果是 `0.0.0.0:3306`，说明 `bind-address` 没生效
3. **`.env` 里 `DB_HOST` 是不是 `127.0.0.1`**（不是公网地址）
4. **库建了吗**：`sudo mysql -e "SHOW DATABASES;"` 看有没有 `kuile`
5. **账号密码对吗**：`sudo mysql -u kuile -p -e "SELECT 1;"`
6. **认证插件报错？**（`ER_NOT_SUPPORTED_AUTH_MODE`）
   → `ALTER USER 'kuile'@'localhost' IDENTIFIED WITH mysql_native_password BY '你的密码';`

> **💡 原理：为什么自建的排查顺序是「先看服务、再看监听」？**
>
> 托管版出问题时，数据库是**别人家的服务**，
> 你只能检查「网络通不通、密码对不对、安全组放没放行」。
>
> 自建版出问题时，**数据库就在你手边** —— 排查手段多得多：
> - 服务起没起 → `systemctl status`
> - 端口监听到哪了 → `ss -tulpn`
> - 账号存不存在 → `SELECT user,host FROM mysql.user;`
> - 能不能用密码登进去 → `mysql -u kuile -p`
> - 甚至可以直接 `tail -100 /var/log/mysql/error.log` 看错误日志
>
> **自建的代价是「你要自己负责」，回报是「出问题你有完整的手感」。**
>
> **💡 最常见的一个坑：改完 `mysqld.cnf` 忘了重启**
> `bind-address`、`innodb_buffer_pool_size`、`default-time-zone`
> 这些**改完必须 `sudo systemctl restart mysql` 才生效**。
> 改完就 `ss` 看一眼确认，是最快的验证方式。

## B.7 服务重启后没了

```bash
pm2 save          # 保存当前进程列表
pm2 startup       # 设置开机自启（已执行过就跳过）
```

> **💡 原理：为什么「restart 之后没了」是个经典问题？**
> `pm2 restart` 是**临时**的 —— 重启后 PM2 会记得这个进程，但**服务器重启**就不一定了。
>
> 原理是：`pm2 startup` 让 systemd 在开机时启动 PM2 **守护进程**，
> 而 PM2 守护进程启动后要读 `~/.pm2/dump.pm2` 这个存档，
> 才知道要拉起哪些服务。`pm2 save` **就是生成这个存档。**
>
> **只做 startup 不做 save = 开机后 PM2 起来了但什么都没跑。**

## B.8 🆕 内测阶段用户问「怎么不让我付钱 / 押金什么时候退」

这是内测阶段的**预期内咨询**，不是 bug。按下面回：

> 「内测阶段暂不收取押金，界面上的金额只是记录你的承诺额度，
> 实际没有扣款，也就不需要退款。正式开放时会提前公告。」

> **💡 原理：为什么这类咨询必须「主动说明」而不是「含糊带过」？**
>
> 用户看到「押金 500 元」却不用付，一定会困惑。
> 如果你回答得含糊（比如「系统问题」「以后会通知」），用户的感受是**「这产品不靠谱」**。
>
> 而明确说清「这是内测阶段、没扣钱、所以不需要退」，
> 用户感受到的是**「这个产品在认真分阶段推进」**。
>
> **同样重要的是：绝不能收下钱。** 内测期收了钱却没有退款通道，
> 这就踩了第 12.1 节的合规红线。
