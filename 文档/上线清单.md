- [ ] ✅ **身高不再采集**
- [ ] ⚠️ 敏感个人信息**采集前单独同意**（不能只放在隐私政策里）
- [ ] ⚠️ **打卡照片在平台内公开**（见 R2.5）—— 隐私政策**必须如实写明**：公开范围（平台内所有用户）、公开内容（原图不打码，**含体重读数 / 背景**）、**一律公开、不提供关闭开关**

- [ ] ⚠️ **打卡页提示「拍照时请避开他人与私密空间」**；隐私政策提示「画面里如有他人，请先征得对方同意」—— 背景里的第三方是同意链覆盖不到的
- [ ] ⚠️ **分享图 / 记录卡 / 小红书笔记不带照片** —— 站外传播是另一套合规口径

- [ ] 数据导出与删除入口

- [ ] 不面向未成年人，不做年龄推断之外的收集

## 登录与游客态

> 规则见 **R0.7** ｜ 设计理由见 **D21**

- [ ] 登录页无标语，结构 = **柴犬头像（92px）+ 大字「亏了」** + **药丸分段控件（默认微信，在卡片外，橙底白字，可左右拖拽跟手）** + 卡片（**内含协议勾选**）+ 「先吃瓜围观」+ 底部弱化协议链接
- [ ] 登录页底层铺**弧形装饰色块**（品牌橙 / 浅橙，20%~60% 浓度），只落在页面边缘与角落，**内容区保持留白**；白色卡片浮在色块之上
- [ ] **一次只显示一种登录方式** —— 微信态只有一颗绿色胶囊；手机号态只有手机号/验证码表单 + 品牌橙「登录」按钮，**不出现任何微信元素**
- [ ] 分段控件**可左右拖拽跟手切换** —— 拖到一半面板就跟着切；松手吸附；到边界有阻尼；**纵向滑动不抢页面滚动**
- [ ] 切换方式时就地换面板，**不整页重渲染**（手机号表单已输入的内容要保住）
- [ ] 协议勾选在**卡片内、登录按钮上方**，协议名加粗可点；**微信按钮与手机号「登录」按钮都被它 gate 住**；未勾选时**两颗按钮均为灰色禁用态**（灰底灰字，不是半透明）
- [ ] ⚠️ 勾选状态是**全局单一状态** —— 登录页与浮层任一处勾选，另一处立即同步
- [ ] 「先吃瓜围观」进广场后，浏览广场 / 详情 / 记录卡 / 协议 **全程不弹登录浮层**
- [ ] 游客点立 Flag / 打卡 / 订阅 / 见证 / 押金 / 异议 / 召集令 → 弹**半屏登录浮层**（标题「登录后继续」），当前页不跳转
- [ ] 浮层内用**同一套药丸分段控件**（卡片外、可左右拖拽），默认微信；浮层与登录页的切换互不干扰
- [ ] ⚠️ 切换微信 / 手机号时**画面完全不动** —— 柴犬、标题、Tab、卡片边框、游客入口、协议链接位置**逐像素不变**；两态卡片**等高 238px**
- [ ] 浮层内登录成功 → **自动回到被拦截的那个动作**；取消 → 留在原页，游客态不变
- [ ] 点赞 / 预设短语 / 分享 **不要求登录**
- [ ] 用户协议与隐私政策**正文可点开**且内容完整（不能只有标题链接）
- [ ] ⚠️ App 商店审核：**未登录即可浏览**不影响过审，但需确认隐私弹窗在首次采集个人信息前出现
- [ ] ⚠️ **敏感个人信息（体重 / 照片 / 位置）的单独同意仍需在发起前独立勾选** —— 不得依赖登录页这一个勾选框

## 一票否决项（⚠️ 违反任意一条就不能上线）

> **这 14 条是上线闸门**，不是建议清单。
> 其余各组（类目与资质 / 内容安全 / 隐私 / 运营 / 商店与发布资料）见本文件上方各节。

| # | 项 | 依据 / 落点 |
|---|---|---|
| **1** | **押金条款写明退还方式、程序、时限（≤3 工作日），且扣除以实际损失为标准** | 消保条例第 20 条 / 电商法第 21 条（见 R10.7） |
| **2** | **押金逐用户独立记账、专款专用，扣收部分不进平台营收科目** | 长租公寓判例（见 R10.6） |
| **3** | **达标必须 100% 全额退还，无任何扣收** | 无损失无理由扣款违法（见 R10.3） |
| **4** | **「不是运气，是可控行为」论证全文已写入用户协议** | 见 A2.4 用户协议 |
| **5** | **禁用词逐屏检查**（押金档位页 / 结算页 / 记录卡 / 分享图 / 见证席收益页） | 见「文案自查」相关小节 |
| **6** | **三个律师必答问题已确认** | 见下方「资金合规专项待办」 |
| **7** | **无资金池、无「打卡赚挑战金」式玩法、无有偿投票 / 利益诱导分享** | 微信运营规范 2.5.11 / 2.5.27 |
| **8** | **不用「最终解释权归平台」这类无效条款** | 民法典第 497 条 |
| **10** | **敏感个人信息采集前单独同意**（不能只放在隐私政策里） | 个人信息保护法（见 R11.1） |
| **11** | **押金相关页面在推送上线后才开放** | 见 R19.5 前置条件 |
| **12** | **打卡照片公开的隐私政策已如实改写**（不得再写「100% 私密」；须写明**一律公开、不提供关闭开关**）+ **律师已确认「平台内公开、无单独同意项」的表述方式** | 个人信息保护法 / 虚假告知风险（见 R2.5） |
| **13** | **补充照片与打卡照彻底分开存储**（不得混入同一个照片序列）+ **补充照不得计入打卡证据** + **补充照不进分享图与站外** | 伪造证据风险（见 R2.6） |
| **14** | **打卡照是「提交打卡」的硬门槛** —— 没拍照时按钮禁用 **且** 提交逻辑里必须有第二道拦截；**补充照不得替代打卡照** | 见 R2.8 |

> **（必读）第 12 条** —— 打卡照片改为平台内公开后，隐私政策里「物证照片 100% 私密」的表述**必须删掉**。留着就是虚假告知。
> **（必读）第 13 条** —— 补充照片上线后，最危险的技术错误是**把它塞进打卡照的数组**。那会让**断卡天出现图片** —— 断卡信号消失，等于伪造证据。这条必须在上线前用单元测试守住。
> **（必读）第 14 条** —— 打卡页简化后，最危险的错误是**让补充照顶替打卡照的准入位**。用户会用生活照交差，「今天称了没有」这个信号就消失了 —— 押金与见证机制全部失去依据。**禁用按钮不算数，必须在提交逻辑里真的拦住。**
