# 技术选型

> **架构前提：App 为主 + 小程序作引流壳。**
> 小程序长期订阅消息不向本品类开放，**推送能力是硬伤** —— 所以完整功能放 App，小程序只做分享落地与极简打卡。

---

## 一、平台架构

### App 为主 + 小程序作引流壳（不是两个产品）

```
微信分享卡片 / 小程序码 / 立据图
        ↓
    小程序（只做 3 件事）
    ① 展示「立据」内容 + 订阅
    ② 引导装 App（「下载 App 体验完整版」）
    ③ 极简打卡（拍照 + 随机词 + 上传）
        ↓
    App（完整功能）
    ① 全部 40 页
    ② 完整推送（断卡 / 判负 / 结算）
    ③ 离线存档、完整称重历史
    ④ 押金支付
```

### 为什么是「壳」而不是「两个产品」

| 端 | 承担 | **不**承担 |
|---|---|---|
| **小程序** | 分享卡片落地页 · 扫码落地页 · 极简打卡 · 围观 + 订阅 + 互动 + 留言 · 引导装 App | 全部 40 页 · 深度打卡体验 · 押金支付 · 完整通知 |
| **App** | 全部 40 页 · 完整推送 · 离线存档 · 完整称重历史 · 押金支付 | — |

**开发量控制：小程序只做 3 件事，不做缩水版全功能。**

### 职责分工（细）

| 能力 | 小程序 | App | 说明 |
|---|---|---|---|
| 分享落地页 | ✅ | ✅ | 小程序用 `onShareTimeline`，App 用原生分享 |
| 扫码落地页（静默登录） | ✅ | ✅ | |
| 广场浏览 + 围观订阅 | ✅ | ✅ | |
| 极简打卡 | ✅ | ✅ | 小程序只做"拍照 + 随机词 + 上传"，无历史管理 |
| **断卡 / 判负 / 结算推送** | ❌ **做不到** | ✅ | ⚠️ 见第二节 |
| 打卡历史 / 称重历史 | ❌ | ✅ | |
| 见证席面板（完整判定） | ❌ | ✅ | 小程序可只读展示判定状态 |
| 见证席收益页 | ❌ | ✅ | |
| **押金支付** | ✅ **微信普通支付** | ✅ | ⚠️ iOS 有抽成问题，见第五节 |
| 离线存档 | ❌ | ✅ | |

### 否了什么

- **支付宝小程序** —— 社交与裂变弱，但**预授权冻结**是 v2 真金押注版的最佳载体（留作 v2）
- **纯 H5 落地页** —— 无法调相机权限与微信授权。**但可用作 App 的下载落地页**（无相机需求）
- **纯 Web / 纯小程序** —— 无推送（见第二节）

## 二、⚠️ 推送能力：小程序是硬伤（核实结论）

微信官方《订阅消息》文档明确：

> **长期订阅消息仅向政务民生、医疗、交通、金融、教育等部分二级类目开放，且只支持少量公共服务节点通知**……**没有可用模板即暂不支持，不能自定义长期订阅模板。**

我们的类目是「工具」或「健康管理」—— **拿不到长期订阅**。

**小程序只能用「一次性订阅」**：用户每次点授权，才可下发一条消息。

### 对我们的影响（我们的核心召回机制全是高频推送）

| 推送需求 | 小程序可行性 |
|---|---|
| 断卡通知 | ⚠️ 每次都要用户重新授权 |
| 判负 / 作弊通知 | ⚠️ 同上 |
| 结算通知（结局） | ⚠️ 同上 |
| 每日打卡提醒 | ❌ 基本不可能 |

**用户要为一个"结束通知"重新点一次授权弹窗？** 转化率会崩。

### 官方社区明确指出的两个坑

1. **服务号模板消息需要关注公众号**
   > 「服务号+模板消息组合方案是有前提用户关注你的服务号才可以下发。**这种容易风控**」
   → 意味着要**同时做一个公众号 + 引导关注**，又多一层转化漏斗。

2. **一次性订阅不能强制订阅或群发**
   > 「不能强制订阅或发送与用户预期不符、群发性质的内容」

### 结论

> **「断卡通知 → 围观者回流 → Flag 人感受到被看着」是飞轮的必需环节。**
> **小程序做不到这一环，飞轮就是断的。**
> **这是「App 为主」的核心理由 —— 不是因为 App 更好，是因为小程序缺这一块能力。**

## 三、小程序阶段的推送替代方案

**在 App 上线之前，小程序阶段不能没有推送。** 三个方案并行：

### 方案 1｜一次性订阅额度攒起来（主力）

**关键：在关键节点引导授权，一次授权长期不用。**

| 引导授权的位置 | 攒到的用途 |
|---|---|
| 打卡成功页 | 断卡 / 结算通知 |
| 订阅 Flag 页 | 该 Flag 的结局通知 |
| 支付成功页（如有） | 退款到账通知 |
| 见证席接受邀约页 | 节点判定提醒 |

> **新版一次性订阅消息（Beta）**还有一个更好的能力：用户完成微信支付后，开发者可将**微信支付订单号作为 code** 直接下发服务通知，**无需用户弹窗授权**。适用于押金支付场景的退款通知。

### 方案 2｜服务号模板消息（补充）

- 需做公众号 + 引导关注（多一层漏斗）
- 推送能力完整
- ⚠️ 官方提示"容易风控"，需谨慎设计（不做群发性质内容）

### 方案 3｜App 上线后补齐（终态）

- App 端推送无限制（APNs + 国内各厂商通道）
- 小程序引导装 App 的提示本身可以包含"装 App 可接收断卡提醒"

## 四、⚠️ Android 推送通道是隐藏工作量

**"能上 iOS 和安卓" ≠ "推送能用"。**

| 平台 | 通道 | 难度 |
|---|---|---|
| **iOS** | APNs | ⭐⭐ 简单，官方文档全 |
| **Android 国内** | 华为 HMS Push / 小米 MiPush / OPPO / vivo / 魅族 + FCM（境外） | ⭐⭐⭐⭐ **需接 4–5 个通道** |

**这是"App 能发版"和"推送能到达"之间的差距。**

### 应对

| # | 措施 | 说明 |
|---|---|---|
| 1 | **用第三方推送聚合服务** | 个推 / 极光 / 友盟 —— 一次接入覆盖各厂，**强烈推荐**（否则自己适配 5 个通道） |
| 2 | **降级策略** | 厂商通道失败时降级到 App 内轮询 + 首页红点 |
| 3 | **推送内容分级** | 断卡 / 判负 / 结算 = 强推送（必达）；每日提醒 = 弱推送（可降级） |
| 4 | **到达率埋点** | 推送到达率、点击率是**召回效果的唯一度量**，必须埋 |

### ⚠️ 推送与内容安全的冲突

小程序端的内容安全靠 `mediaCheckAsync`，**但 App 推送不走微信审核** —— 推送文案里的用户昵称、目标体重等内容**必须自己过滤**。

## 五、⚠️ 支付能力（押金要做，v1 上线）

> **押金 v1 就做。** 完整设计见 `需求规格.md` R10 节。
> **这里只保留支付通道的技术结论。**

### 5.1 各端押金路径

| 端 | 押金路径 | 状态 |
|---|---|---|
| **小程序** | 微信普通支付 | ✅ **押金是履约保证金，非虚拟商品**，可走普通支付 |
| **App (Android)** | 微信 / 支付宝普通支付 | ✅ |
| **App (iOS)** | ⚠️ **只能走小程序虚拟支付** | Apple 抽 **12%+**，独立商户号、道具配置、T+3 结算，**iOS 还要等 Apple 45–60 天结算** |

**iOS 的三个处理方案（已定，用 C）：**

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 押金只在小程序支付** | App 内引导"去微信小程序支付押金" | ❌ iOS 用户要装微信，体验断裂 |
| **B. 走虚拟支付，费率上浮** | 收 12%+ 覆盖抽成 | ⚠️ 费率不透明 → 投诉风险 |
| **C. iOS 押金统一走高价档** | **iOS 用户的押金档位整体上浮，抵消抽成** | ✅ **最干净** —— 用户看到的是「iOS 押金 5700 元」，**与费率无关，不存在透明度问题** |

**采用 C。** 换算基准：最高档 5000 元 → iOS 对应档 5700 元（5000 ÷ 0.88 ≈ 5682，取整到 5700）。其余档位按同比例上浮。

### 5.2 ⚠️ 开放时机的前置条件（三条都要满足）

| # | 前置条件 | 为什么 |
|---|---|---|
| 1 | **推送已上线** | 押金用户付了钱却收不到"扣款/退款"通知 = 投诉温床 |
| 2 | **退款流程已跑通并压测** | 3 个工作日到账是硬承诺 |
| 3 | **客服 SLA 已就位** | 升级投诉率红线 0.05%，没有客服撑不住 |

**⚠️ 建议：先只开放「达标全退」这个最安全的形态，扣收比例从低档起步（20% / 25%，即优秀与卓越两档），观察投诉率后再放开。**

### 5.3 技术实现要点

| # | 要点 | 说明 |
|---|---|---|
| 1 | **支付模块做成可插拔 `payment` 接口** | 小程序 / Android / iOS 各自实现，同一套订单与退款逻辑 |
| 2 | **订单表 / 流水表 `pledge` / `order` 独立** | 逐用户独立记账，**不与经营资金混同**（长租公寓判例） |
| 3 | **退款走原路** | 微信 / 支付宝 / Apple 各自的退款 API；**不做提现** |
| 4 | **退款时限 ≤ 3 个工作日** | 结算后自动发起；用户申请也必须 3 个工作日内到账 |
| 5 | **扣收金额在服务端计算** | 客户端不传扣收比例 → 防篡改；公式见需求规格 R10.3 |
| 6 | **失败扣收部分不计入平台收入** | 是违约金性质，用于覆盖服务成本；**平台不得从押金中获利** |
| 7 | **协议勾选与留痕** | 支付前必须勾选押金协议；**协议版本号 + 时间戳入库**（争议时举证） |
| 8 | **iOS Bundle ID 与支付配置留位** | 包名不可改，将来要加支付不能动 |

## 六、技术栈

### 6.1 总览

```
        小程序（微信原生）           App（Flutter）
                ↓                        ↓
                └──── 后端 API ─────────┘
                   （同一套 schema）
```

| 层 | 选择 | 理由 |
|---|---|---|
| **小程序端** | **微信小程序原生（WXML + JS）** | `onShareTimeline` / 小程序码 / 静默登录 / 订阅消息能力最完整；**裂变链路是生命线，不能冒险用跨端框架** |
| **App 端** | **⭐ Flutter** | 一套代码出 iOS + Android；相机 / 本地存储 / 推送插件生态成熟 |
| **后端** | **自建 / BaaS（不绑微信云开发）** | 云开发对非微信客户端支持有限；App 端必须能直连 |
| **数据库** | 单集合起步，不引 MySQL | |
| **图片处理** | 服务端压水印（缩放后压）+ 裁剪缩略图 | |
| **OCR** | 腾讯云 OCR（通用/手写） | 提取体重秤读数与手写随机词 |
| **推送** | **腾讯云移动推送 TPNS**（首选）或个推 / 极光 / 友盟 | 一次接入覆盖 iOS + 国内各 Android 厂商 |
| **跨端复用** | **只复用后端 API 与设计规范（Figma token），不复用 UI 代码** | 两端交互模式差异大（相机权限、分享、推送授权） |

### 6.2 ⭐ Flutter 选型落地

**确认用 Flutter，需要配套的决策：**

| 项 | 决策 | 说明 |
|---|---|---|
| **状态管理** | **Riverpod**（或 Bloc） | Flutter 社区事实标准，比 Provider 更适合中大型项目；无 BuildContext 依赖 |
| **路由** | **go_router** | 支持声明式路由 + 深链接（**App 分享链接落地必需**） |
| **网络** | **dio** | 支持拦截器（统一鉴权、错误处理、埋点） |
| **本地存储** | **shared_preferences + sqflite** | sqflite 存离线打卡队列 |
| **相机** | **camera** | 需自定义取景框叠随机指令（比小程序 `chooseMedia` 更强） |
| **图片压缩/水印预览** | **flutter_image_compress** | 客户端压缩 + 预览，最终水印仍由服务端压 |
| **推送** | **TPNS Flutter 插件**（`tpns_flutter_plugin`） | 见 6.3 |
| **统计埋点** | **友盟 Flutter SDK** 或自建 | 到达率/点击率/转化漏斗都要埋 |
| **包名 / Bundle ID** | `com.xxx.lede` / `com.xxx.lede` | ⚠️ **一旦上架不可改**，现在就要定死 |

**⚠️ Flutter 的三个已知坑：**

| 坑 | 说明 | 对策 |
|---|---|---|
| **iOS 上架需要 Mac** | 打包 iOS 必须在 macOS + Xcode 上做 | CI 用 macOS runner；**开发期就要确认有 Mac** |
| **包体积** | 空包约 20MB+，加图片/推送/OCR 会更大 | 资源压缩 + 首屏按需加载 |
| **热更新限制** | **iOS 禁止热更新代码**（App Store 规则 3.2.2） | 不依赖热更新做紧急修复；服务器端配置化下发 |

### 6.3 ⭐ 推送选型：腾讯云移动推送（TPNS）

**核实结论：**

> 腾讯云 Push 覆盖 **华为、荣耀、小米、OPPO、vivo、魅族、蔚来、FCM、APNs** 等主流厂商通道，
> 官方明确支持 **Android、iOS、微信小程序多端框架、Uni-App、React Native、Flutter** 等平台，
> 且 **Flutter SDK 持续更新**（2026-06 版本仍在适配 AGP 9.0、修 iOS 偶发崩溃）。

**Flutter 侧可用插件（已核实存在）：**

| 服务 | Flutter 插件 | 备注 |
|---|---|---|
| **腾讯云信鸽 TPNS** | `tpns_flutter_plugin` | ⭐ **首选** —— 通道最全、Flutter 支持最好、免费版长期免费 |
| 个推 | `flutter_getui` / `getui-flutter-plugin` | 备选 |
| 极光 | `jpush_flutter` | 备选 |
| 友盟 | `umeng_push` | 备选，U-Push 聚合小米/华为/魅族/OPPO/vivo |
| 百度云推送 | ❌ Flutter 未找到 | 不考虑 |

> **⚠️ FCM 在国内多数机型不可靠，只能作为海外或补充通道。**

**推送配置要点（腾讯云官方）：**

| # | 要点 |
|---|---|
| 1 | **必须正确配置厂商的「消息分类」** —— 配错会被厂商降级处理，推送不及时或收不到 |
| 2 | **华为 / 荣耀必须配置证书指纹**，否则离线推送不生效 |
| 3 | **OPPO / vivo 有消息分类新规**，需在控制台按「系统消息 / 重要消息」类申请 |
| 4 | **每日推送总量受厂商限制**（按订阅数动态计算），需关注额度 |
| 5 | 厂商资源文件名**不能改**，否则集成失败 |

**我们只需 4 类推送：**

| 推送 | 优先级 | 频次 |
|---|---|---|
| **断卡** | ⭐ 最高（必达） | 低频 |
| **判负 / 被判作弊** | ⭐ 最高（必达） | 极低频 |
| **结算（结局）** | ⭐ 高 | 极低频 |
| **每日打卡提醒** | 低（可降级/可关） | 每日 |

> **因为高优先级推送频次极低，厂商的每日额度完全够用 —— 这是我们消息量的天然优势。**

### 6.4 后端一次设计，两端共用

> **⚠️ 关键约束：数据库 schema 从第一天就按双端设计 —— 用户体系、认证方式、API 边界都不能绑死微信。**

| 决策 | 选择 | 理由 |
|---|---|---|
| 认证 | **后端签发自己的 token**（JWT 或类似），小程序用 `wx.login` 换 code → 后端换 openid → 发 token；App 用手机号 → 发 token | 同一套 token 机制，两端通用 |
| 用户标识 | 后端内部用 `uid`，`openid` / `phone` 作为绑定渠道 | 不绑微信 |
| API | **REST + 统一鉴权中间件** | 两端共用 |

**详细数据模型见第八节。**

## 七、关键实现决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 拍照方式 | 小程序 `wx.chooseMedia` + `sourceType: ['camera']`；App 原生相机 | 关闭相册入口，堵住"翻旧图" |
| 权限链路 | `scope.camera` + `scope.record` 分离申请 | 必须在用户点击的交互回调里触发 `wx.authorize`；被拒过要引导 `wx.openSetting`；**iOS 上系统层关了微信权限时 `openSetting` 里可能不显示开关**，需额外文案兜底 |
| 内容安全 | 小程序：文字 + 图片走 `mediaCheckAsync` | 微信官方接口 `media_type` 支持 `1:音频; 2:图片`，本产品只用图片通道 |
| 内容安全（App） | **自建**（图片鉴黄 + 文本审核 + 人工兜底） | ⚠️ **App 推送与分享不走微信审核**，用户昵称 / 体重 / 物证必须自己过滤 |
| 支付 | **押金 = 履约保证金，走普通支付**；**iOS 走虚拟支付 + 高价档抵消抽成** | 见第五节；完整规则见 `需求规格.md` R10 节 |
| 打卡记录不可篡改 | 只追加结构 + 服务端时间戳 | 每条打卡写入后不提供编辑接口；纠错走"作废并重打"并留痕 |
| 身份 | 微信 openid + 昵称头像，**不强制取手机号**；App 端支持手机号登录 | 减到最少个人信息收集，降低审核与隐私成本 |
| 随机词生成 | 服务端生成 + 会话存储 | 必须服务端下发，客户端拿不到未来词 |
| 水印 | 服务端压（时间 + 编号） | 客户端水印不可信：手机时间可改、位置可伪造。**水印必须在缩放之后压**，否则跟着图被缩看不清 |
| 抽检升级 | 标记后升级为完整人工复核，直到标记解除 | 抄 DietBet："平时便宜、出事升级"。把复核成本只花在真正可疑的人身上 |
| 位置 | 只在打卡那一刻读一次，不做持续采集 | 最小化采集。隐私政策要写明 |

## 八、数据模型（草稿）

```
flag        // 目标：发起人、起始/目标体重、周期(7/14/30/90)、开始日、结束日、状态、
            //       规则快照、见证席列表、监督席计数、结算结果、信用分变动、证词id
            //       ⚠️ 结束日由周期算死（= 生效日 + 周期 - 1），不可自定义
            //       ⚠️ 筹备期：发起日 + 24h 为筹备期截止，其后为生效日
            //       ⚠️ 初始档位 / 有效档位、押金、起始称重物证均锁进规则快照
checkin     // 打卡：flagId、服务器时间、图片路径、OCR读数、
            //       水印编号、状态(正常/存疑/作废)、随机词id
witness     // 见证席：flagId、用户、贡献分、见证信用分、来源(invited/applied/recruited)、
            //       状态(pending/accepted/declined/expired/withdrawn)、
            //       发出时间、接受截止时间(发起日 + 12h)、接受时间
            //       ⚠️ 名册在筹备期结束时冻结：冻结后不可增删
            //       ⚠️ pending 状态不公示姓名（见 W7.5）
supervisor  // 监督席：flagId、用户、订阅时间、互动次数、结局通知状态
            //       ⚠️ 人数不限，不受见证席坑位约束
message     // 留言：flagId、用户、角色(监督席/见证席)、内容、匿名标记、
            //       审核状态(通过/拦截/删除)、删除时间、创建时间
            //       ⚠️ 仅目标人可见；不进广场、不进记录卡、不进分享图
verdict     // 判定：flagId、见证人、判定项(通过/存疑/作弊)、reason(举报理由，选填)、
            //       是否被复核校准、是否成立、
            //       状态(已判定/未响应)、节点序号
            //       ⚠️ 表态（通过/存疑/作弊）算「已判定」，未响应不算
            //       ⚠️ 连带责任仅由「已判定且判通过」者承担
            //       ⚠️ 「作弊」= 见证席的实名举报，不再单设 report 集合
objection   // 异议：flagId、节点序号、异议人、角色(监督席)、理由枚举、
            //       状态(已提交/已启动复核/不成立/已结算)、是否恶意
            //       ⚠️ 仅监督席可提交；≥3 票才启动人工复核；1-2 票只入库
            //       ⚠️ 实名对平台，匿名对发起人
appeal      // 审核后异议/申诉：flagId、节点序号、提交人、角色(发起人/见证席/监督席)、
            //       理由、窗口截止时间、状态(待审/已受理/驳回/已重审)
            //       ⚠️ 人工出结论后开 24h 窗口；窗口内提异议 → 转人工重审一次即终局
node        // 节点：flagId、节点序号(1=起始称重 / 2..n-1=中期 / n=结束称重，n 由周期定)、
            //       节点名(起始称重/中期称重/中期复核/结束称重)、节点日(第N天)、
            //       见证门槛(min(应到人数, max(2, ceil(应到×50%))))、应到人数、已判定数、
            //       是否降级为「仅平台审核」、窗口截止时间、该节点实到人数快照
            //       ⚠️ 已判定数 < 见证门槛 → 该节点判定不生效，转平台审核
            //       ⚠️ 「作弊/存疑」不受门槛约束：≥1 人即转人工复核
            //       ⚠️ 节点数按周期缩放：7天=2 / 14天=3 / 30天=4 / 90天=4（见 R5.4）
pledge      // 押金：flagId、用户、金额、档位、支付流水号、扣收比例、
            //       退还状态、服务费扣除金额、退还时间、协议版本号、
            //       区间下界、区间上界（区间制：下限=周期下限，上限=min(信用上限,周期上限)）
            //       ⚠️ 发起时即支付；筹备期内不退还；档位降档不触发任何追缴
user        // 用户：openid/手机号、信用分、见证信用分、连续打卡天数、失败次数
creditlog   // 信用分流水：userId、事件、分值、说明、时间（可审计）
shortcode   // 归因短码：短码 → { inviterId, flagId, role, channel, expiresAt }
```

**设计要点：**
- `flag` 里的**规则快照**很重要 —— 发起时把当时的规则、目标、起止日完整存一份，之后改规则也不能影响已发起的 Flag
- **节点计划在发起时算好并写进规则快照** —— 节点数与节点位置由周期决定（见 R5.4），**在发起那一刻定死**：7 天 → 第 1/7 天；14 天 → 第 1/7/14 天；30 天 → 第 1/10/20/30 天；90 天 → 第 1/30/60/90 天。**平台后续调整节点规则，不影响已发起的 Flag**
- **`node` 集合按 `flagId + 节点序号` 建唯一索引** —— 节点数可变，序号不能变（已提交的 `verdict` / `objection` / `appeal` 都引用节点序号，序号必须稳定）
- **筹备期状态机存在 `flag.status` 里** —— `prep`（筹备中，24h）/ `running`（已生效）/ `success` / `failed` / `stopped` / `void`。**筹备期内只能追加见证席邀约**，其余写操作一律拒绝
- **`witness` 的坑位计数用「accepted + pending」** —— 上限 10；pending 过期或被拒后释放（见 R5.5.2）
- **`flag` 存「初始档位」与「有效档位」两个值** —— 有效档位每关一个节点取 min 一次，**只降不升**（见 R1.2.1）
- `creditlog` 单独存流水，信用分是可追溯的，不是随手改的数字
- 打卡记录 `作废` 而不是删除 —— 留痕
- `pledge` 用**逐用户独立记账**，不与经营资金混同（长租公寓判例）；**扣收比例由服务端计算，客户端不可传**
- `shortcode` 用 Redis + TTL（90 天），scene 只放 5 字符短码（微信限制 32 字符且不能有中文）
- **`verdict` 承担见证席举报**（判定「作弊」即举报，理由存 `verdict.reason`）—— 不再单设 `report` 集合，避免同一个动作两处记账
- **`objection` 与 `appeal` 分开** —— `objection` 是**投票**（监督席，满 3 票才启动复核）；`appeal` 是**复议**（人工出结论后的 24h 窗口，任何角色可提，触发人工重审一次即终局）
- **`appeal` 带 `窗口截止时间`** —— 窗口的开关靠时间戳判断，不靠状态机，避免"忘了关窗口"的悬挂状态

## 十一、App 的获客路径（不靠买量）

**"能做 App"和"能获客"是两回事。** App 的自然流几乎为零。

**但我们的路径不同：**

| | 达目标 / 脸疼 | 我们 |
|---|---|---|
| 获客方式 | 买量 + 应用商店 ASO | **微信分享裂变 → 小程序 → 装 App** |
| 谁装 App | 新用户直接装 | **已经立了 Flag 的人**（已投入，有动力） |

> **我们不需要让"随便一个路过的人"装 App。**
> **我们只需要让"已经立了 Flag、已经被围观、已经上瘾"的人装 App。**
> **这些人已经是高价值用户 —— 他们不需要被获客，只需要被"提醒去装"。**

**转化路径：**
```
微信扫码 → 小程序开始打卡（当天就能开始，流失率最低）
    ↓ 一周后"这个我得每天用"
引导装 App（分享卡片里提示"装 App 可接收断卡提醒"）
    ↓
App 拿到完整推送 → 飞轮闭合
```

**这条路径的转化率远高于买量。**
